# Jetson策略试验交付与回退

**当前是待Jetson构建、待实车验证的试验源码。** Windows已验证的图像效果、CPU耗时和理想通道不能替代Jetson性能或VT03→VT13实测。本轮不改C板，不操作ToDesk，不执行车端命令；正常客户端不需要更新，因为入围档仍传标准H.264、未使用接收后处理。

## 改动文件

仅在`autoaim/my_lf_INF_20261025`增加显式`--cw-profile`试验分支：

| 文件 | 改动 |
|---|---|
| `io/video_sender/cw_trial.hpp`（新增） | 统一试验参数、20ms门限、仅移除SEI的Annex B过滤 |
| `io/video_sender/cw_tx_worker.hpp`（新增） | 独立有界发送线程，整帧取出、逐包交接，拒绝时重试原包，退出不突发清队列 |
| `io/video_sender/video_sender.hpp/.cpp` | 全视野SWS_AREA、彩色、592 B/2包、4736bit VBV、线程/AQ/GOP参数、IDR恢复、整帧积压上限 |
| `io/gimbal/gimbal.hpp/.cpp` | 试验专用交接与服务；沿用同一串口写锁、半帧续写、控制优先级，在完整309 B写入后至少再等20ms才开始下一视频包 |
| `src/standard_mpc.cpp` | `--cw-profile`入口与独立发送线程生命周期 |
| `tests/video_sender_test.cpp` | 同一参数/编码路径及逐包时间记录；不发串口、不驱动执行器 |

未带`--cw-profile`时仍走原YAML、原编码与发送路径。车端旧灰度8包突发配置作为**链路修复对照**，不是双包基线。试验档优先级高于旧`video_*`和尺寸/fps覆盖参数，防止无意放宽约束。

| 试验名 | 对应仿真配置 | 取舍 |
|---|---|---|
| `baseline` | `baseline.ini` | 彩色192×152，GOP10，原始双包对照 |
| `smooth` | `one-160.ini` | 160×128、单线程单VCL片；细纹理分辨率较低 |
| `detail` | `one-320.ini` | 320×256、GOP10；旧记录存在桌面状态不明时的低帧率；解锁后结果见统一验收 |
| `detail-aq0` | `one-320-aq0.ini` | 320×256、关闭AQ；旧运动记录存在桌面状态不明时的低帧率；解锁后结果见统一验收 |
| `quality` | `one-320-gop20.ini` | 320×256、GOP20；画质较好，丢包后的等待可能更长 |

全部20fps、约74548bps、slow、完整视野、彩色、无锐化。基线auto线程/slices4，其余单线程/slices1；实际分片须以抓包复核。Jetson使用已有libavcodec/libx264，而Windows使用FFmpeg 7.1.1子进程：版本、颜色转换、强制IDR及耗时必须实测，不能宣称二进制码流完全一致。Windows超限会重启编码进程；车端使用libx264`forced-idr`，语义目标相同但恢复耗时尚未对齐。

## 传什么 → 传到哪 → 如何确认

在Windows仓库的`compression-war`目录生成**仅8个改动/新增源码**的包：

```powershell
python .\tools\package_vehicle_trial.py --out .\runs\delivery\RM26_cw_trial_20261109_r2.zip
```

通过ToDesk手动把该ZIP及同名`.sha256`传到Jetson的`/home/nvidia4/cw_transfer/`。解压到**独立副本**`/home/nvidia4/my_lf_INF_20261025_cwtrial/`，不要覆盖当前服务使用的`/home/nvidia4/my_lf_INF_20261025/`，不要覆盖标定、模型和YAML。

下面是届时手工执行的准备命令；这次没有在车上执行：

```bash
cd /home/nvidia4/cw_transfer
sha256sum -c RM26_cw_trial_20261109_r2.sha256
test ! -e /home/nvidia4/my_lf_INF_20261025_cwtrial || exit 1
python3 - <<'PY'
import shutil
shutil.copytree('/home/nvidia4/my_lf_INF_20261025', '/home/nvidia4/my_lf_INF_20261025_cwtrial',
                symlinks=True, ignore=shutil.ignore_patterns('build','build_cw','records','logs','.git'))
PY
cd /home/nvidia4/my_lf_INF_20261025_cwtrial
unzip /home/nvidia4/cw_transfer/RM26_cw_trial_20261109_r2.zip
sha256sum -c SHA256SUMS
cmake -S . -B build_cw
cd build_cw
make standard_mpc video_sender_test -j2
./standard_mpc --help
./video_sender_test --help
stat -c '%y %s %n' standard_mpc video_sender_test
sha256sum standard_mpc video_sender_test
```

两份help都必须出现`cw-trial-20261109-r2`及`cw-profile`，8个源码摘要全部OK。**构建报错就保留原始输出，停止这一分支，不用旧exe冒充新版本。** 未在Jetson完成这些步骤前，不标为车端已可用。

先跑无相机、无串口的编码试验（仅生成本地数据），核对超限、输出参数及`cw-packet-times.csv`，再拷回Windows复核码流：

```bash
cd /home/nvidia4/my_lf_INF_20261025_cwtrial
./build_cw/video_sender_test /tmp/cw-quality-check --cw-profile quality --seconds 15
```

USB写入完成时间不是USART6线上时间；C板排队和USB调度仍可能改变线上的间隔。`HAL_OK`、上位机写入计数均不能代替逻辑分析仪证据。正常短写按已确认字节数续写；若串口抛异常，内部已写前缀可能未知，试验分支停止后续控制/视频写入并报错，要求结束试验重新建立传输，禁止猜长度继续。串口故障会使本轮试验无效。`[CW timing]`输出本机实际前处理/编码均值、最大值及待处理覆盖数，现场据此核对Jetson是否跟得上。

## 现场实测顺序与回退

1. 先用**原目录、原服务、原图传配置**验证C板修复。固定画面/变化画面与无操作/有操作分开，确认第一处异常是否消失。
2. 再测独立副本的`baseline`，核对完整309 B帧、50包/s、收到300 B包、关键帧恢复及实际显示。
3. 最后测`smooth`与`quality`；研究档`detail/detail-aq0`单列。不要同时改电控和压片参数来解释结果。

只有安排好现场控制权限后，才手动停旧服务、前台运行试验；以下命令**会启用自瞄/车端控制**，不属于这次离线操作：

```bash
sudo systemctl stop autoaim-20261025
cd /home/nvidia4/my_lf_INF_20261025_cwtrial
./build_cw/standard_mpc configs/standard3.yaml --cw-profile=baseline
# 下一次前台启动改为 --cw-profile=smooth 或 --cw-profile=quality
```

回退使用另一终端定向停止试验进程、恢复原服务；不要在客户端按CTRL：

```bash
trial_pattern='^\./build_cw/standard_mpc configs/standard3\.yaml --cw-profile='
pkill -INT -f "$trial_pattern"
for attempt in $(seq 1 10); do
    pgrep -f "$trial_pattern" >/dev/null || break
    sleep 1
done
if pgrep -f "$trial_pattern" >/dev/null; then
    echo '试验进程尚未退出，先处理卡住的进程；禁止同时启动原服务。'
    exit 1
fi
sudo systemctl start autoaim-20261025
systemctl status autoaim-20261025 --no-pager
```

本方案未改服务文件、开机启动项及原目录；回退不需要重新烧录、不需要用试验文件覆盖旧文件。

现有主循环仍可能在`camera.read`或`gimbal.q`等待；它们属于原车流程，本轮未改。发送线程独立不等于相机输入已与自瞄解耦，Jetson实测须同时看主循环FPS和待处理覆盖数。上述退出检查正是避免阻塞时SIGINT未被主循环处理，却又启动第二个串口进程。
