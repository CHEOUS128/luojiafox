# 双包实时链路仿真（2026-11-09）

这是独立于正常客户端的 Windows 程序。源视频在正常速度播放的同时，图像经过实际预处理、持续编码、协议封包、限速、接收解码和绘制。当前起点为**彩色、完整视野、只等比降低分辨率**。

## 直接运行

从仓库根目录在PowerShell执行：

```powershell
Set-Location -LiteralPath '.\compression-war'
& '.\scripts\启动-实时仿真.bat'
```

窗口打开后点“开始”。默认读取现有 `素材\car_raw.bgr`，按 `1280×1024 @20 fps` 解释；没有这份原片时打开文件选择窗口。文件选择、输出尺寸、帧率、限速和裸帧尺寸在停止时可改。源视频有多少视野，两栏就保留多少视野；适配尺寸产生黑边，**不裁边、不拉伸**。

也可以直接传普通视频（MP4、MKV、MOV、AVI等，以本机 FFmpeg 支持为准）：

```powershell
& '.\scripts\启动-实时仿真.bat' 'D:\素材\我的视频.mp4'
```

普通视频使用源时间戳。其文件解码是“模拟相机的素材供给”，耗时单列；从原片按节拍发布到处理链开始，计量后续实际耗时。解码供给迟到超过一帧时丢弃过期图像，不通过放慢原片来掩盖处理跟不上。

裸帧没有尺寸、颜色或帧率信息，必须填写导出时的真实参数。错误的尺寸可能导致图像错位或尾部不完整；不要根据文件名猜。首版支持紧排 BGR24 裸帧 `.bgr/.raw/.bin`，源尺寸每边不超过4096。

## 首版固定策略与模拟范围

默认：`192×152`输出框、目标20 fps、50包/秒、H.264彩色YUV420P、GOP10。**所有帧（包括关键帧）最多2包、592 B净码流**，无锐化、无图像还原、无自适应算法。按每帧2包预留，理论容量25 fps；目标超过25 fps直接拒绝。程序不为通过验收自动降低分辨率。

编码码率沿用车端预算公式：`50 × 0.85 × 296 × 8 ÷ 1.35 = 74548 bit/s`。85%只用于编码预算，令牌积累仍按50包/秒；VBV为4736 bit。编码后去除NAL类型6的SEI说明，保留SPS、PPS和全部图像编码数据，自动测试比较去除前后的逐帧像素SHA256。码率和VBV不能保证每帧长度，**编码后仍逐帧检查592 B硬上限**；超限整帧丢弃、记录原因并重启编码进程使下一帧为IDR，绝不截断或拆第三包。重启的实际代价计入耗时。

8包及18944 bit VBV属于此前旧档，记录保留在[旧档验收记录](../档案/2026-11-09-八包实时试运行.md)。它们不再是实时入口默认参数，离线对账入口保持原样。

链路依次走：

1. 原片按时间戳到达，预处理执行等比缩小与补边。
2. 持续 FFmpeg 进程逐帧输入BGR，输出真实H.264访问单元；不先编码整段视频。
3. 封成300 B数据：`2 B长度BE + 2 B序号BE + 最多296 B码流 + 补零`。
4. 再封成309 B的0x0310外层帧，按车端格式写入CRC8、CRC16和外层序号。
5. 令牌够整帧包数才释放；发送积压按车端策略丢最老整帧。理想通道每包至少占用 `1000/包率` ms，默认20 ms，迟到不突发追赶。
6. 官方端适配器校验外层帧，提取300 B，按真实 `CustomByteBlock.data` Protobuf字节格式序列化、反序列化后投递接收队列。
7. 独立快照中的客户端代码实际解包、解析H.264、等待关键帧、解码。接收队列最多256包，显示端取最新图像。
8. 接收后处理接口首版原样返回，窗口实际绘制解出的图像。

界面明确标注：**C板旁路、理想通道**。这里不运行官方MQTT服务器，也没有复刻官方软硬件内部实现；本次模拟其已知消息格式和通信容量。尚未测量的VT03/VT13损失及额外延迟未加入默认档，结果不能作为那一跳已被排除的证据。

实时接收端位于 `live_rx/`，以当前客户端解码代码为独立快照；来源和原始SHA256写在同目录的 `客户端代码来源.txt`。实时目标不再编译客户端源文件。第三方解码库、spdlog和stb仍从仓库现有目录只读引用。历史离线目标维持原来的客户端解码器引用，两者头文件搜索目录隔离。

## 画面和计时怎么读

- 左栏在原片入链时更新，保持原片的颜色和完整内容。
- 右栏实际解出并完成接收后处理后才更新；没有新图时保留上一张。
- **至提交显示延迟**：该帧完成GDI绘制提交的实际时间，减去同一帧原片入链时间；包含预处理、管道编码、排队、传输、解析缓冲、解码、后处理及等待绘制。它不是显示器发光时刻的硬件测量。
- **画面年龄**：当前时刻减去右栏这一帧的原片入链时间。冻结时这个数持续增长。
- **更新fps**：过去一秒实际提交的新图像数量，不是目标帧率或窗口重绘次数。
- 界面分别显示实际解码fps、显示fps、实际包率，以及当前帧净码流字节数和包数/2；勾选“右栏原生1:1”可按192×152原生像素查看。放大显示不会增加码流分辨率。
- 所有时间来自同一个单调时钟。本机的真实处理代价有参考意义，不换算为Jetson性能。

帧号由只读观测信息关联：只将完整收到且码流匹配的访问单元关联到原片。观测信息不进入载荷、不修补丢失字节，也不改变解码决策。关联不了就记 `decoded_unassociated`，窗口显示延迟未知，不能按解码输出序号硬配。

观测编号绑定到解析器实际接收的字节范围，再核对该帧码流，静止画面产生重复码流时也不按相同内容猜较早的帧。测试会把此副本与未修改客户端解码器的逐帧像素结果比较，分别覆盖无丢包和定点丢包。

当前客户端解码代码使用流式解析器，可能等后续数据才吐出前一帧。这段等待原样进入延迟。EOF只刷新已经收到的解析器数据，不强发尚未走完限速通道的包。

## 日志与图像

每次默认创建 `runs/live/<时间戳>/`：

| 文件 | 内容 |
|---|---|
| `events.csv` | 原片、处理、编码、令牌释放、到包、解码、显示等实际事件时间 |
| `per_frame.csv` | 每个原片帧的阶段时间、字节/包数和丢弃原因；未知时间为-1 |
| `quality.csv` | 独立任务计算的PSNR-Y、SSIM-Y，比较缩小后的编码输入与正确关联的解码图像 |
| `summary.txt` | 实际配置、计数、延迟分布、最小包间隔和队列峰值 |
| `tx-0310.bin` / `tx-times.csv` | 每个实际发出的309 B外层帧、实际时间、接受/丢包/接收溢出状态 |
| `rx-300.bin` / `rx-times.csv` | 真正进入接收队列的300 B数据段及实际到包时间；无原片观测编号 |
| `decoded.csv` | 实时解码输出的顺序、解码器编号、PTS、尺寸和RGBA像素SHA256；后处理之前记录 |
| `display-seconds.csv` | 去掉前2秒启动和输入结束后的收尾，每个完整1秒实际提交的新图数量，少于15即FAIL |
| `replayed-decoded.csv` / `rx-replay-verification.txt` | 独立接收包重放的逐帧摘要与像素一致性结果 |
| `wire-verification.txt` | 外层CRC/序号、内层补零、独立H.264访问单元解析、关键帧长度、包间隔和滚动1秒预算核对 |
| `last-source.png` / `last-received.png` | 结束时两栏各自保留的最后一张图；两张的源帧时刻可以不同 |

逐帧表保留完整运行，运行内存中的观测记录最多512项，延迟分布最多使用最近4096个显示样本。质量任务队列最多2项，忙不过来只跳过质量统计，不阻塞视频链路。

报告单列H.264字节、每包4 B内层头、补零、300 B数据段总量、309 B外层帧总量。**PNG文件大小不代表传输大小**。实际右栏仅由收到的数据解码产生；没有收到任何包时不能产生图像。证据文件会持续写盘，写入代价也在实际运行中发生。指定的输出目录若含旧记录则拒绝运行，避免旧图或旧包混入新测试。

## 脱离原片独立复核

完整核对一份已自然结束的会话（按实际到包时间重放，60秒会话约需60秒）：

```powershell
.\cw_wire_verify.exe 'runs\live\你的会话目录'
```

只需要把该会话的 `rx-300.bin`、`rx-times.csv`、`decoded.csv` 三个文件复制到一个空目录，就能独立核对接收端像素：

```powershell
.\cw_wire_verify.exe --rx-only 'D:\独立证据目录'
```

此入口只读取这三个输入文件。解码器仅接收300 B包，时间表只决定何时投递；`decoded.csv`只用于输出比较，不参与解码。它不读取原片、发送记录、summary或观测编号，链接的是未修改客户端解码器。数量、顺序、尺寸和全部RGBA像素的SHA256必须一致，否则退出码1。默认完整核对还检查TX/RX对应、309 B外层CRC和序号、300 B补零、每帧最多2包/592 B、SEI已去除且SPS/PPS保留、任意连续1秒最多50包、相邻包至少20 ms。访问单元边界由H.264解析器从实际字节识别，不依赖仿真帧号。

`--headless` 可用于检查链路，但它计量的是消费解码结果的时间，**没有真实绘制**，报告会明确标注。验收显示延迟使用正常窗口模式。

## 编译和验证

```powershell
& '.\scripts\编译-实时仿真.bat'
powershell -NoProfile -ExecutionPolicy Bypass -File '.\scripts\验证-双包实时仿真.ps1' -Full
```

编译脚本在缺失时创建并检查 `C:\rm26cw` 是指向仓库根的junction，在其下 `compression-war` 配置、增量构建，运行协议自检后同步 `cw_live.exe` 和 `cw_wire_verify.exe` 到仿真目录。它不删旧build。自动查找VS2022（本机Community实测），需要C++桌面开发、Windows SDK、CMake、Ninja及 `ffmpeg.exe`。

验证脚本执行相机原片、横竖屏四角运动视频、变帧间隔、25 fps、100 ms预处理/编码/后处理负载、定点丢包、全丢包冷启动、关键帧超限恢复、SEI像素等价、解码副本回归、非法输入、仅三文件重放和篡改证据拒绝测试；`-Full` 额外执行60秒真实窗口绘制及独立重放。测试产物位于 `runs/two-packet-validation/<时间戳>/`，不入库；控制台打印本次目录。

脚本会故意触发非法输入并要求退出码2，篡改证据要求退出码1；最后以 `PASS two-packet realtime and independent wire proof` 判定该次检查通过。`-Full`要求60秒运行中每个稳态完整秒至少15张新画面，未达标直接报FAIL，不放宽包数或更改分辨率。`live_probe` 的 `memory_mb` 是仿真主进程工作集，不含外部FFmpeg进程。变帧间隔素材本身低于15 fps的区段及故障注入档不适用正常档15 fps验收线。

手动复现60秒真实绘制：

```powershell
.\cw_live.exe --input '素材\car_raw.bgr' --loop --duration 60 --autostart --close-on-end --out 'runs\我的实时验证'
```
