# compression-war —— 压片战争仿真平台

> 第四个子系统。目标只有一个：**在 300 B/包、50 包/秒的硬约束下，把一帧图像压得尽可能清楚。**
>
> 这块镜子要说实话的地方在于：它跑的是**客户端的真解码器**，而不是"我以为的解码器"。
> 任何"我这边能看出来、实车看不出来"的差异，都会被它放大暴露。

---

## 一、这个平台在干什么

**一句话：拿一段真实画面，走一遍和实车一模一样的压缩→封包→令牌桶→解码，然后左右并排给你看。**

```
 车上小电脑 (Jetson)                     Windows：compression-war
 ┌──────────────────┐            ┌──────────────────────────────────────────┐
 │ 大恒相机 1280×1024│            │  素材\car_raw.bgr   给播放器左栏（原始彩色）│
 │ BGR 彩色（原生）  │───────────▶│  素材\car192.gray   派生：缩放+黑边+转灰度  │
 │ video_sender_test │  原片导出  └──────────────┬───────────────────────────┘
 │  -c --gray 0      │                          │ 192×152 灰度
 └──────────────────┘                          ▼
                          ffmpeg(libx264) ─▶ H.264 ─▶ 300B 封包 ─▶ 令牌桶 ─┐
                                                                          ▼
                          player.html ◀── 左栏 car_raw.bgr       客户端真解码器
                          （左=原片先出，右=处理完才出，实时显示延迟）
```

**左右两栏的语义（2026-11-07 CH 定的，别改回去）：**

| | 内容 | 什么时候出现 |
|---|---|---|
| **左栏** | **相机原片，原封不动**——彩色 BGR、1280×1024，没缩放、没转灰度、没锐化、没编码 | `t = 这一帧被拍到` |
| **右栏** | 这一帧**处理完**以后客户端才收到的画面：缩放 → 转灰度 → H.264 → 拆 300 B 包 → 令牌桶排队 → 最后一包到齐 → 解码 | `t = 拍到的时刻 + 编码 + 链路` |

灰度、缩放、H.264 **全都是"我们这边后续做的处理"**，只能出现在右栏。
右边必然比左边晚，播放器把这段时差实时显示成「延迟 ms / 落后 N 帧」——
掉帧就表现为**右边画面冻住、落后帧数往上跳**，和实车肉眼看到的一样。

**「和实车一样」也包括编码线程跟不上这件事。** 车端 `VideoSender` 的编码线程只有一个
`pending_frame`，编码慢于相机节拍时，还在等的那一帧会被新帧**直接覆盖掉、永远不进 x264**；
客户端那边就是画面停一下。仿真照这个语义跑（见 §5.6）：`--encode-ms 51` 时 300 帧丢 5 帧；
按车上实测的 51.6 ms 跑 302 帧丢 9 帧（293 进 x264），和车上那轮「302 拍到 / 293 编出来」对得上。

**五段都是"真"的：**

| 环节 | 实现方式 | 为什么这样 |
|---|---|---|
| 编码 | 外部 `ffmpeg.exe` 调 libx264，参数**逐条**照抄 `video_sender.cpp` | 仓库里那份 ffmpeg 静态库**只解不编**（0 个 encoder，验过两次） |
| 编码线程 | 复刻 `feed()` / `worker_loop()`：单槽 `pending_frame`、累加节拍、**编不完就被下一帧覆盖** | 车端就是「同一个时刻只有一帧在编」，跟不上 fps 时那些帧**从没进过 x264**。丢掉的帧不能事后补编，只能从编码输入里拿掉（见 §5.6） |
| 封包 | `src/packetizer.cpp` 逐字节复刻 `encode_and_pack`/`make_transport_packet` | 和实车日志对账能对上（见第五节） |
| 令牌桶 | 复刻 `drain_due`：整帧原子释放、积压丢最老帧 | 这是"为什么掉帧"的答案所在 |
| 解码 | **直接编译 `luojiamaster/源码/src/video/custom_byte_block_video_decoder.cpp`** | 不复制不修改，客户端改了仿真自动跟着改 |

> **为什么不在车上顺便把右栏也解出来？**

> 更关键的是**没有必要**：右栏本来就该由 `cw_sim` 用**同一个客户端解码器源码**解，
> 车上再解一遍等于换了个解码环境，反而会引入差异。车上只负责一件事：把原始彩色数据交出来。

> **文件很大。** 3.75 MB/帧 × 20 fps = 75 MB/秒。15 秒 1.1 GB。
> 传 Windows 只能走 ToDesk（网络共享/网线在这台机上不通），先 `df -h ~` 看一眼。

放别处也行，`D:\cam_raw\video_test_raw.bin` 这种纯英文短路径最省心；
bat 里中文路径是能处理的，但 ToDesk 传大文件本身容易被长路径拖慢。

#### 当场排错：`GXOpenDevice failed` / `Permission denied`

相机是 `GX_ACCESS_EXCLUSIVE` 独占打开（索引 1），**任何一个进程占着就开不了**。
`systemctl is-active` 说 inactive 也不够——进程可能还在退，或者有手动跑的残留：

```bash
sudo systemctl stop autoaim
sudo pkill -9 -x standard_mpc
sleep 1
pgrep -x standard_mpc             # 没有输出才算干净
```

> ⚠ **别用 `pkill -f standard_mpc`。** 2026-11-07 实测：`-f` 匹配整条命令行，
> `sudo pkill -9 -f standard_mpc` 自身的 argv 里就有 "standard_mpc"，
> 结果先把父进程 sudo 杀了（终端只打印 `[1] 71361 killed`），目标进程毫发无损。
> 用 `-x` 按进程名精确匹配，不带 `-f` 就没有这个问题。

> **2026-11-07 实测：杀完几秒就被重新拉起来。** 清完场再跑，相机仍然 `GXOpenDevice failed`，
> 而 `ps` 里冒出一个新的 `~/my_lf_INF_20261025/build/standard_mpc`。
> 说明有个**没找到的守护/cron/脚本**在拉它。先揪出父进程再清场：
>
> ```bash
> ps -o pid,ppid,lstart,cmd -p $(pgrep -f 'my_lf_INF_20261025/build/standard_mpc')
> ps -fp <上面那个 PPID>
> systemctl list-units --type=service --all | grep -iE 'aim|standard|watch|guard'
> systemctl list-timers --all | head
> sudo crontab -l; sudo ls /etc/cron.d; ls -l /etc/rc.local
> ```
>
> 抢跑办法（守护只隔几秒，必须一条命令连着做）：
>
> ```bash
> sudo systemctl stop autoaim; sudo pkill -9 -x standard_mpc; \
>   sudo ./build/video_sender_test records/raw -c configs/standard3.yaml --seconds 15
> ```

> **`autoaim.service` 指向的是旧目录（2026-11-07 确认）。** `systemctl cat autoaim` 显示
> `ExecStart=/home/nvidia4/my_lf_INF_20261013/build/standard_mpc`，也就是
> **开机自启跑的是 20261013 那版，不是 `~/my_lf_INF_20261025`**。
> 这个 unit 现在是 `disabled`，但每次 `systemctl start autoaim` 都会把**旧版**拉起来，
> 和当前代码两份进程一起抢相机和串口。
>
> 2026-11-07 17:24 实测 `ps` 里同时躺着两个：
> `71643 .../my_lf_INF_20261013/build/standard_mpc`（`start autoaim` 拉起来的旧版）
> 和 `72175 .../my_lf_INF_20261025/build/standard_mpc`（**另有东西拉起来的**，不是这个 unit）。
> 所以 `pkill` 之后清干净了、几秒内又会被拉回来——**先找出那个守护**，否则白忙。

> **`systemctl stop autoaim` 停不掉 `standard_mpc`。**
> 两次都是 stop 之后进程还在（一次 PID 3402、一次 58145，前者只靠 `kill -9` 才清掉）。
> 而且这个进程的路径是 `~/my_lf_INF_20261025/build/standard_mpc`，
> 但 `systemctl status` 里 unit 的描述写的是 `lf_INF 20261013`——
> **服务很可能根本没在管这个进程**（unit 指向旧目录，或 `Type`/`KillMode` 不吃它）。
> 顺手确认一下平时到底是怎么起自瞄的：
>
> ```bash
> systemctl cat autoaim | grep -E "ExecStart|WorkingDirectory|Type=|KillMode="
> ```
>
> 所以清场一律用 `pkill`，别指望 `systemctl stop`。

之前那个 `mkdir: cannot create directory 'records/raw': Permission denied` 是另一回事：
`records/` 被 sudo 跑的程序建过，属主变成 root 了。新版程序自己建目录，**不用再 mkdir**；
真要清就 `sudo rm -rf records/raw && ls -ld records`。

**判断车上那份源码是新是旧**，只看一行：`./build/video_sender_test --help | grep -- --seconds`。
没输出 = 还是旧文件，别往下跑，先按 §2.2 开头把 `tests/video_sender_test.cpp` 传上去。

### 2.3 转成仿真输入

**从这里开始，全部在 Windows 上，不碰小电脑。** 三条命令，按顺序：

x264 线程自动 / 120 帧）。想跑满 300 帧再给 `0 40 8 51 300`。

第 0 步是把车上那份 `video_test_raw.bin`（1.1 GB）用 ToDesk 拷下来，**直接存成**
`compression-war\素材\car_raw.bgr`（改名即可，脚本会跳过内部那一遍 1.1 GB 复制）。
放别的名字/别的位置也能跑，把路径换掉就行：

```bat

```

> **跑之前先确认 exe 是新编的**（1 秒，不做会白跑）：
> `cw_sim.exe --help` 的「全部参数」里有 `--ref-pix` 和 `--encode-ms` 两行。
> 2026-11-07 14:47 那版 exe 没有这两个开关，跑仿真.bat 会直接报「不认识的参数」。
> 一键编译.bat 跑完会自动把新 exe 拷到 `compression-war\` 和 `scripts\` 两处。

第 2 个参数就是车上打印的「相机实际出图」，**不是 192×152**。
写错了第一步会读出乱码，脚本会在字节数校验那关拦住并提示你改。

脚本干两件事，**这一步的分工就是播放器左右栏的分工**：

1. 车端原片**原封不动**存成 `素材\car_raw.bgr`（只做像素格式归一，不裁不缩不转灰度）
   —— 这是相机原片，播放器左栏显示它，**不参与任何指标**；
2. 再从它派生编码器输入：等比缩放 + 居中黑边 + 转灰度 → `素材\car192.gray`
   —— 这一份才是车端 `VideoSender` 真正拿到的画面，右栏显示的就是它压完再解出来的结果。

默认取 **300 帧**（= 车上 `--seconds 15` @ 20fps），源不够就自动截到源的实际帧数。
按车上 17:16 那一轮，两个文件的字节数应该正好是：
`car_raw.bgr` = 1,179,648,000 B、`car192.gray` = 8,755,200 B。

> **省一次 1.1 GB 复制：** ToDesk 传回来的 `video_test_raw.bin` 可以直接改名成
> `素材\car_raw.bgr`，然后 `scripts\准备素材.bat "素材\car_raw.bgr" 1280x1024`
> ——脚本发现源就是目标本身，会跳过第 1 步，只做第 2 步派生。车上导出的本来就是
> 1280×1024 紧排 BGR，字节内容和转换结果一模一样。

| 位置 | 内容 |
|---|---|
| `compression-war\素材\` | `car_raw.bgr`（彩色原片）、`car192.gray`（编码器输入）、`raw_size.txt`（原片尺寸，跑仿真.bat 读它） |
| `compression-war\cw_sim.exe` | 编译产物（`scripts\` 里也放一份） |
| `compression-war\runs\<码率>\` | 每次跑的 summary / csv / viewer（码率参数给 0 = 自动时目录是 `runs\auto\`） |

帧数按字节数反推，不写死：`car192.gray` / `192×152` 就是实际帧数，
`car_raw.bgr` / `W×H×3` 必须和它**相等**，不等就是尺寸填错了，脚本会直接报错退出。

也可以把车上录的 PNG 目录（`camera_record_test` 的产物）当源：

```bat

```

这条路省一次 `cv::Mat` 落盘，但只录画面、不跑发送链路；`video_test_raw.bin` 那条
是**一边跑真链路一边录**，更能代表车上那一瞬间的状态，优先用它。

### 2.5 2026-11-07 车上真实那轮：仿真的对账锚点

17:16 在 Jetson 上跑通的那一轮，是**第一份来自车上相机的真素材**，
它同时给出了仿真参数的实测值。以后任何仿真结论，先拿这张表对一遍。

| 车上日志 | 数值 | 仿真里对应什么 |
|---|---|---|
| `相机实际出图` | 1280×1024 | `--ref-size 1280x1024`（脚本从 `raw_size.txt` 读） |
| `原片帧数` | 300 帧 / 1,179,648,000 B | `car_raw.bgr` 的帧数必须是 300 |
| `192x152 @20fps` | 目标 20 fps | `--fps 20` |
| `输入帧数 873`、`有输出的帧 280` | 编码器只跟到 19.4 帧/秒 | **`--encode-ms 51`**（15.125 s ÷ 293 帧 = 51.6 ms） |
| `0x0310 包数 496`、`包率 32.79 包/秒` | 令牌桶 40 的 **82%** | ⚠ 见下：这轮是**彩色**编码，不能直接拿来对灰度仿真的包率 |
| `平均码率 56.30 kbps` | 目标公式算出来 59.6 | 同上，彩色口径 |
| `I 30 / P 263`、`AQ QP 28.0 / 25.9` | GOP=10、4 slice | 默认档，不用动 |

> ⚠ **这一轮编的是彩色，不是比赛配置。** 命令里带了 `--gray 0`，所以 x264 是
> `4:2:0` YUV420P 彩色，而不是 `standard3.yaml` 的 `video_gray: true`。
> **原片本身完全正确、可以继续用**（导出与这个开关无关）。
> 只是 496 包 / 32.79 包/秒 / 56.3 kbps 这三个数是彩色口径，别拿去对灰度仿真的包率。
>
> 灰度锚点想补再补，**不急、不阻塞**。而且补的时候还得先把相机从自瞄手里抢出来，
> 那是运维的事，别让它挡在「跑通仿真」前面。

所以**和实车一字不差**那一档是：

```bat
scripts\跑仿真.bat                 （默认值就是下面这一组：码率自动 / 40 / 8 / 51 / 120 帧）
scripts\跑仿真.bat 0 40 8 51 300   （跑满 300 帧，和车上那次同长度）
```

> **编码线程刚好卡在 20fps 线上。** 车上 15 s 编出 293 帧（= 19.37 fps，
> 按 20fps 应约 302 帧），而 51.6 ms/帧 × 293 帧正好吃满 15 s ——
> 说明独立编码线程**是满负荷**的，只差 3% 就跟不上节拍。再慢一点（或画面更复杂、
> I 帧更大）就会开始丢积压帧，实车上表现为**右栏卡顿**。
>
> 仿真现在也照这个跑（§5.6）：`--encode-ms 51.6 --frames 302` → **进 x264 293 帧、
> 丢 9 帧（2.98%）**，和车上那一轮的 293 帧**数字完全相同**；脚本默认的 300 帧那档丢 5 帧。
> 右栏会在这些时刻停住，和实车一样。（想自己复现这行：`--timeline-only`，见 §5.6。）

## 三、一键跑一档

```bat
compression-war\scripts\跑仿真.bat
```

**默认值就是实车那一档**：码率自动（= 车上 yaml 的 0）/ 40 包每秒 / 20 fps /
编码耗时 51 ms / 前 120 帧；跑完自动弹出左右对比播放器。
五个位置参数依次是 **码率 / 每秒包数 / 每帧最多几包 / 每帧编码耗时 ms / 最多几帧**：

```bat
scripts\跑仿真.bat 0 40 8 51          和车上那轮一字不差（码率自动 + 实测编码耗时）
scripts\跑仿真.bat 0 40 8 51 300      跑满 300 帧
scripts\跑仿真.bat 60000 40 8 0 120   指定码率 / 不算编码（只看链路）
```

第 4 个参数（编码耗时）**默认 51 ms**，就是车上 17:16 那轮量出来的。
给 **0** 时播放器会明确标注「⚠ 编码耗时未计」，右栏的延迟只算了链路：

| 来源 | 值 | 说明 |
|---|---|---|
| 车上 2026-11-07 17:16 实测 | **51 ms** | 15.125 s 编出 293 帧 = 19.4 帧/秒。同一次运行的包率/码率最能对账 |
| 档案\日志.md 旧值 | 66 ms | 早期估值，偏保守（右栏会显得更慢） |

> **脚本不再钉 `--threads 1`。** 车端是 `ctx->thread_count = 0`（x264 自己定），
> 仿真的默认也跟着是 0。代价是每次码流略有不同（±1.3%），
> **要 A/B 或对账时在命令行手动加 `--threads 1`**。

第 1 个参数给 **0** = 码率自动，走和车端 `video_sender.cpp` 同一条公式
（`40 × 0.85 × 296 × 8 ÷ 1.35 ≈ 59.6 kbps`），结果落在 `runs\auto\`。

> **为什么默认只跑 120 帧？** 播放器把每一帧左栏原片都写成 1280×1024 的 PNG，
> 300 帧 = 300 张大图 + 280 张右图，浏览器要同时扛着，容易卡。120 帧足够看压缩差异和延迟。
> 要跑全 300 帧：第 5 个参数给 300。

要试别的码率：

```bat
scripts\跑仿真.bat 74000
```

> `cw_sim.exe`、`素材\`、`runs\` 都在 `compression-war\` 下，脚本留在 `scripts\`。
> 脚本自己换算路径，也会在 `scripts\` 和 `compression-war\` 两处找 `cw_sim.exe`，
> 所以不用再把 exe 拖来拖去。要完全手动跑，见下面 §3.1。

### 3.1 手动跑（推荐，更灵活）

```bat
cd compression-war
cw_sim.exe --input 素材\car192.gray --width 192 --height 152 --pix gray ^
  --fps 20 --frames 120 --out runs\auto --bitrate 0 ^
  --send-rate 40 --max-pkts 8 --encode-ms 51 ^
  --ref 素材\car_raw.bgr --ref-pix bgr24 --ref-size 1280x1024
```

> `--max-pkts 8` 别省，它是 yaml 的值（对账口径）。
> 要做 A/B 或对账，再加 `--threads 1` 保证可重复，理由见第五节。
>
> `--ref` 只喂播放器左栏的「真原片」，**不进编码 / 不进封包 / 不影响任何指标** ——
> 不给它，左栏就退回 192×152，和右栏一样糊，对比就没意义了。
> 相机录的 PNG 序列可以直接 `--original 目录`，左栏**逐帧读原图**，连裸帧都不用拼。

**全部参数：**

| 参数 | 默认 | 说明 |
|---|---|---|
| `--input` | 必填 | 裸帧文件（gray: W×H/帧，yuv420p: W×H×1.5/帧） |

| `--pix` | gray | `gray` \| `yuv420p` |
| `--h264` | — | 已有码流，给了就跳过编码（改包策略时省时间） |

| `--out` | runs/run1 | 输出目录 |
| `--send-rate` | 40 | 令牌桶速率（协议上限 50） |
| `--max-pkts` | 8 | 一帧最多拆几个包（**对账必须用 8**，= yaml 的 `video_max_frame_packets`） |
| `--max-frame-bytes` | 296 | 每包净载荷 |
| `--drop` | 0 | 随机丢包概率（0 = 理论档） |
| `--bitrate` | 0 | 0 = 自动（等于实车 yaml 的 0）；给了就**硬覆盖** |
| `--gop` | 10 | GOP |
| `--single-packet` | — | 单包模式（每帧独立 IDR） |
| `--color` | — | 彩色（默认灰度） |

| `--threads` | 0 | 编码线程数。**0 = 自动 = 实车同款（结果不确定 ±1.3%）**；对账/复现请给 `1` |
| `--viewer <dir>` | `<out>/viewer` | 对比播放器目录 |

| `--ref-size <WxH>` | 1280x1024 | 原片分辨率 |
| `--encode-ms <ms>` | 0 | 每帧编码耗时。**>0 时按车端编码线程真跑**：编完才算处理完，跟不上相机节拍就丢旧帧。0 = 不计（只算链路），播放器会标注 |
| `--wire-ms <ms>` | 0 | 固定链路/解码开销，算进右栏延迟 |
| `--timeline-only` | — | 只算编码线程时序（丢几帧、每帧几时编完），**不读素材、不编码**。配 `--frames/--fps/--encode-ms` 用，几秒出结果，专门用来和车上日志对账 |

跑出来的包率画质全是假的。

**两个包率别混**：`包率` 是桶放出去多少（不可能超过 40）；
`需求包率` 是这些帧一共要多少包（**可以超过 100%**，超了就说明码率给高了、桶在净流出）。
对账只认后者，见第五节。

### 4.2 三个画质数字，别混着看

| 指标 | 含义 | 什么时候用它 |
|---|---|---|
| **SSIM-Y** | 客户端真实看到的画质 | 判断"实车用户会看到什么" |
| **SSIM-Y(去色调)** | 去掉整体色调偏置后的画质 | 判断"码率够不够"——**这才是压片战争该优化的数** |
| **PSNR-Y** | 逐像素误差 | 辅助；受大面积平坦区影响大 |

> **两个 SSIM 差很多 ⇒ 问题不在码率，在别的地方。** 实测过一次：差 0.50，
> 追下去发现是码流的色彩范围没写标记，客户端把亮度按 limited range 展开，暗部全被削掉。
> 这在第六节有完整说明。

### 4.3 左右对比播放器 `viewer/player.html`

双击就能看。两栏在浏览器里撑到同样宽，但**内容和出现时刻都不同**：

| | 显示什么 | 对比什么 |
|---|---|---|
| 左 · 相机原片 | 1280×1024 **彩色 BGR**，相机直出、没经过任何处理 | 左边的清楚是**真清楚** |
| 右 · 处理完、客户端收到 | 192×152 **灰度**解码结果 | 右边那层糊是**真糊**，不是播放器压小的 |

**右侧不是按 20 fps 傻放，是按"这一帧处理完、最后一个包到齐的时刻"切换。**
严格说是 `max(整帧到齐, 编码器编完这一帧)`：真实客户端收到第一包就开始解，
但编码器是**编完才吐第一包**的，所以"编完"这一条必须参与。
所以同一帧左栏先出现、右栏要等它处理完才出现，两者的时间差就是播放器上实时显示的
**「延迟 ms」**；掉帧则表现为**画面冻住、落后帧数往上跳**——和实车肉眼看到的一模一样。

首帧延迟会比后面大：开头相机立刻放行、编码器还在编第一帧，这时左栏已经出图、右栏还没有，
默认档实测首帧 **125 ms**（后面稳定在 74 ms 左右），页面上 `延迟` 会如实显示，不是 bug。

延迟由 `--encode-ms`（编码线程真的占用这段时间） + 链路（拆包/令牌桶/到齐） + `--wire-ms`（固定开销）组成。
编码**不是**加在链路后面的一个常数：编完才有包，所以 `ready_ms` 里天然含着它，summary 里的
「帧完成延迟」就是这个口径。**`--encode-ms` 给 0 时页面会标「未计编码」**，别把只算链路的数当成真实延迟。

编码线程跟不上时（`--encode-ms × fps > 1`），图例底下会多一句
「⚠ 编码线程跟不上相机节拍，有 N 帧还没被取走就被下一帧覆盖」，右栏在那些时刻会停在上一张——
**这就是实车上看到的卡顿**。

> 左栏原片来源二选一：`--ref 素材\car_raw.bgr --ref-pix bgr24`（裸帧），
> 或 `--original <PNG 目录>`（逐帧读原图，最忠实）。`跑仿真.bat` 发现
> `素材\car_raw.bgr` 就自动带上前者。都没有时左栏退回 192×152（和右栏一样糊，只能看丢帧）。
>
> 代价：左栏是 1280×1024 PNG，**每帧约 1.4 MB、120 帧就 160 MB**（右栏一共才 4 MB）。
> 磁盘吃紧时可以 `--no-viewer` 跑，或者只跑 `--frames 30` 看个开头。

按钮：播放/暂停、慢/快（0.1×~8×）、实时 1×、跳到下一个丢帧、拖动时间轴。

### 4.4 逐帧账本 `per_frame.csv`

```csv
frame_index,frame_bytes,packets,released,decoded,psnr_y,ssim_y,completion_ms,why
```

**`frame_index` 是相机帧号**，不是编码器帧号——所以表里的行数 = 相机放行的帧数
（`--encode-ms 51 --frames 300` 就是 300 行，其中 5 行是 `encode-drop`）。

最后一列 `why` 是**这一帧丢在哪一环**：

| 值 | 含义 |
|---|---|
| （空） | 正常解出来了 |
| `encode-drop` | **相机拍到了、但编码线程还没取走就被下一帧覆盖**。这一帧从没进过 x264，发不出任何包 |
| `oversize` | 超过「单帧字节上限」（`max_pkts × 296`），整帧丢弃 |
| `backlog` | 进了令牌桶但积压超限，被丢最老的帧 |
| `inflight` | 进网了但客户端没解出来（缺包 / 等 I 帧） |

任何一次"掉帧"都能在这张表里找到是哪一环丢的，不用猜。

## 五、和实车对不对得上（对账记录）

这个平台的价值全在"它和实车是同一件事"，所以每次改核心逻辑都要重新对账。

**基准**：`autoaim/档案/包率85%+灰度版-部署与回退-2026-10-28.md` 第三节，
300 帧真实赛场画面（官方图传 1080p HEVC，转 20 fps 喂 x264）。
**注意它用的是一条不同的素材**，见下面 5.2。

### 5.1 对账的唯一正确口径：**需求包率**

档案里的 `35.5 包/秒 / 88.8% 桶` 和 `41.1 包/秒 / 102.8% 桶`，
数的是 **"这些帧一共需要多少包"**，不是"令牌桶放出了多少包"：

```
需求包率 = Σ ceil(帧字节 / 296) / (帧数 / fps)
```

这个口径**可以超过 100%**，因为它是需求；放行包率则**永远不能**超过 `send_rate_hz`。
档案里那个 `102.8%` 不是笔误，正是"这条码率已经超编了、桶在净流出"的证据——
如果把它误当成放行包率，就会以为令牌桶能发得比令牌还多。

本仿真把两个数都打出来：稳态放行包率（`包率`）和需求包率（`需求包率`）。
**对账只认后者。**

### 5.2 对账结果（`--max-pkts 8`，yaml 的值；`--threads 1`，确定性）

| 档位 | 档案需求包率 | 本仿真 | 差 |
|---|---|---|---|
| 60 kbps | 35.5（88.8%） | **35.00（87.5%）** | −1.4% |
| 74 kbps | 41.1（**102.8%**） | **40.80（102.0%）** | −0.7% |

**两行都在 1.5% 以内，而且 74 kbps 那行同样越过 100%** —— 这是关键判据，
说明复刻的口径对了，不是凑数。

### 5.3 剩下的 1% 是什么（三个来源，都不是链路错）

| 来源 | 量级 | 怎么处理 |
|---|---|---|
| **x264 多线程非确定性** | **±1.3%**（60k 档连测 12 次：350~359 包） | 对账时 `--threads 1`，实测 5 次 md5 完全一致 |
| 素材不同 | 帧大小分布不同 → `ceil` 取整浪费不同 | 想彻底闭环得拿档案那批原始帧重跑 |
| SSIM 绝对值 | 档案那次素材 83% 纯黑，指标虚高 | **绝不能用 SSIM 绝对值当闸门** |

关于第一条，实车 `VideoSender` 写的是 `ctx->thread_count = 0`（交给 x264 自动），
**所以实车的编码结果本身就是每次启动都不一样的**。仿真的默认值也保持 0，
和实车一字不差；`跑仿真.bat` 也不再钉 `--threads 1`。只有明确要复现实验时才在命令行加上它。

> 顺带一个教训：这个 ±1.3% 的抖动在早期对账里制造过两次"精确命中"
> （35.3 vs 35.5、41.17 vs 41.1），当时误以为是链路复刻准确，
> 其实只是抽样撞上了。**先量化噪声，再谈对账。**

### 5.4 ⚠ 别把分母写成墙上时间

令牌桶物理上不可能超过 `send_rate_hz`。如果把分母写成
"从第一个包到最后一个包的墙上时间"，帧数少的时候会得到比 40 还大的包率。
现在的分母固定是 `帧数 / fps`，物理上封顶，不会骗人。

### 5.5 封包与令牌桶的逐项核对

| 检查项 | 结果 |
|---|---|
| `包数 == ceil(帧字节/296)` | 逐帧复算 400 帧，**0 帧不符** |
| 放行包率 ≤ 物理上限 | 两档都不超 `40 包/秒`（35.00 / 40.00） |
| 丢包 / 积压 | 两档都是 **0**，与档案"0 丢包 0 丢帧"一致 |
| VBV | `--max-pkts 8` 时 VBV=18944 bit，与档案一字不差 |
| **`--max-pkts 6` 会偏小** | 6×296=1776 B/帧，包数整体约 −2%，**这是用错参数，不是平台错** |

### 5.6 ★ 编码线程跟不上就丢旧帧（第六环，2026-11-07 补）

车端 `video_sender.cpp` 的编码线程只有一个槽：

```cpp
std::optional<cv::Mat> pending_frame;   // 待编码帧（只保留最新一帧，慢于 fps 时自动丢旧帧）
```

`feed()` 按**累加**节拍放行：`last_send += interval; if (last_send + interval < now) last_send = now + interval;`
每放行一帧就 `pending_frame = 这一帧`，然后叫醒 `worker_loop()`。worker 取走 → `reset()` → 编 `encode_ms`。
**这期间相机又放行了新帧，就直接覆盖掉还没被取走的那帧——它从来没进过 x264。**

为什么仿真必须照这个做（而不是"全编完再丢包"）：P 帧会引用前一帧。如果编码器编了一帧车端
根本没编的帧，后面所有 P 帧的参考帧链全错，客户端解出来的东西和实车上完全是两回事。
所以**丢失帧必须在送进编码器之前就拿掉**，仿真为此先算时序、生成一份过滤后的编码输入。

丢帧数的公式（`--encode-ms × fps > 1` 时才有）：

```
丢帧率 ≈ (encode_ms − 1000/fps) / (1000/fps)
```

实测对账（`--fps 20`）：

| 输入 | 车端实测 | 仿真 | 一致 |
|---|---|---|---|
| 302 帧 × 51.6 ms | 15.125 s 编出 **293** 帧 | 进 x264 **293** 帧、丢 9（2.98%） | ✅ 帧数完全相同 |
| 300 帧 × 51 ms | — | 进 x264 **295** 帧、丢 5（1.67%） | 理论值 2%，0.33% 差在首末帧边界 |
| 300 帧 × 0 ms | — | 300 / 300，丢 0 | 理论档，老基线不受影响 |

想只对这条线、不跑 1 GB 素材（几秒出结果）：

```bat
cw_sim.exe --timeline-only --frames 302 --fps 20 --encode-ms 51.6
```

输出三行：`相机放行 302 帧，进 x264 293 帧，丢 9 帧（2.98%）` / 编码滞后分位数 / 编码线程实际出帧率。
**车上日志换一行，这里换一个数，就能立刻判断仿真参数是不是车上的那套。**

> 实现是**事件驱动**（下一个事件 = min(相机放行, 编完)），不是按毫秒步进：
> 步进会把每次编完凑到整毫秒，等于悄悄把 `encode_ms` 抬到 52 ms 左右，
> 302 帧就会错成 291。这个坑踩过一次，别改回步进。

## 六、已知边界与坑

### 6.1 ★ 色彩范围约定错配（这条会误导所有画质结论）

**现象**：右侧画面整体发黑，暗部细节全丢。用真实赛场夜景素材时 SSIM 只有 0.34。

**根因链**（三段都查证过）：

1. `VideoSender` 用 `sws_getContext(BGR24 → GRAY8)` 转换，**输出是 0..255 满量程**。
2. x264 编码时**不写 range 标记**（`ffprobe` 报 `color_range=unknown`）。
3. 客户端解码器 `ensure_sws_context` 用 `sws_getContext(GRAY8 → RGBA)`，
   **没有传颜色属性**，sws 只能按默认的 limited range 展开：`1.164 × (x − 16)`。
   于是所有 `< 16` 的像素被削成纯黑，整体压暗。

**实测拟合曲线**：`dec = 0.993 × src − 7.6`，与 `1.164×(x−16)` 的削底特征完全一致。

**代价**：

| 配置 | PSNR-Y | SSIM-Y | 需求包率 |
|---|---|---|---|
| 现状（无标记） | 28.64 dB | 0.3419 | 35.00（87.5%） |
| 加 `-color_range pc` | **38.11 dB** | **0.9563** | 35.10（87.8%） |

**几乎零成本**：+0.1 包/秒（+0.3%），换来 SSIM +0.61。

**但这是"实际上车"阶段的事**，本阶段只把它当测量基线，
`--full-range` 默认关，仿真的默认行为必须和实车一字不差。

#### 6.1.1 ★ 反过来也会坏：ffmpeg 版本会让仿真"比实车好看"（2026-11-07 踩到）

2026-11-07 CH 在 Windows 上第一次跑通，**觉得右栏画质高得离谱，怀疑是不是真 300 字节**。
查下来的确是仿真偏了，而且偏的正是这一节的方向——**偏反了**：

- 同一份素材、同一个 `cw_sim.exe`、同一条 x264 参数，
  **沙盒的 ffmpeg 4.4.2** 编出来 `ffprobe` 报 `color_range=unknown`（= 车端口径），
  **CH 机器的 ffmpeg 7.1.1** 编出来报 **`color_range=pc`**。
- 灰度（单平面）输入没有 chroma，本来就是"范围未指定"。新版 ffmpeg/libx264
  把这个 unspecified 直接按**全量程**写进 SPS 的 VUI。客户端解码器看到 pc 就不再
  按 `1.164×(x−16)` 展开，暗部不再被削 —— 于是**右栏比实车漂亮一大截**：

| 口径 | PSNR-Y | SSIM-Y | 色调拟合 `dec = a·src + b` |
|---|---|---|---|
| 车上（无标记 → limited 展开） | ~29 | ~0.92 | **1.116 / −15.5** |
| CH 机器上那版（被标成 pc） | **38.78** | **0.9488** | 0.979 / +1.5 |

**修法**：灰度编码时显式给 ffmpeg 加 `-color_range tv`（放在 `-i` 之前）。
x264 拿到明确的 tv 契约，就不会再自作主张写 pc。

**★ 2026-11-07 19:48 已在 CH 的机器上验证通过**：重编后用默认档（`跑仿真.bat`）跑，
`summary.txt` 的色调拟合是 `dec = 1.11576 * src + -15.4514`，PSNR-Y 29.5455、SSIM-Y 0.919314——
**和沙盒 4.4.2 的基线一致，说明 7.1.1 认这个参数**，仿真不再偏乐观。
（这一版还顺手修了 MSVC 才能发现的 `<algorithm>` 缺头，见 §八。）

> ★ **以后每次换 ffmpeg 或换电脑，第一件事就是看这一行**，不要看 PSNR：
> `dec = 1.116 * src + -15.5` = 和车端一致（对）；
> `dec ≈ 0.98 * src + 1.5` = 被标成 pc 了（仿真偏乐观，所有画质结论都不可信）。
>
> 这条也解释了"是不是真 300 字节"这个疑问的一半：字节数是真的
> （包是 `300 B` 定长、`2 B 长度 + 2 B 序号 + ≤296 B`，
> 那次 118 帧共 42,468 B 的 H.264，上线 203 包 ≈ 61 KB，对 3.4 MB 编码输入是 81 倍压缩），
> 但**右栏看起来的清不清楚，取决于解码器怎么解释亮度范围**。
> 车上那段 `×1.16 − 16` 的削底就是实打实画在客户端画面上的损失。

> 复现上面 6.1 表格那两行的命令（`--threads 1` 保证可重复）：
>
> ```bat
> REM --full-range：码流里写 full range 标记
> cw_sim.exe --input 素材\car192.gray --width 192 --height 152 --pix gray ^
>   --fps 20 --frames 200 --out runs\range-on --bitrate 60000 ^
>   --send-rate 40 --max-pkts 8 --threads 1 --full-range
>
> REM 现状：什么都不写，和实车一字不差
> cw_sim.exe --input 素材\car192.gray --width 192 --height 152 --pix gray ^
>   --fps 20 --frames 200 --out runs\range-off --bitrate 60000 ^
>   --send-rate 40 --max-pkts 8 --threads 1
> ```

**为什么之前没发现**：一直用纯黑背景的电竞录像做素材，黑对黑看不出来。

### 6.2 素材决定了结论，不是平台决定的

同一套参数，亮素材 SSIM 0.86、暗素材 0.34。**换素材前先把旧的绝对值作废**，
只比"同一素材下不同参数"的相对高低。

### 6.3 帧率轴验不了

素材是 30 fps，实车相机约 100 Hz。**"提高采样率"这条优化线在本平台里无法验证**，
必须实测。本平台专治"同一个码率预算下怎么压得更清楚"。

### 6.4 编码走子进程，且结果不确定

每次跑都要 fork 一次 `ffmpeg.exe`，200 帧大约 3~8 秒。
改包策略时用 `--h264` 复用已编好的码流，能省掉这段时间。

**更要注意的是非确定性**：默认不钉线程（= 实车 `thread_count = 0`），
x264 的帧级并行 + VBV 会让你每次跑出略微不同的码流——
实测 60 kbps 连测 12 次，包数在 **350~359** 之间飘，md5 每次不同。
**要做 A/B 对比或对账，一律加 `--threads 1`**，此时 5 次结果 md5 完全一致。

### 9.1 最快跑通路径（用仓库自带画面）

### 9.2 没有 ffmpeg.exe 怎么办

`ffmpeg.exe` 不在仓库里（约 80 MB，超 GitHub 习惯）。
Windows 版取一个：<https://www.gyan.dev/ffmpeg/builds/> 选 `ffmpeg-release-essentials.zip`，
解压后把 `bin\ffmpeg.exe` 放到 `compression-war\` 或 `compression-war\scripts\` 都行。
**必须是带 x264 编码器的版本**（essentials 版有）。

> 本机已经放好了：`compression-war\ffmpeg.exe` = **7.1.1-essentials**（静态单文件，
> 带 libx264/libx264rgb，sha256 `b9022598…522997`）。换电脑或重新 clone 才需要重做这一步。

4. **更高效的编码器**——x265 / 其他，改一行参数就能试（这是选用外部进程的好处）。
