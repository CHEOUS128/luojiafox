# 压片战争：实时仿真与策略对比

**先用这个入口跑实时画面。** 视频按原速度输入，实际经过缩小、H.264编码、封包、限速、接收解码和窗口显示，处理耗时由这台Windows电脑实际测量。

2026-11-09双包基线已完成验收并经CH确认，作为后续压缩与还原方案比较的里程碑。

**策略探索现已接入。** [策略使用说明](docs/策略试验使用说明.md)给出队员可直接运行的入口；[本轮对比与验收](docs/验收/策略探索-2026-11-09.md)区分收益、失败轮次和未上车验证项。39份可复现配置覆盖编码、灰度/粗颜色、分辨率、帧率、降噪和接收后处理，不限制后续增加方案。原始基线保留为`profiles/baseline.ini`。

**本轮上车档选 B**。彩色、完整视野、`320×256`、目标 20 fps，H.264 每 20 帧安排一次关键帧。仿真用 `profiles/one-320-gop20.ini`，双击 `scripts/启动-B方案.bat` 直接跑。四轮一分钟测试中，稳态最低 19 fps，典型延迟约 0.1 秒。故意漏一包的那次约 0.86 秒恢复。Jetson 用 `quality` 档，现场按[仓库首页](../README.md)的顺序测。

已有本机结果时双击`scripts/启动-策略对比.bat`；队员首次生成对比：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File '.\scripts\运行-策略对比.ps1' -InputPath 'D:\视频\比赛录像.mp4'
```

需先完成下方编译与FFmpeg准备；对比导出另需Python、numpy、Pillow。各档真实运行后再离线导出，播放器提供保留真实延迟/冻结的操作体验，以及缺帧留空的同源帧画质对照。具体试车文件与回退见[车端试验交付](docs/车端策略试验交付.md)。


| 当前基线 | 约束 |
|---|---|
| 图像 | 彩色、完整视野、等比缩小补边，192×152 |
| 帧率 | 默认20 fps，目标最高25 fps |
| 每包 | 300 B数据段 = 4 B内层头 + 最多296 B H.264 + 补零；外层含CRC共309 B |
| 每帧 | **包括关键帧在内，最多2包、592 B净码流**；超限整帧丢弃并恢复关键帧 |
| 通道 | 50包/秒，每包实际间隔至少20 ms，迟到不突发补发 |
| 编码 | H.264、GOP10、约74.5 kbps、VBV4736 bit，去除SEI说明 |
| 模拟边界 | C板旁路、理想通道；不含未测量的VT03→VT13额外延迟与丢包 |

60秒实际窗口验收：57个稳态完整秒最低19 fps，延迟中位94.7 ms；1200帧独立收包重放像素一致。**本机结果不等于Jetson或实车图传性能。**

## 第一次用：从源码到画面

需要完整克隆`luojiafox`，保留同级`luojiamaster`提供的第三方解码库与头文件。实时窗口只支持Windows；旧离线模式仍可在Windows/Linux编译。仓库不提交生成的exe和大视频素材。

准备：

1. Visual Studio 2022的“使用C++的桌面开发”，含Windows SDK、CMake和Ninja。
2. 带`libx264`编码器的`ffmpeg.exe`，放在本目录根部。基线使用7.1.1-essentials，可从队内获取已验证版本。SHA256：`b90225987bdd042cca09a1efb5e34e9848f2d1dbf5fbcd388753a44145522997`。
3. 已有普通视频；没有视频时运行下面的演示生成脚本即可，**不需要接车或获取工业相机原片**。

在仓库根目录打开PowerShell，执行：

```powershell
Set-Location -LiteralPath '.\compression-war'
powershell -NoProfile -ExecutionPolicy Bypass -File '.\scripts\编译-实时仿真.ps1'
if ($LASTEXITCODE) { throw '编译失败，请查看上方原始错误' }
powershell -NoProfile -ExecutionPolicy Bypass -File '.\scripts\生成演示视频.ps1'
if ($LASTEXITCODE) { throw '演示视频准备失败' }
& '.\scripts\启动-实时仿真.bat' '.\素材\演示-四角运动.mp4'
```

打开窗口后点“开始”。编译脚本会在缺失时建立`C:\rm26cw → 当前仓库根`的junction，并在编译前核对指向；已有链接指向别处时直接报错，不覆盖。构建源为`C:\rm26cw\compression-war`。

有自己的视频时直接运行：

```powershell
& '.\scripts\启动-实时仿真.bat' 'D:\视频\比赛录像.mp4'
```

已有相机原片时也可不带参数启动：优先打开`素材\car_raw.bgr`（1280×1024 BGR24、20 fps）；缺失则弹出文件选择窗口。参数只在停止时调整，支持停止、重新播放、循环和右栏原生1:1查看。

## 看什么，怎么判断跑对

- 左栏是原片，右栏只显示真正收到的包所解出的图像；不裁剪或拉伸视野。
- 窗口显示当前帧净码流字节、包数/2、实际包率、解码fps、显示fps、延迟和画面年龄。冻结时年龄继续增加。
- 日志每秒一行`live_probe`；每次运行自动写到新的`runs/live/<时间戳>/`。显示fps统计新画面提交次数，不统计重复重绘。
- 正常档验收：去掉前2秒启动和输入结束后的收尾，每个完整1秒至少提交15张新图。未达标记FAIL，不自动放宽包数或降低分辨率。
- 修改脚本/源码前看[档案索引](档案/README.md)；更换电脑或FFmpeg时另看[离线指南6.1/6.1.1](docs/离线对账指南.md)，不要把色彩范围差异误判为压缩收益。

## 不需要原片的独立真实性复核

仓库保留[原始双包基线证据](evidence/README.md)（约2.3 MB）和[策略探索精选证据](evidence/strategy-milestone/README.md)。重复试跑、原片和逐帧大图不上传。先复核原始基线（按原到包时间重放，约60秒）：

```powershell
.\cw_wire_verify.exe '.\evidence\two-packet-baseline'
```

要求退出码0，输出`pixel_sha256_match=1`。它校验实际309 B外层帧、CRC、2包/592 B上限、20 ms间隔、滚动1秒不超过50包，并使用未修改的客户端解码器重放收到的300 B数据。

更严格地隔离发送端，仅使用收到的包、到包时间和预期像素摘要：

```powershell
.\cw_wire_verify.exe --rx-only '.\evidence\two-packet-baseline'
```

该入口不读取原片、TX记录、summary或仿真观测编号；摘要只用于解码后比较，不帮助恢复图像。H.264的P帧使用此前收到的参考图像，PNG导出大小不代表无线传输字节数。
