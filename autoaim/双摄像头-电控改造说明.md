> 目标：让**自瞄上位机的工业相机画面**显示到**自定义客户端**的第二视角（客户端按 H 键切换）
>
> 参与方：视觉（上位机/自瞄）、电控（主控固件）、软件（自定义客户端）
> 版本：v2（2026-10-20 更新）
> v2 变更：补充内层封装说明、修正带宽/帧率参数、补充验收抓包方法、明确"必须原样透传"。

## 〇、一句话分工

- **视觉（已基本完成）**：工业相机取图 → 300×240（全视野）→ H.264 编码 → 拆成 **309 字节的 0x0310 帧**，从 USB CDC 串口（`/dev/ttyACM0`）发出来。
- **电控（本文件）**：在 STM32 上**按帧头分流**（0xFF 控制帧 / 0xA5 视频帧），把完整的 309 字节视频帧**原样转发**到 VT03 串口。
- **自定义客户端**：已经支持 CustomByteBlock 视频，**不需要改**。客户端按 H 键切换主画面/第二视角。

## 二、协议：0x0310 帧（309 字节）

来自《RoboMaster 2026 高校系列赛通信协议 V2.0.0》，图传链路自定义数据通道。

### 2.1 外层格式

```
偏移  字段              说明
[0]   0xA5              帧头
[1:3] 0x2C 0x01         数据段长度 = 300（小端）
[3]   seq               外层包序号，0~255 循环
[4]   CRC8              前 4 字节的 CRC8（多项式 0x8C，初值 0xFF）
[5:7] 0x10 0x03         cmd_id = 0x0310（小端）
[7:307] data            300 字节：视频数据（双层结构，见 2.2）
[307:309] CRC16         前 307 字节的 CRC16（多项式 0x1189，初值 0xFFFF，小端）
```

**整帧固定 309 字节，data 段固定 300 字节（尾部不足补 0）。**

### 2.2 data 段的双层结构（客户端就按这个解包）

```
data (300B) =
  [2B 内层包长度 大端][内层包1]
  [2B 内层包长度 大端][内层包2]
  ...（剩余字节补 0；长度为 0 表示后面全是填充）

每个内层包 =
  [2B 序号 大端][H.264 数据片段，最大 296 字节]
```

我们目前的实现是**每个 0x0310 帧只装 1 个内层包**（H.264 片段 ≤296，其余补 0）。

> ⚠️ **电控只需要原样透传，不需要理解内层结构。** 千万不要对 data 段做任何"整理"。

### 2.3 与控制帧的区别

| 帧类型 | 帧头 | 长度 | 方向 |
|---|---|---|---|
| 云台控制帧（现有三阶指令） | `0xFF` | 32 字节 | 上位机 → 主控 |
| 视频帧（新增） | `0xA5` | **309 字节** | 上位机 → 主控 → VT03 |

## 三、电控需要改的三处

### 3.1 USB CDC 接收：从"固定 40 字节"改成"按帧头分流"

**现状**（`gimbal_project/Src/usbd_cdc_if.c` / `Self_aim.c`）：

```c
memcpy(Usart_Receive, Buf, 40);        // 写死 40 字节
process_usb_data_packet(Usart_Receive, 40);
```

**问题**：如果现在打开视频，309 字节的视频帧会被当成控制帧解析，导致**帧头错乱、控制失效**。
（所以视觉侧在电控改完之前一直保持 `video_send_enable: false`。）

**要求**：

1. 用 `CDC_Receive_FS` 里真实的 `*Len`，不要写死 40。
2. USB CDC 是**流式**的：一次回调可能收到半帧，也可能一次收到 2 帧。必须做**环形缓冲 + 状态机**，不能假设"一次回调=一帧"。
3. 状态机按帧头分流：

```c
typedef enum { WAIT_HEAD, IN_CONTROL, IN_VIDEO } cdc_state_t;

// 控制帧：0xFF 开头，32 字节
// 视频帧：0xA5 开头，之后 2 字节长度（应为 0x2C 0x01），再 1B seq + 1B CRC8 + 2B cmd，
//         再 300B data + 2B CRC16，共 309 字节
void cdc_stream_feed(const uint8_t *data, uint16_t len)
{
    for (uint16_t i = 0; i < len; ++i) {
        uint8_t b = data[i];
        switch (state) {
        case WAIT_HEAD:
            if (b == 0xFF) { state = IN_CONTROL; ctrl_idx = 0; ctrl_buf[ctrl_idx++] = b; }
            else if (b == 0xA5) { state = IN_VIDEO;  vid_idx = 0;  vid_buf[vid_idx++]  = b; }
            // 其它字节：丢弃（避免误同步）
            break;

        case IN_CONTROL:
            ctrl_buf[ctrl_idx++] = b;
            if (ctrl_idx >= 32) { process_usb_data_packet(ctrl_buf, 32); state = WAIT_HEAD; }
            break;

        case IN_VIDEO:
            vid_buf[vid_idx++] = b;
            if (vid_idx >= 309) {
                // 可选：校验 0xA5 / 长度 / CRC8 / CRC16，通过才转发
                forward_video_to_vt03(vid_buf, 309);
                state = WAIT_HEAD;
            }
            break;

        default:
            state = WAIT_HEAD;
        }
    }
}
```

4. **缓冲区建议放在 USB 回调外**（全局/静态），不要在 `CDC_Receive_FS` 里做长时间处理；转发到 VT03 可以放进主循环，用一个简单队列（例如 8 个 309B 槽位）解耦，避免 USB 回调里阻塞。
5. 注意：视频帧的 data 段里**可能出现任何字节**（包括 0xFF、0xA5），所以状态机一旦进入 `IN_VIDEO` 就必须按 309 字节计数走完，不能中途重新找帧头。

### 3.2 新增：把完整的 309 字节视频帧原样转发给 VT03

```c
void forward_video_to_vt03(uint8_t *frame, uint16_t len)   // len == 309
{
    // 原样透传：不要改任何字节（包括 seq、CRC、内层结构）
    // 不要重算 CRC，不要改长度字段
    HAL_UART_Transmit(&huart_vt03, frame, len, 20);  // 10~20ms 超时足够发 309B@921600
}
```

**注意**：

- VT03 串口波特率应为 **921600**（与遥控 SBUS 常见配置相同，见 3.3）。
- 视觉侧按 **40Hz 节拍**发包，每包载荷最多 296B → **上限约 94.7 kbps**；当前配置约 90 kbps，即**平均每秒约 40 个包**。
- 主控只需保证**丢包可接受、错包不可接受**：CRC 校验失败的视频帧直接丢，不要转发。
- 建议加一个计数器（转发成功/CRC 失败/超时），联调时看得到状态。

### 3.3 确认 VT03 接在哪个串口（**最关键，需要看实物接线**）

**当前主控串口占用**（`gimbal_project/Src/usart.c` / `remote_control.c`）：

| 串口 | 波特率 | 引脚 | 当前用途 |
|---|---|---|---|
| USART1 | 9600 | PB7(RX) / PA9(TX) | 裁判系统 |
| USART3 | 100000 | PC11(RX) / PC10(TX) | 遥控 DBUS |
| **USART6** | **921600** | PG14(TX) / PG9(RX) | 遥控 SBUS ⚠️ |

**问题**：`921600` 正好是 VT03 的标准波特率，但代码里 USART6 被遥控占用。请电控确认属于哪种情况：

| 情况 | 需要做什么 |
|---|---|
| A. VT03 接在 USART6，遥控已不用 SBUS | 删掉 `remote_control.c` 里 USART6 的中断/DMA，腾给视频 |
| B. VT03 接在别的串口 | 新增串口初始化与引脚配置（注意 DMA + 中断优先级） |
| C. VT03 由裁判系统主控模块转发 | 链路不同，需另外确认 0x0310 该怎么送进裁判系统 |

**需要电控回答：VT03 图传发送端的 UART 线，物理上接在 STM32 的哪个引脚？**

| 参数 | 当前值 | 说明 |

| 分辨率 | 300 × 240 | 5:4，与工业相机 1280×1024 同比例，全视野无黑边 |

## 七、参考：CRC 算法

```c
// CRC8：多项式 0x8C，初值 0xFF（校验前 4 字节）
uint8_t get_crc8(const uint8_t *data, size_t len) {
    uint8_t crc = 0xFF;
    while (len--) crc = CRC8_TAB[crc ^ (*data++)];
    return crc;
}

// CRC16：多项式 0x1189，初值 0xFFFF（校验前 307 字节，结果小端写入 [307:309]）
uint16_t get_crc16(const uint8_t *data, size_t len) {
    uint16_t crc = 0xFFFF;
    while (len--) crc = (crc >> 8) ^ CRC16_TAB[(crc ^ (*data++)) & 0xFF];
    return crc;
}
```

完整查表见：
- 我方：`autoaim/my_lf_INF_20261025/tools/crc.cpp`
- ACE 参考实现：`ACE_RM26_VideoEncoder/src/image_serial/src/serial_transmitter_node.cpp`

## 附：为什么现在不能直接打开视频

视觉侧已把 `video_send_enable` 默认设为 `false`。原因：主控现在的 USB 接收写死 40 字节，打开后 309 字节视频帧会被当作控制帧解析，**云台控制会乱**。

**顺序必须是：电控先改好分流与转发 → 双方联调 → 再打开 `video_send_enable: true`。**
