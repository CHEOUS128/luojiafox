# 「一帧一个包」改版：Jetson 部署与验证（2026-10-23）

> 目标：**先把画面显出来**。
> 之前 300×240 / 90kbps，一帧要切成 2~4 个包，而链路通过率只有 0.16%~0.64%，
> 一个完整帧几乎永远拼不起来。现在改成 **160×160 / 5fps / 一帧 = 一个包**，
> 任何一个包单独到达，客户端都能解出一张完整的图（最坏情况就是"幻灯片"）。
>
> 本次只改**上位机（Jetson）**：5 个文件。STM32 固件、客户端**都不动**。

---

## 一、改了什么（对应 5 个文件）

| 文件 | 改动 |
|---|---|
| `io/video_sender/video_sender.hpp` | `VideoSenderConfig` 新增两项：`single_packet`、`max_frame_bytes` |
| `io/video_sender/video_sender.cpp` | 单包模式：每帧独立编码（全 I 帧）、整帧硬限制 ≤296B、超限整帧丢弃（**绝不拆包**）、每 5 秒打一次统计日志 |
| `src/standard_mpc.cpp` | 从 yaml 读 `video_single_packet` / `video_max_frame_bytes` |
| `configs/standard3.yaml` | 视频段改成 160×160 / 中心裁 320 / 5fps / 10kbps / 单包模式 |
| `tests/video_sender_test.cpp` | 测试程序也读这两个新配置项 |

**协议层面没有任何变化**：还是 309 字节 0x0310 帧、300 字节 data、`[2B 长度][2B 序号][H.264]`。
只是每一帧的 H.264 从"一大块、要几个包"变成"一小块、正好一个包"。

### 为什么这样就能出画面

- 原来：一帧 = 2~4 个连续包。丢包率 99% 时，四个包都到的概率 ≈ 0.01⁴ ≈ 0，永远没有完整帧。
- 现在：一帧 = 1 个包，而且每帧都是自带 SPS/PPS 的 IDR（全 I 帧），**不需要前一个包**。
  包到了就出一张图，包丢了就是少一帧。
- 画质和帧率都做了大幅让步（160×160、5fps、约 10kbps），目的只有一个：**先看到画面**。

## 二、离线验证结果（已经在电脑上确认过参数）

用和你 Windows 上同样版本的 libx264、同样的参数，跑 50 帧合成比赛画面：

```
每帧 H.264 字节：中位数 208B，p95 233B，最大 824B（只有第 0 帧，SPS+PPS+IDR 初始化帧）
超 296B 的帧：1 个（就是第 0 帧，按设计整帧丢弃）
第 2/10/25/40 个包分别用全新解码器单独解：4/4 都出完整 160×160 图像
用 rm0310.py 的 CRC 表校验 49 个 0x0310 帧：CRC8/CRC16 全对，序号连续，尾部补 0 正确
```

> 第 0 帧丢掉没关系：它是编码器刚启动时的初始化帧（带 SPS/PPS 的那一帧最大）。
> 后面每一帧都是独立 IDR，丢第 0 帧不影响第 1 帧以后任何一帧。

## 三、部署（ToDesk，照抄）

### 3.1 传文件

把 Windows 上这 5 个文件（**保持目录结构**，ToDesk 选"覆盖"）：

```
autoaim/my_lf_INF_20261025/io/video_sender/video_sender.hpp
autoaim/my_lf_INF_20261025/io/video_sender/video_sender.cpp
autoaim/my_lf_INF_20261025/src/standard_mpc.cpp
autoaim/my_lf_INF_20261025/configs/standard3.yaml
autoaim/my_lf_INF_20261025/tests/video_sender_test.cpp
```

目标目录：Jetson 上的 `~/my_lf_INF_20261025/`（对应上面相对路径）。

### 3.2 备份 + 校验覆盖成功（Jetson 终端，一次粘贴）

```bash
cd ~/my_lf_INF_20261025
STAMP=$(date +%Y%m%d-%H%M%S)
mkdir -p ~/backup-$STAMP
cp -v io/video_sender/video_sender.hpp io/video_sender/video_sender.cpp \
      src/standard_mpc.cpp configs/standard3.yaml tests/video_sender_test.cpp \
      ~/backup-$STAMP/
echo "备份在 ~/backup-$STAMP"

echo "--- 校验（每一项都要 ≥1 / OK）---"
grep -c "single_packet"        io/video_sender/video_sender.hpp
grep -c "1包/帧 统计"           io/video_sender/video_sender.cpp
grep -c "video_single_packet"  src/standard_mpc.cpp
grep -c "video_single_packet"  tests/video_sender_test.cpp
grep -n "^video_\|three_order_enable" configs/standard3.yaml
```

**判读**：前四个数字都 ≥1；yaml 里 `video_single_packet: true`、`three_order_enable: true`、
`video_send_enable: true` 三项都在。缺哪项就是那个文件没传上去。

### 3.3 编译（只编这两个目标，别全量）

```bash
cd ~/my_lf_INF_20261025
cmake --build build --target standard_mpc video_sender_test -j$(nproc)
```

期望最后一行类似 `[100%] Built target standard_mpc`，没有 `error:`。

> 编译前先确认没有生成器缓存不匹配的问题：如果报 `CMakeLists.txt` 相关错误，
> 跑一次 `cmake -B build` 再重编（不会动别的配置）。
>
> 全量 `make` 会编 `tests/fire_test.cpp` 失败，这是原有问题，**不要全量编**。

### 3.4 重启服务 + 看日志

```bash
sudo systemctl restart autoaim-20261025
sleep 25
systemctl is-active autoaim-20261025
grep "VideoSender" ~/my_lf_INF_20261025/logs/autostart.log | tail -n 20
```

**期望看到**（关键三行）：

```
[VideoSender] 已启用（160x160 @5fps 10kbps preset=slow keep_aspect=false sharpen=0 单包=是）
[VideoSender] 单包模式：每帧独立编码（全 I 帧），整帧必须 ≤ 296 字节，超限整帧丢弃（绝不拆包）。
[VideoSender] 1包/帧 统计：成帧 23 超限丢弃 0 编码错误 0  最近帧 187 字节（上限 296）
```

**判读**：

| 看到什么 | 含义 |
|---|---|
| `单包=是` + 每 5 秒一行 `1包/帧 统计` | ✅ 新代码生效了 |
| `最近帧 100~250 字节`，`超限丢弃` 增长很慢（5 秒 0~2 个） | ✅ 正常 |
| `超限丢弃` 每 5 秒十几次 | 场景太复杂/码率偏高 → 把 `video_bitrate_kbps` 从 10 降到 8，重启服务即可（不用重编） |
| `成帧` 一直不涨、`编码错误` 在涨 | 编码器有别的报错，把这行日志原样发我 |
| 没有 `单包=是` | 编译没成功/跑的还是旧二进制，回到 3.3 |

想实时盯着看：

```bash
tail -f ~/my_lf_INF_20261025/logs/autostart.log | grep --line-buffered VideoSender
```

### 3.5 客户端上看画面

1. 客户端（`源码\build\release\luojiamaster.exe`）正常登录 `192.168.12.1`，选手端视频正常。
2. 按 **H** 切到第二视角。
3. 期望：**能看到一张一张的画面，帧率低（几帧/秒），但不是黑屏/等待**。

> 如果每次切过来只闪一下就没了：那是客户端旧版"丢包重置解码器"的问题。
> 现在每帧都是独立 IDR，重不重置都能马上出图——所以这也算一次客户端版本的旁证。

## 四、怎么判断"这次到底好没好"

跑 60 秒后退出客户端，拆抓包（在 `lower-machine/诊断工具/` 里）：

```
python rm0310.py dump "C:\...\logs\<最新会话>\network_capture.bin"
```

重点看三行：

| 看什么 | 之前（300×240 多包） | 现在（160×160 单包）期望 |
|---|---|---|
| `CustomByteBlock(rx)` 条数 | 9 条 / 34 秒 | 越多越好（通过率没变，但每条现在都是一整帧） |
| 内层 `长度` 分布 | 300（每包塞满 296B 数据） | **100~250 左右的零散值**（一帧一条，长度都不一样） |
| 内容类型 | `H264 SPS / H264 P帧 / 未知` | **每一条都应该是 `H264 SPS` 开头**（全 I 帧） |

**只要「内容类型」里每一条都是 `H264 SPS`，并且条数 ≥ 1，客户端就应该能出图。**
如果 dump 有包但客户端还是黑屏，那就轮到解码/显示这一段，把 dump 输出发我。

## 六、下一步（看完画面以后再调，不是现在）

单包模式证明了链路能"偶尔送货"以后，可以按实测的到达率往回加：

| 实测到达率 | 建议 |
|---|---|
| ≥ 50% | 保持单包，把分辨率加到 192×192 / 200×160、帧率 10fps（每帧约 250B，仍在 296B 内） |
| 20%~50% | 保持 160×160，先不要动 |
| < 5% | 说明通道确实只有每秒零点几个包，只能继续降低帧率（2fps）做"看路况"用 |

**注意**：不管怎么调，只要 `video_single_packet: true`，每帧就还是一个包，
到达一帧就是一帧，不会再回到"永远拼不出来"的状态。
