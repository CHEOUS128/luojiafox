## 按时间倒序

**2026-10-24 · [`图传v3-串口写修复-2026-10-24.md`](图传v3-串口写修复-2026-10-24.md)**
Jetson 侧「成帧在涨、客户端 0 包」的真因：串口 `write()` 超时全 0，309 字节只写出去一部分，
半帧留在线上把下位机状态机顶歪。修法是 `gimbal.try_send_raw()` 检查返回值 + 跨轮重发。
**这条是后面所有「能出图」的前提。**

**2026-10-23 · [`单包模式-部署与验证-2026-10-23.md`](单包模式-部署与验证-2026-10-23.md)**
把发送端改成「一帧 = 一个包」（160×160 / 5fps / 全 I 帧 / 整帧 ≤296B）。
理由：链路通过率极低，多包一帧永远拼不完整；改成单包后任一包单独到达都能解出一张图。

**2026-10-23 · [`主循环卡顿诊断-2026-10-23.md`](主循环卡顿诊断-2026-10-23.md)**
`Current FPS: 0.0`、`成帧` 不涨时怎么判断卡在相机/云台数据/检测。
现在 `standard_mpc.cpp` 里的 `LoopWatchdog` 就是这次加的，日志里搜 `[看门狗]`。

**2026-10-20 · [`图传v2-部署与验证手册.md`](图传v2-部署与验证手册.md)**
第一版 Jetson 部署流程（传文件 → 编译 → 离线验证）。文件清单仍有参考价值。

## 已被取代的结论（别再照着做）

| 当时的说法 | 现在的事实 |
|---|---|
| 「第二视角要 300×240 / 10fps / 90kbps」 | 现在是 160×160 / 5fps / 10kbps 单包，296B 硬上限 |
| 「`video_send_enable` 默认 false，别开」 | 现在是 `true`，开机自启就在发 |
| 「瓶颈在 Jetson 编码」 | 编码一直是好的，瓶颈在串口短写与后面的转发跳 |
| 「主循环几十秒才转一次」 | 已由看门狗日志 + 相机出图速率确认，不再是当前问题 |
