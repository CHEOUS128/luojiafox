# 图传 0 帧的真实原因：串口 write 短写（2026-10-24）

## 一句话结论

**编码器一直是好的，是串口写只写出去半帧，然后把半帧丢在线上就走了。**
下位机的 309 字节状态机从此错位，把后面紧跟的控制帧当成视频帧的剩余字节吞掉，
一个完整视频帧都凑不出来。

自瞄能用，恰恰说明了问题不在"串口通不通"：32 字节控制帧只要内核缓冲里有 32 字节空位就能一次写完；
309 字节的视频帧在缓冲将满时只会写出去一部分。

---

## 1. `成帧` 计数到底说明什么

`[VideoSender] 1包/帧 统计：成帧 11127→11224` 是**编码线程**打的：

- 11127→11224，20.434 秒，**4.75 帧/秒**，与 `video_fps: 5.0` 相符；
- `超限丢弃 25` 是启动阶段的一次性现象（第一帧 208 字节都在 296 上限内，最近帧 243~256）；
- `编码错误 0`。

也就是说：**相机 → 缩放 → x264 → 封成 309 字节一帧 → 塞进待发队列，全程正常。**

`成帧` 只统计到"塞进 `impl_->pending` 队列"为止，**不等于写进了串口**。
中间还有一步 `gimbal.try_send_raw()`，而这一步以前不看返回值。

## 2. 为什么控制帧到得了、视频帧到不了

`io/serial` 这个库的 `SerialImpl::open()` 用的是：

```cpp
fd_ = ::open(port_.c_str(), O_RDWR | O_NOCTTY | O_NONBLOCK);   // src/impl/unix.cc:139
```

而 `Timeout` 默认**全是 0**，旧代码从来没有调用过 `setTimeout()`。于是 `SerialImpl::write()` 的行为是：

```
第 1 轮：timeout_remaining = 0 → pselect 立即返回 → ::write() 写多少算多少
第 2 轮：timeout_remaining <= 0 → break          // 只写了一次就收工
返回 bytes_written（可能远小于 length）
```

三种帧的下场完全不同：

| 帧 | 长度 | 内核缓冲将满时 |
|---|---|---|
| 控制帧 `VisionToGimbal3` | 32 B | 只要还剩 32 字节空位就一次写完 → **自瞄正常** |
| 视频帧 `0x0310` | 309 B | 可能只写 0~300 字节 → **返回半帧，旧代码直接丢** |

旧代码三个写点（`send()`、`send(VisionToGimbal)`、`try_send_raw()`）**都没有检查返回值**，
`send_raw()` 甚至连返回值声明都没有（`void`）。

## 3. 下位机那边发生了什么

`Self_aim.c::process_usb_data_packet()` 只有一个状态机：

```c
if (kind == 0) { 0xA5 → kind=1（收 309）; 0xFF → kind=2（收 32）; }
else            { 不看内容，盲收够 309 / 32 字节 }
```

收到半帧视频后，它还停在 `kind==1`，接下来几帧控制帧的 `FF ... 0D` 全被当成视频帧的剩余字节吃掉，
凑满 309 字节 → CRC 失败 → 回到 `kind==0` 重新找帧头。
**所以每帧视频会连累 3~4 条控制帧**（还有 160 多条能活下来，自瞄照样能打）。

客户端收到的是"CRC 不对的 300 字节包"或"根本没有完整包"，画面自然是 0 帧 / 最多 1 帧。

## 4. 实测证据（PTY，用的是仓库里这套 serial 库）

### 4.1 裸 write，读端故意慢（复现短写）

```
【修复前】100 帧 309B：短写 32 帧，最少只写出 0 字节，单帧平均耗时 10 us / 最慢 65 us
【修复后】100 帧 309B：短写 0 帧
```

32% 的 309 字节帧短写，最坏一个字节都没写出去，平均只花 10µs —— 就是"假装写了"。

### 4.2 真实 `io::Gimbal` 类 + 与 `Self_aim.c` 等价的下位机状态机

主循环 6ms 一轮（控制帧 32B）、视频 309B 每 210ms 一帧，下位机按现场速率排空
（`162901 B / 30 s ≈ 5430 B/s`，来自 `VideoForward_Debug` 的计数）：

```
=== 上位机侧（真实 Gimbal::serial_stats）===
控制帧：完整 1000，短写 0，重发 0（send() 最慢 53 us）
视频帧：完整 29，短写 0，跨轮续写 0，失败 0（共发 29 帧）

=== 下位机侧（等价状态机）===
视频完整 29 / 坏 0（100%）| 控制帧 OK 1000 / 坏 0 | 结束时残留 0 字节
```

再把下位机拖慢到 1200 B/s 制造持续堵塞：

```
控制帧：完整 604，短写 405，重发 390（send() 最慢 5423 us）
视频帧：完整 22，短写 0，跨轮续写 0，失败 6（共发 29 帧）
下位机：视频完整 22 / 坏 0（76%）| 控制帧 OK 604 / 坏 0 | 残留 0 字节
```

**任何情况下都不会出现半帧**，短写只会让"这一轮少写"，不会让"线上多出垃圾"。

## 5. 改了什么

只改了三个文件：

### `io/gimbal/gimbal.hpp` / `gimbal.cpp`

1. **`apply_timeout()`**：`open()` 之后、`reconnect()` 之后都设置
   `setTimeout(0, 100, 0, kWriteWaitMs=5, 0)`。
   - `write_timeout_constant = 5ms`：单次 `write()` 最多在库内部循环 5ms；
   - `write_timeout_multiplier = 0`：**必须 0**，否则 5 + 1×309 = 314ms，一次写就把主循环拖死。

2. **写队列 `pump_writes()`**，严格顺序：
   `续写上一帧剩余字节 → 控制帧 → 整帧视频`
   - 半帧绝不留在线上：没写完的字节存进 `video_leftover_`，下一轮接着写；
   - 控制帧一律 `ctrl_len_=0` 才算写完，没写完就保留 `ctrl_off_` 断点，**本轮不再写视频**；
   - 控制帧短写是**不可恢复**的（32 字节没有长度字段，下位机会把后续视频当控制帧吞掉），
     所以只允许"从断点补完"，绝不能"重发整帧"（旧方案重发整帧是错的）。

3. **`try_send_raw()` 只允许一帧在途**：上一帧还没写完就直接丢新帧（`video_fail++`），
   否则写慢的时候一帧接一帧会占死写通道，控制帧永远排不上队（自瞄直接废掉），
   而且 309 字节断在半路时 `video_leftover_` 会被顶掉 → 半帧上线。

4. **`SerialStats`**：`ctrl_ok / ctrl_short / ctrl_resync / video_ok / video_short / video_stall / video_fail`。

### `src/standard_mpc.cpp`

每秒多打一行（和 `Current FPS` 同一时刻）：

```
[Serial] 控制帧 完整 N 短写 N 重发 N | 视频帧 完整 N 短写 N 跨轮 N 失败 N
```

## 6. 怎么判读新日志

**核心对照：`[Serial] 视频帧 完整` 的增量 vs `[VideoSender] ... 成帧` 的增量。**

两者都在 5 秒 / 1 秒量级上，正常应该是"完整 ≈ 成帧"（都在 4~5 帧/秒）。

| 现象 | 含义 | 下一步 |
|---|---|---|
| 视频帧 完整 ≈ 成帧 | 309 字节整帧已经写进 USB，问题在**下位机 → VT03 → 无线** | 查 `VideoForward_Debug` 的 `forwarded / tx_error / tx_retry / tx_stuck` |
| 视频帧 完整 ≈ 0，短写/跨轮在涨 | USB 侧写不动 | 看 `[Serial]` 数字，排查下位机 USB 取数 |
| 视频帧 完整 ≈ 0，失败在涨 | 上一帧没写完就把新帧顶掉 | 同上 |
| 控制帧 重发 长期 > 0 | 上一条控制帧没补完就来新指令（理论上应为 0） | 说明串口真的堵死了 |

`send()` 最慢一次是 5ms 量级（实测 53µs ~ 5.4ms）——它现在是主循环最坏情况的上限，
不会出现 100ms 级别的卡顿。

## 7. 仍未解释的一点（诚实记录）

现场 `VideoForward_Debug` 的 `usb_bytes` 是 30 秒 162901 字节 ≈ 5430 B/s。
按 `Current FPS 66.8~87.7` 算，控制帧 32B × 78Hz ≈ 2500 B/s，视频 309B × 4.75Hz ≈ 1470 B/s，
合计约 4000 B/s，比实测少 ~1400 B/s。

`usb_bytes` 统计的是**原始 USB 字节数**，不经过帧解析，所以它证明"字节在流"，
但不能证明"帧完整"——这个量对不上，可能是日志窗口与 Watch 采样窗口不一致，
也可能 `Current FPS` 不是主循环真实频率。**不影响本次修复的判断**（模块自测里 309B 短写是可复现的），
但下次抓日志时建议把 `usb_bytes / frames / crc_error / forwarded` 四个计数在同一时刻一起读。
