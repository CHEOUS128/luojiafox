## 一、本次改动（唯一新增功能）

### 双摄像头：工业相机画面 → 自定义客户端第二视角

**目的**：把自瞄用的工业相机画面送到操作手屏幕（客户端按 H 键切换）。

**链路**：

```
大恒相机 → 自瞄程序 → 全视野缩放 300×240 → H.264 编码
    → 切 300 字节包 → 封 0x0310 帧（309 字节）
    → USB CDC 串口（与云台控制共用）
    → 主控（电控待改造，原样转发）
    → VT03 图传发送端 → 无线 → VT13 → 选手端 → 客户端
```

**协议依据**：《RoboMaster 2026 高校系列赛通信协议 V2.0.0》表 1-41（`0x0310`）

## 三、2026-10-20 v2 更新（客户端兼容 + 画质）

### 1. 修复客户端解包格式（关键 bug）

客户端 `CustomByteBlockVideoDecoder` 期望的 300 字节 data 是**双层结构**，
原实现直接塞裸 H.264，客户端读到起始码 `00 00` 会当成"长度 0"整包丢弃。

现在 0x0310 的 data 字段按客户端源码实现：

```
[2B 内层包长度 BE][2B 序号 BE][H.264 片段 ≤296B]，剩余补 0
```

- 内层长度 = 2 + 载荷长度（最大 298）
- 载荷最大 296 字节/包

### 2. 修复尾巴跨帧滞留（会卡顿/卡死）

原实现只有攒满 296 字节才发包，每帧末尾不足 296 的尾巴留在缓冲区等下一帧。
编码器输出又常以帧/NAL 为单位 → 尾巴长期滞留，客户端持续缺数据。
现在每帧剩余字节**立即发完**（补 0 到 300）。

### 3. 画质调整

| 项 | 旧 | 新 | 理由 |
|---|---|---|---|
| 取景 | 1280×1024 中心裁 300×300 | **整幅缩放**到 300×240 | 原来只看到画面中间 23% 宽；改为全视野（不丢任何像素），300×240 与相机 5:4 同比例、无黑边 |
| 帧率 | 12 fps | 10 fps | 带宽固定，降帧率 = 每帧更多比特 |
| 码率 | 80 kbps | 90 kbps | 40Hz×296B≈94.7kbps 是实际上限；90 留余量，避免发包节拍跟不上被丢弃 |
| preset | veryfast | **slow** | 画质明显更好（ACE 实战就是 slow）；实测单帧编码约 66ms，已移到独立线程，不占主循环 |
| 锐化 | 无 | USM 0.6 | 主观清晰度↑，几乎不加码率 |
| SPS/PPS | 无 | repeat-headers=1 | 客户端中途接入也能解 |

### 3.5 编码移到独立线程（2026-10-20 21:30 实测后补）

实测 preset=slow 时，单帧编码约 66ms（测试程序从 10fps 掉到 6.7fps，每轮多出 66ms）。
如果在自瞄主循环里同步编码，主循环每 100ms 会被卡住 66ms，云台控制会抖。

改法：`VideoSender` 内部起一个工作线程。
- `feed()` 只做三件事：按 fps 节流、把最新帧 clone 下来、非阻塞取走已到节拍的包（microseconds 级）
- 编码/锐化/缩放/封包全部在工作线程完成
- 只保留"最新一帧"：编码慢于 fps 时自动丢旧帧，延迟不会累积
- 析构时 join 线程，`flush()` 会等工作线程当前编码完成（最多 300ms）

### 3.6 发送节拍改为令牌桶（修 bug）

原实现写的是"每轮最多补 8 个包"，但主循环一帧只调用一次 feed，
结果一帧就把 8 个包全发出去；仿真显示实际 80 包/秒，是限值 40 的两倍。
现改为令牌桶：按真实流逝时间积令牌（上限 4 个），长期平均严格 40 包/秒。
这就是实测"平均码率 55.9kbps"偏低的原因之一（发包节奏失真）。

### 4. 主循环发送预算与失败处理

- `Gimbal::try_send_raw()`：串口写失败返回 false
- 主循环每轮最多 16 个视频包（兜底），失败/超预算就丢弃剩余包
- 保证图传永远不会拖慢云台控制

### 5. 测试程序增强

```bash
# 读 config 里的 video_* 参数
sudo ./build/video_sender_test /tmp -c configs/standard3.yaml --compare

# 临时覆盖参数比较画质
sudo ./build/video_sender_test /tmp -c configs/standard3.yaml --fps 10 --kbps 100 --preset slow --sharpen 0.6 --compare
```

## 五、关键设计

### 1. 两种帧共用一条串口，靠帧头区分

| 帧类型 | 帧头 | 长度 | 用途 |
|---|---|---|---|
| 控制帧 | `0xFF` | 32 字节 | 三阶云台指令（现有） |
| 视频帧 | `0xA5` | 309 字节 | 0x0310 图传数据（新增） |

**下位机按帧头分流即可**，不需要额外协议协商。

### 2. 写锁保证帧完整性

视频帧 309 字节，若与 32 字节控制帧交错写入，会导致两帧都损坏。
新增 `write_mutex_`，`send()` 和 `send_raw()` 互斥。

### 3. 默认关闭

```yaml
video_send_enable: false
```

先保证原自瞄功能不受影响，联调通过后再打开。

### 4. 节流与取景

- 主循环 ~75fps，视频按 `video_fps`（默认 10fps）节流
- 默认**整幅缩放** 1280×1024 → 300×240（5:4 同比例，全视野、无黑边）
- 如需中心裁剪：`video_keep_aspect: false` + `video_crop_size: 300`

## 六、0x0310 帧格式（309 字节）

```
偏移    长度   内容
0       1     0xA5               帧头
1       2     0x2C 0x01          数据长度 300（小端）
3       1     seq                包序号（0~255 循环）
4       1     CRC8               前 4 字节，多项式 0x8C 初值 0xFF
5       2     0x10 0x03          cmd_id = 0x0310（小端）
7       300   data               双层封装（见下），不足补 0
307     2     CRC16              前 307 字节，多项式 0x1189 初值 0xFFFF
```

data 段内部（客户端解包规则）：

```
[2B 内层包长度 BE][2B 序号 BE][H.264 片段 ≤296B]，剩余补 0
```

**已离线验证**：用工程内 `tools/crc.cpp` 的真实 CRC 表重算，帧长/帧头/长度/CRC 全部正确；
双层封装按客户端源码逐字节仿真，H.264 字节可 100% 还原。
