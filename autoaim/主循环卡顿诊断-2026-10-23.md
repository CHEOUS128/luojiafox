# 主循环「几乎不转」诊断（2026-10-23 晚）

> **结论（2026-10-23 22:14，已解决）**：卡点是 **`gimbal.q()` 等不到下位机的上行帧**。
> 下位机接紧 + `systemctl restart` 后立刻恢复：
> `First q received.` → `Current FPS: 86.7~99.3` → `成帧` 每 5 秒 +24（≈4.8fps），
> `超限丢弃` 只有 1（编码器初始化帧），`最近帧 217~250 字节`。
> 下面的内容保留下来，作为下次遇到同样症状时的判读依据。

> 背景：单包模式部署成功后，日志显示 `成帧` 36 秒只涨了 2，`Current FPS: 0.0`。
> 这不是图传的问题——**相机每 20~30 秒才进主循环一次**，编码器没有输入，自然没有包可发。
>
> 这篇文章只做一件事：**把"卡在哪"用日志钉死**，不靠猜。
> 加了两处日志、零行为改动，编译一次（约 1 分钟），跑 40 秒看输出即可。

## 一、先看那次日志里已经很明显的一件事

| 时间 | 发生了什么 |
|---|---|
| 21:13:50 | `Current FPS: 0.0` |
| 21:16:06 | `Current FPS: 0.0` ← **和上一条隔了 136 秒** |
| 21:21:49.758 | `1包/帧 统计：成帧 0 …` |
| 21:21:50.772 | `Current FPS: 1.0` ← **开了视频之后才动了一下** |
| 21:22:25.268 | `1包/帧 统计：成帧 2 …` |

`Current FPS` 这一行是**主循环每轮都算、满 1 秒就打印**的。
它隔 136 秒才出现一次，说明**那 136 秒里主循环几乎没转**。

而且 21:13 / 21:16 这两次发生在当时还是 `300x240 @10fps` 的配置下，
**和本次单包模式无关**——所以 `成帧 2` 只是"主循环慢"的结果，不是单包模式写错了。

> 代码本身没问题：`最近帧 127 字节` 就是一个合法的单包帧。
> 缺的是"每秒钟至少 5 张图送进编码器"。

### 如果卡在「等云台数据」，说明自瞄其实也停了

这不是图传的锅，而是**比图传更严重的事**：`gimbal.q()` 一直等不到下位机回的 16 字节帧，
主循环就停在那里——顺便自瞄的云台控制也一起停了。
常见原因只有三个：C 板没上电 / 没在跑；USB 数据线松了或换过口（`/dev/ttyACM0` 变了）；
下位机发上来的不是 `FF … 0D` 的 16 字节帧。

先用这两条命令确认：

```bash
ls -l /dev/ttyACM0 /dev/ttyACM*          # 设备在不在、名字对不对
grep -a "Gimbal\]" ~/my_lf_INF_20261025/logs/autostart.log | tail -n 10
```

- 看不到 `/dev/ttyACM0` → 线/口的问题，换线换口后重启服务。
- 有 `Link lost, reconnecting...` / `Reconnect failed` → 下位机没回数据，找电控确认 C 板在跑。
- 有 `First q received.` 之后再没别的 → 串口开着，但对端不发合法帧，同样找电控。

## 八、最后确认到的根因与"为什么下传成功也会出这个问题"

**根因**：下位机 → Jetson 的**上行** 16 字节帧（`FF 04 | roll pitch yaw | crc | 0D`）断了。
`Gimbal::read_thread()` 连续 20 次、每次最多等 100ms 读不到合法帧，
就判定 `Link lost, reconnecting...`（约 2 秒一次），而主循环卡在 `Gimbal::q()` 里等新四元数，
于是自瞄、编码、发包全部停摆——表面上服务还 `active`，但一帧都发不出去。

**为什么"下传能用"不能证明"上行正常"**：上下行是两条独立的通道/方向。

| 功能 | 用什么数据 | 依赖方向 |
|---|---|---|
| 自瞄让云台转向 | `Gimbal::send()` → 下发 32 字节三阶帧 | **下传** |
| 自瞄算"当前云台角度" | `Gimbal::q()` ← 上行 16 字节帧 | **上行** |
| 第二视角视频 | `camera.read()` + `video_sender->feed()`，每轮主循环执行一次 | 间接依赖上行（卡在 `q()` 就轮不到它） |

所以"下传指令能生效"只说明下传通；上行断了，主循环会先卡死，视频跟着一起停。
**视频发不出去，很多时候不是图传的问题，而是主循环根本没走到发视频那一步。**

**下一步可以做的加固（尚未改，需要同意）**：给 `Gimbal::q()` 加超时——
上行断开时跳过这一轮的瞄准、让视频继续发。
代价是自瞄在掉线期间会失去云台角度输入，属于控制逻辑改动，等 CH 确认。
