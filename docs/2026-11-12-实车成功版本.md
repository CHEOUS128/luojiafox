# 2026-11-12 实车成功版本：直接用这套

这台车已经完成部署：原有自瞄继续运行，B 方案发送彩色工业相机画面，云台 C 板负责完整转发，自定义客户端按 `H` 看本车第二视角。2026-11-12 刷入 DMA 修复后，用户接回官方图传实测，确认效果“非常完美”。

**日常使用从第 2 节开始。不需要重新传源码、重新编译或重新烧板。** 本页统一记录当前成功组合；此前文档中的单包灰度、8 包上限、阻塞串口转发和旧目录部署步骤属于历史版本。

## 1. 四个目录各管什么

| 仓库目录 | 在哪里运行 | 当前职责 |
| --- | --- | --- |
| `autoaim/` | 车上的 Jetson | 原有自瞄、相机、模型、标定、与 C 板通信；同时发送 B 方案视频。 |
| `lower-machine/` | 云台、底盘 STM32 | 本轮只更新云台 C 板视频转发；控制与反馈继续沿用本车代码，底盘未改。 |
| `luojiamaster/` | 操作手 Windows | 连接官方选手端，接收视频和比赛数据，显示第二视角；本轮源码与 EXE 未改。 |
| `compression-war/` | Windows | 独立仿真与方案对比；仿真旁路 C 板、使用理想限速通道，不参与实车运行。 |

本车第二视角链路：

```text
工业相机 → Jetson 完整自瞄程序中的视频线程 → USB → 云台 C 板
→ USART6 / PG14 → 车端官方图传 VT03 → 官方接收端 VT13
→ 官方选手端 → MQTT CustomByteBlock → luojiamaster 解码显示
```

| 当前组件 | 确认方法 |
| --- | --- |
| Jetson B 档 | 启动参数含 `--cw-profile=quality`；程序版本标记 `cw-trial-20261109-r2`。仿真中同档叫 `one-320-gop20`。 |
| 云台 DMA 修复 | 最新仓库的 `gimbal_project/application/video_forward.c`、`video_forward.h`、`remote_control.c`；诊断构建标记 `0x261112D1`。本车已刷入。 |
| Windows 客户端 | `luojiamaster/程序/luojiamaster.exe`，10,843,136 B，MD5 `f76e9fe71ca07a9f7be1ee1e7a543bfc`。 |

B 档固定为彩色、完整视野、等比缩小补边，`320×256`、目标 20 fps、H.264、GOP20，编码预算约 74.5 kbps。每张图包括关键帧最多 2 包、净 H.264 最多 592 B；每包数据段 300 B，其中内层头 4 B、H.264 最多 296 B；外层串口帧 309 B，最高 50 包/秒。包格式和原客户端解码器保持兼容。

云台本次把容易超时截断的阻塞发送改为 DMA 整包发送，确认发送结束后才更换缓冲，保留原控制接收。**它不需要靠云台或底盘运动才能发送视频。**

## 2. 上电后怎么用

1. 按本车既有接线连接相机、Jetson 和云台 C 板，接回官方图传。Jetson 上电后现役服务自动启动，终端不用再手工开一个自瞄程序。
2. 客户端 Windows 接官方端的网卡设为 `192.168.12.2`，掩码 `255.255.255.0`，网关、DNS 留空。对应官方端为 `192.168.12.1`。先前调试 Jetson 用的 `10.88.26.1` 要切回这个比赛地址。
3. 官方选手端正常登录、显示图传，按 `P` 把键鼠来源设为“自定义客户端”。保持与本车既有裁判端、WiFi 连接一致。
4. 双击 `luojiamaster/程序/luojiamaster.exe`，服务端填 `192.168.12.1:3333`，队伍和机器人 ID 与官方端一致。登录后按 `Esc` 进入比赛模式，按 `H` 看本车第二视角。

完整的四台电脑接线图仍见 [Windows 四台电脑现场手册](../luojiamaster/现场施行手册-四台电脑-WiFi版.md)；队友互联的独立 `10.77.0.x` 网卡不与接官方端的网卡混用。

**短红线：客户端不要按 `Ctrl`，它会触发整车复位；接串口只接确认过的数据线与 GND，12V、VCC、5V、3V3 电源脚都不接。** 现役完整自瞄会发送控制，现场执行器状态由电控确认。

## 5. 以后改源码或换电脑时再用

当前车已部署完成，本节用于维护。更新前保留本车的配置、模型、标定和原运行目录；按停机维护安排切换，避免两个完整自瞄程序同时占用相机、USB。

| 传什么 | 用什么传、传到哪 | 怎么确认 |
| --- | --- | --- |
| Jetson r2 源码包及同名 `.sha256`；新包按下方命令加时间命名 | **手动 ToDesk 文件传输**到 `/home/nvidia4/Downloads/`；核验后，包内 8 个源码文件对应更新到 `my_lf_INF_20261025_cwtrial/`，不覆盖 `configs/`、`assets/`。 | 核对对应新包的SHA256；编译后两个程序的 `--help` 都应出现 `cw-trial-20261109-r2`。 |
| 云台固件源码 | 从最新仓库取完整云台工程，按本页第 1 节确认三个 DMA 文件，不需要再找一份额外“测试工程”。 | 电控打开 `lower-machine/26赛季全向轮步兵/gimbal_project/MDK-ARM/standard_robot.uvprojx`，Target 为 `standard_robot`；用本次新编译的 `standard_tpye_c/standard_tpye_c.hex`，由电控负责烧录。 |
| Windows 客户端 | 直接用仓库唯一交付 EXE；两台客户端电脑用同一份。 | 大小、MD5 按第 1 节核对。 |

本车当时已使用的历史包 `RM26_cw_trial_20261109_r2.zip` SHA256：

```text
e6dcb827598847accc45389ac1865de5a9b9cd8f325c08723f4c5c7b1c33b390
```

维护时需要生成新包，在 **Windows 仓库根目录**运行以下命令，以时间命名避免覆盖已有文件；打包器会显示新包路径、SHA256，并在旁边生成同名`.sha256`。随后手动ToDesk传输这两个文件。

```powershell
$package = '.\compression-war\runs\delivery\RM26_jetson_B_' + (Get-Date -Format 'yyyyMMdd_HHmmss') + '.zip'
python '.\compression-war\tools\package_vehicle_trial.py' --out $package
```

Jetson在`Downloads`中核验时，把下面文件名换成这次的真实名称：`tr -d '\r' < RM26_jetson_B_日期时间.sha256 | sha256sum -c -`。生成日期、打包说明或源码改变都会改变ZIP校验值，新包使用新SHA，不沿用上面的历史值。

在源码准备好的 **Jetson 现役目录**，实际成功的编译配置如下。只编这两个目标：

```bash
cd /home/nvidia4/my_lf_INF_20261025_cwtrial
cmake -S . -B build_cw -G 'Unix Makefiles' \
  -DOpenCV_DIR=/usr/local/lib/cmake/opencv4 \
  -DCUDA_TOOLKIT_ROOT_DIR=/usr/local/cuda-12.6 \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.6/bin/nvcc
make -C build_cw standard_mpc video_sender_test -j2
./build_cw/standard_mpc --help | grep 'cw-trial-20261109-r2'
./build_cw/video_sender_test --help | grep 'cw-trial-20261109-r2'
stat -c '%y %s %n' build_cw/standard_mpc build_cw/video_sender_test
sha256sum build_cw/standard_mpc build_cw/video_sender_test
```

这台车已编好的 `standard_mpc` SHA256 为 `9e4fef10f9c7ce68aac3ec70eb3f0bb915fbebb4d0394fdec68130beaccf2f50`。编译完成只说明产物准备好，现役服务仍以第 3 节的启动配置为准。需要回退时，由负责人把该服务切回保留的原目录；本页日常步骤不执行回退或重启。

## 6. 这次实际验证到了什么

| 环节 | 实际结果 |
| --- | --- |
| 修复前，静止离线、CH340 纯接收 | 两轮均未找到完整 CRC 合格的 309 B 包；同一包反复只输出前段，共重试三次。 |
| 修复后，第一轮 60 秒纯接收 | 2391 个完整 309 B 包，CRC 全部通过，序号无缺失、重复或倒退，采集器错误为 0；平均 39.84 包/秒。只有开始监听时的 37 B 起始残段。 |
| 原客户端解码器重放这轮接收数据 | 按原接收时刻统计，稳态每秒 19～21 张，平均约 19.95 张；这是抓包重放统计，不是屏幕刷新或端到端延迟实测。 |
| 后两轮 Windows 串口采集 | 因 Overrun 提前停止，未计为通过一分钟连续验收；原因没有确认。 |
| 接回官方图传 | 用户现场确认第二视角效果“非常完美”。本次没有额外记录官方链路的精确丢包率或延迟数字。 |

后续优化从这套成功组合继续；B 的画质和时延对比仍使用 `compression-war/` 的原始对照与统一播放器，不改已经确认的传输预算。
