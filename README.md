## 三、完整信息流：一帧画面从相机到屏幕

这是本仓库最核心的一条链路。下面把**每一跳是什么、怎么实现的、有没有验过**写清楚。

```
 车上（Jetson + STM32 + VT03）                       操作间（VT13 + 选手端 + 客户端）
 ┌──────────────────────────────────┐              ┌────────────────────────────────┐
 │ ①相机 → ②编码 → ③USB → ④STM32   │              │ ⑦VT13 → ⑧选手端 → ⑨MQTT → ⑩客户端 │
 │                            ↓     │              │                                │
 │                        ⑤UART     │   ⑥无线      │                                │
 │                            ↓     │ ◄──────────► │                                │
 │                          VT03    │              │                                │
 └──────────────────────────────────┘              └────────────────────────────────┘
```

### 跳① 相机 → Jetson

大恒 MER2-135-208U3C 模组，USB3 接 Jetson。自瞄程序按 10fps 取图。

**为什么是 10fps**：这条自定义通道的硬上限是 50Hz × 300 字节 ≈ 94.7 kbps，装不下更高帧率。
“及格就行”的取舍，画面清晰度和帧率都是这条带宽限制下的结果，不是 bug。

### 跳② Jetson 编码

**2026-10-23 起：一帧 = 一个包。** 从相机画面中心裁 320×320 → 缩到 160×160 →
每帧单独 H.264 编码（全 I 帧，自带 SPS/PPS）→ 整帧必须 ≤296 字节，
塞不下就整帧丢掉（**绝不拆成多个包**）。5fps，约 10kbps。

> 为什么：链路通过率只有 0.16%~0.64%，一帧需要好几个包时永远拼不完整；
> 一帧一个包以后，**任何一个包单独到达都能解出一张完整的图**（最坏是"幻灯片"）。
> 原来的做法是 300×240 全视野、10fps、90kbps，一帧切 2~4 个包。

### 跳③ Jetson → STM32（USB 线）

Jetson 通过 USB 数据线连着 C 板，走 USB CDC（虚拟串口，`/dev/ttyACM0`）。

**这条线上混着两种帧**，靠第一个字节区分：

| 首字节 | 长度 | 含义 |
|---|---|---|
| `0xFF` | 32 字节 | 自瞄的云台控制指令（帧尾 `0x0D`） |
| `0xA5` | 309 字节 | 第二视角视频帧（0x0310） |

**为什么视频帧是 309 字节**：裁判系统协议规定 0x0310 的 `data` 段是 300 字节（表 1-41），
外面再套 7 字节帧头（`0xA5` + 长度 2 + 序号 1 + CRC8 1 + cmd_id 2）和 2 字节 CRC16，
7 + 300 + 2 = **309**。这就是官方通信协议 1.2 节的串口帧格式，不是我们自创的。

### 跳④ STM32 校验并排队

`video_forward.c` 做四件事：检查帧头/长度/cmd_id → 校验 CRC8 和 CRC16 → 放进 8 帧深的队列 → 由 200Hz 任务取出来转发。

代码里有三个计数器，是**判断这一跳是否正常的关键**：

| 计数器 | 含义 | 正常表现 |
|---|---|---|
| `Forwarded` | 成功转发出去的帧数 | 随视频帧持续增长（约 40 帧/秒） |
| `CrcError` | 收到但校验失败 | **必须是 0** |
| `Overflow` | 队列满导致丢帧 | **必须是 0** |

> 实测：`Forwarded` 在涨、`CrcError = 0` → **跳①②③④ 全部正常**。

### 跳⑤ STM32 → VT03（串口，PG14）

C 板的 **PG14** 脚用 921600 8N1 把 309 字节帧发出去，接到 VT03 的 **RX**。

**协议依据**：通信协议 1.3 节原文写的是“图传链路由裁判系统选手端和图传模块进行数据转发，
**从图传模块（发送端）的串口接收数据**”，表 1-1 规定这个口就是 921600。
所以“机器人往 VT03 的 RX 发裁判系统帧”这方向是对的。

**实测结论**：`HAL_UART_Transmit()` 返回 `HAL_OK`，说明数据已经写进芯片的发送寄存器、从 PG14 出去了。

### 跳⑥ VT03 → 无线 → VT13  ← **它没坏，但只放过极少数包**

VT03 把串口收到的数据经无线送到操作间的 VT13 接收端，VT13 再交给选手端，选手端转成 MQTT 的 `CustomByteBlock` 主题。

**这里有两个必须分开的事实**：

1. **官方图传画面正常**，只能证明“VT03 的相机 → 无线 → VT13 → 选手端视频”这条链是好的。
   官方画面走的是 VT03 **内部**的相机，**根本不经过 UART**。所以它对我们要走的这条路**没有任何证明力**。
2. **VT03 的产品说明书从头到尾只写了 21 字节遥控帧（`0xA9 0x53`），从没写它会解析/转发 0x0310。**

**现在的实测结论（2026-10-23 复核）**：

| 场景 | 发送节奏 | 通过率 |
|---|---|---|
| 电控本机 probe（灌包，309 整帧样式） | ~1 包/秒 | **100%**（22/22） |
| 真车（10-21 21:24 会话） | ~40 包/秒 | **0.64%**（1397 包到 9 个） |
| 真车（10-22 16:42 会话） | ~38 包/秒 | **0.16%**（2506 包到 4 个） |

→ **这一跳会转发，但吞吐有很低的上限。** 1 包/秒能全过，40 包/秒几乎全丢。
→ 这是目前唯一的真问题，也是下一步要测的东西（见结论文档 A0/A 步）。

### 跳⑦⑧⑨ MQTT → 客户端

选手端把数据发布到 `192.168.12.1:3333` 的主题 `CustomByteBlock`，客户端订阅。
这一跳也**验过是好的**：客户端的血量、状态、官方画面都正常，说明网络、机器人 ID、订阅都没问题。

### 跳⑩ 客户端解码显示

`H` 键切到第二视角。客户端解包后送 FFmpeg 解码。

**客户端只认 300 字节的包**（`kMaxSupportedPacketBytes = 300`）。
如果 VT03 把 309 字节原样透传过来，客户端会**静默丢弃**。
不过实测到 MQTT 的全是 300 字节（外壳已经被剥掉），所以**这条不是现在的问题**。

**客户端这一段的好消息**：10-21 / 10-22 两次真车会话里，客户端确实收到了真 H.264 包
（`H264 SPS`、`H264 P帧`），说明「收包 → 解 protobuf → 拆 300 字节 → 认 H.264」全都没问题。
**坏消息**：包太少（0.16%–0.64%）、最长连续 2 个，任何解码器都拼不出完整帧。

### 一句话总结现状

| 跳 | 内容 | 状态 |
|---|---|---|
| ① | 相机 → Jetson | ✅ |
| ② | 编码 | ✅ |
| ③ | Jetson → STM32（USB） | ✅ |
| ④ | STM32 校验排队 | ✅ `Forwarded` 涨、`CrcError=0` |
| ⑤ | STM32 → VT03（串口 PG14） | ✅ 芯片报告发送成功 |
| ⑥ | **VT03 无线 → VT13** | ⚠️ **通，但通过率 0.16%–0.64%（瓶颈在这里）** |
| ⑦⑧⑨ | 选手端 → MQTT → 客户端 | ✅ |
| ⑩ | 客户端解码显示 | ✅ 收到过真 H.264，只是包不够 |

## 四、排查方案在哪里

**主线文档：[`lower-machine/第二视角链路逐环节排查方案.md`](lower-machine/第二视角链路逐环节排查方案.md)**

它把“VT03 有没有转”这个看不见的问题，拆成四个能独立下结论的实验：

| 实验 | 做什么 | 回答什么问题 |
|---|---|---|
| 看灯 | 看 VT03 指示灯颜色 | 无线对频到底成没成 |
| 实验 1 | PC 接在 PG14 上旁听（或示波器量波形） | 串口线上到底有没有数据 |
| 实验 2 | PC 接 VT03 的 TX | VT03 活着吗、引脚定义对吗 |
| **实验 3** | **PC 代替 STM32，直接往 VT03 的 RX 灌包** | **VT03 到底会不会转发自定义数据** |
| 实验 4 | 真链路把发送速率降到 2Hz 数包 | 是“完全不通”还是“通了但丢包” |

**实验 3 是核心**，也是把 STM32 从嫌疑名单里彻底拿掉的办法：
如果电脑直接把数据打进 VT03、客户端还是收不到，那就跟 STM32 一点关系都没有，问题锁定在 VT03 及其之后。

工具在 [`lower-machine/诊断工具/`](lower-machine/诊断工具/)：

```bash
python rm0310.py selftest                        # 先自检，不接任何硬件
python rm0310.py ports                           # 看电脑上有哪些串口
python rm0310.py recv COM7 --seconds 20          # 收包（扮演接收端/旁听）
python rm0310.py send COM5 --style alt --hz 1 --seconds 120   # 灌包（扮演 STM32）
python rm0310.py dump "...\logs\<会话>\network_capture.bin"    # 拆客户端抓包
```

**需要准备的硬件**：USB-TTL 模块（**必须能跳 3.3V 电平**）、杜邦线、万用表。
原因和接线细节都在方案第二节，**接之前务必先读那里的三条安全底线**。

**新手电控先看这个**：[`lower-machine/电控Debug入门手册.md`](lower-machine/电控Debug入门手册.md)
——讲的是“怎么有理有据地查”，而不是“照着我说的试一遍”。

## 五、上位机这一段：原封不动、开机即用

CH 的要求是：**电控把接收侧改好之后，上位机这边不需要任何人操作。**

这件事已经做完了，而且**代码是原封不动在跑的**：

```
车上电 → Jetson 开机 → 15 秒后 systemd 自动拉起 autoaim-20261025 服务
      → 加载自瞄模型 → 打开相机 → 开始往 USB 串口发 32 字节控制帧 + 309 字节视频帧
```

**没有任何人工步骤**：不用 SSH、不用点开始、不用开终端。断电再上电就是完整功能。

| 项目 | 值 |
|---|---|
| 服务名 | `autoaim-20261025` |
| 自启 | `systemctl is-enabled autoaim-20261025` → `enabled` |
| 崩溃自动重启 | `Restart=always` |
| 代码目录 | Jetson 上的 `~/my_lf_INF_20261025` |
| 配置 | `configs/standard3.yaml`（改了不用重新编译，重启服务即可） |

**一次性安装脚本**（已经执行过，换新小电脑时才需要再跑）：

```bash
cd ~/my_lf_INF_20261025
sudo bash scripts/enable_video_service.sh
```

**查看它是不是在跑**：

```bash
systemctl status autoaim-20261025          # 看 active (running)
journalctl -u autoaim-20261025 -n 50       # 看最近 50 行日志
```

**要停它（比如手动测试占串口）**：

```bash
sudo systemctl stop autoaim-20261025       # 测完记得 start 回来
```

> 注意：`autoaim.service`（不带 `-20261025`）是**旧版**，指向 20261013，已被停用。
> 两个不要弄混。

自瞄程序本身的行为：只在**识别到目标**时才发控制帧，空闲时串口上只有视频帧。
所以“串口安静”不代表程序没在跑，看服务状态和日志更可靠。

## 六、各子系统速查

### luojiamaster —— 自定义客户端（Windows）

**功能**：接收比赛数据和官方第一视角图传（HEVC 1080p60），并通过键鼠操控实车。

**前置条件（缺一不可）**：

1. 裁判端 `RoboMasterEngine` 已启动并登录
2. 官方选手端 `RoboMasterClient` **版本 ≥ 12.0.0.213**（关键）
3. 选手端图传画面正常显示
4. 选手端 P 面板 → 键鼠控制来源 → 选「自定义客户端」
5. 客户端与选手端登录**同一机器人 ID**

**登录地址**：选手端在同机用 `127.0.0.1:3333`，异机用 `选手端IP:3333`
**快捷键**：`Esc` 比赛模式 / `H` 视角切换 / `I` 画面翻转 / `P` 设置

**成品**：[`luojiamaster/程序/luojiamaster.exe`](luojiamaster/程序/luojiamaster.exe)（双击即可）
**源码**：`luojiamaster/源码/`（含全部第三方依赖源码，CMake 直接构建）
**从零编译**：[`luojiamaster/完整复现指南.md`](luojiamaster/完整复现指南.md)
**本地模拟比赛环境**：[`luojiamaster/局域网联调手册.md`](luojiamaster/局域网联调手册.md)

### autoaim —— 自瞄 + 第二视角编码（Jetson）

基于[同济大学 SuperPower 战队 25 赛季自瞄](https://github.com/TongjiSuperPower)二次开发。
双模型跟踪（装甲板 KF + 整车 EKF 并行）、三阶指令管道、无 ROS 依赖。

**平台**：Jetson Orin，相机 1280×1024
**关键参数需按车标定**：`yaw_offset`、`pitch_offset`、弹速、相机内外参

详见 [`autoaim/README.md`](autoaim/README.md)、[`autoaim/图传v2-部署与验证手册.md`](autoaim/图传v2-部署与验证手册.md)。

### lower-machine —— 下位机固件（STM32）

两个 Keil 工程：`chassis_project`（底盘）和 `gimbal_project`（云台 + 视觉通信 + 图传转发）。
`gimbal_project` 里 `application/video_forward.c` 就是第二视角的转发实现。

**接口**：三阶指令协议 32 字节帧（帧头 `0xFF`、帧尾 `0x0D`、角度单位为度），
字段为 `fire_advicec`(u8) + `yaw/yaw_vel/yaw_acc` + `pitch/pitch_vel/pitch_acc` + `distance`（7×float）。

详见 [`lower-machine/README.md`](lower-machine/README.md)。

## 七、现在到底卡在哪（一句话）

> **每一跳都活着，但真视频的通过率只有 0.16%–0.64%。**
> 电控那台机器上 309B 整帧能以 100% 通过（1 包/秒）；现场 40 包/秒时只过来不到 1%。
> → **不是哪里坏了，是这条通道吃不下 40 包/秒。**
>
> 这也解释了为什么"客户端显示等待 CustomByteBlock 视频流"却永远没有画面：
> 客户端能收、能解析、也能认出 H.264，只是**包太少、连不成一个完整帧**。

下一步**先按 [`autoaim/单包模式-部署与验证-2026-10-23.md`](autoaim/单包模式-部署与验证-2026-10-23.md)

## 八、已知限制

**luojiamaster**：控制响应延迟高于官方选手端（多一跳 MQTT 转发）；视频为 CPU 软解，未启用硬件加速。

**autoaim**：仅针对 26 全向轮步兵调校；双模型为「注入速度」混合做法，非完整实现；
换板保护（`use_phase_jump_guard`）默认未启用；图传编码 8~10fps、画质未做主观调优（待链路跑通后迭代）。

**图传**：第二视角（0x0310）链路未通，卡在 VT03 无线一跳；
通道带宽硬上限约 94.7 kbps（40Hz × 296B），清晰度受此限制。
