## 这次到底改了什么

下面三份文件都在 `26赛季全向轮步兵/gimbal_project/application/`：

| 文件 | 改动 |
|---|---|
| `video_forward.c` | 从“CPU 一个字节一个字节地等着发”改成 TX DMA；发送任务及时返回，完整发完才算成功；保留队列与私有发送缓冲，加入限速和故障恢复 |
| `video_forward.h` | 增加发送完成入口和可查看的状态计数；原有诊断字段顺序保留 |
| `remote_control.c` | 在原 USART6 中断末尾补上独立的发送完成处理；保留原有遥控接收、DMA 双缓冲和 IDLE 解析 |

此前 `722f2f8` 的两项修复继续保留：`Self_aim.c` 的视频错位恢复，以及发送队列满载时避免覆盖正在发送的数据。经过这次修改，视频不会再走原来的“整包等待 20 ms，没发完就从头重试两次”的路径。

电控需要核对版本时，可在 Keil Watch 查看 `VideoForward_Debug`：

- `build_tag` 应为 **`0x261112D1`**。
- `dma_started` 是启动次数，`dma_completed` 和 `forwarded` 是 **UART 最后一个字节真正发送完成后的计数**。
- `dma_timeout`、`dma_start_fail`、`dma_error`、`dma_abort_fail` 分别帮助区分超时、没启动成功、DMA 错误和恢复失败。

## 链路和接口

```text
Jetson → USB CDC → C板按帧头分流、校验、排队 → USART6 TX DMA → 车载图传 → 官方端 → 自定义客户端
```

- 自瞄控制帧仍为 **32 B**，对应 `autoaim/my_lf_INF_20261025`；视频仍为 **309 B 外层帧 / 300 B 数据段 / 0x0310**。压缩、颜色和每张图的分包由上位机负责，C 板原样转发。
- 视频出口仍为 **USART6 / PG14，921600、8N1**。保留原接线；不要凭板上丝印与 MCU 串口名字的差异随意改线。
- 每次发送启动，包括异常重试，按现有 DWT 周期计数保持至少 20 ms 间隔，上限 50 包/秒；DWT 不可用时保守回退到 21 个 HAL tick。调度迟到时不补发突发包。
- DMA 异常看门狗为 100 ms，恢复只处理发送端；不停止遥控接收，不改变云台或 IMU 任务的优先级。

## 已验证到哪一步

| 验证 | 实际结果 |
|---|---|
| 主机源码测试 | 34 个用例通过，覆盖启动失败、DMA/TC 完成、错误与超时恢复、队列、限速、计数回绕和遥控接收保留 |
| 11-12 烧录后第一轮 CH340 采集 | 60.014 s，2391 个完整 309 B 视频包，CRC 错误 0、序号缺口 0、重复 0；非 flush 解码得到 1178 张图 |
| 上述记录的稳态更新 | 按原到包时间离线解码统计，平均约 19.95 fps，完整秒最低 19 张；这是收到数据可解出的更新，不是屏幕刷新或端到端延迟测量 |
| 后续两轮 CH340 复测 | 采集端分别在 51.49 s、47.87 s 报 `Overrun` 后结束，未作为完整通过的测试 |
| 接回官方图传 | 用户亲自确认画面“非常完美”，当前版本接受；这段未提供测量日志，不填报官方端 fps 或延迟数字 |

首轮采集从发送中途开始，最前面有 37 B 残段；接收器从后续完整包重新同步，并等待关键帧出图。文件结束时的解码 flush 不算实时出图。后两轮采集器溢出记录保留，用户决定目前先以实际使用结果推进。
