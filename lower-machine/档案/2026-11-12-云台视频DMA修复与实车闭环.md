# 2026-11-12 云台视频 DMA 修复与实车闭环

**当前交付：电控已自行编译、烧录云台 C 板，用户接回官方图传后确认自定义客户端画面正常，接受当前版本作为上车里程碑。** 本文保存这次有效证据和改法，取代更早记录中的当前状态描述；旧文原文保留。

## 故障是怎么收敛的

原现象是静止时很难出图，大幅转动云台或移动底盘后偶尔出现一帧。11-12 的检查保持车辆静止，CH340 只接 RXD、GND，替代图传接收 C 板的 USART6 输出；Windows 同时通过网线只读查看 Jetson 原有程序和日志。诊断工具没有向 C 板发送控制数据。

Jetson 当时持续取图、编码并报告 USB 写入完成，没有等到移动或识别出目标才开始送视频的代码门槛。这是进程日志，没有取得真实 USB 总线抓包，不能把它写成逐笔 USB 事务已经验证。

C 板出口出现了清楚的异常：每个视频编号连续出现三次，三次都是同一包的前缀，每段不足应有的 309 B。改用低开销批量采集后，连续两轮各约 60 s、采集器均无错误，仍没有一个完整视频包通过 CRC。

```text
修复前低开销采集：
FINISHED: bytes=630744 chunks=4174 errors=0 failed=False
RAW bytes=630744; VALID 309B=0; INNER valid=0; OTHER frames=0
HEADERS 2317 PREFIX-CONSISTENT 2316 GROUPS {1: 1, 3: 771, 2: 1}
```

这一轮头间片段为 188～298 B，中位数 278 B。除首尾采集边界外，771 组都恰好重复三次。因此不能把最初采集器后来发生的 `Overrun` 当成整个异常的起点，也不能因为看见包头就认定完整包已经发出。

旧转发代码使用 `HAL_UART_Transmit` 阻塞发送 309 B，给整包 20 ms，失败后从包头额外重试两次。本地 HAL 的超时时间从整次调用开始计算，任务被抢占的时间也包含在内。现场的残包、同号三连和约 21 ms 的重试形态与这条路径一致。

主机测试使用仓库原 HAL 发送和等待函数，在明确注入的 TXE 等待条件下，重现了每次 278 B、三次同前缀、无完整包的行为：

```text
LEGACY_INJECTED deadline_ms=20 prefix_per_attempt=278 attempts=3 wire_bytes=834 forwarded=0 retries=2 errors=1 RX_state=32 RX_interrupt_bits=0
```

这说明旧实现确实能产生所观察到的故障形态。**本次修掉的直接问题是 C 板视频发送不完整、超时后反复从头发。** 云台和 IMU 的高优先级任务可以抢占该阻塞发送，但未直接测出板上抢占时长或 CPU 占用；不把这个触发解释写成精确测量结果。也没有通过让车运动来量出运动与出图概率的关系。

另一个代码事实是：仓库 HAL 的超时退出会修改 `gState`、`RxState` 并关闭部分收发中断位，不能将超时理解为只有“少发了几个字节”的影响。此前文档关于 HAL 状态的结论应以实际 HAL 实现为准。

还要注意实际调度的耦合：`Self_aim_task` 先发送USB状态反馈，再调用视频转发；旧转发会循环排队、阻塞和重试。Jetson主循环又先等待 `gimbal.q` 的状态，再给视频供图。因此“控制帧与视频帧解析分开”不代表两者在运行时互不影响。此次DMA任务及时返回，也消除了这条持续阻塞路径。

## 本次改动

只修改 `26赛季全向轮步兵/gimbal_project/application/` 中三份文件：

| 文件 | 本次内容 |
|---|---|
| `video_forward.c` | 非阻塞 TX DMA 状态机、私有缓冲所有权、真实发送完成计数、限速、失败与恢复计数 |
| `video_forward.h` | 完成入口及追加诊断字段；原有字段偏移保留 |
| `remote_control.c` | 在原 USART6 IRQ 末尾补独立的 TX 完成入口，原 RXNE/IDLE 与遥控解析保留 |

此前 [11-09 视频错位恢复及队列修复](2026-11-09-云台视频链路修复.md) 继续保留，包括 `Self_aim.c` 的重新同步，以及短临界区复制并出队、从独立静态缓冲发送的做法。底盘、控制协议、云台/IMU 优先级和任务间隔没有改动。

实现时避免了下面几个容易重新造成问题的点：

- DMA 完成前不覆盖私有 309 B 缓冲；Task 每次只做有限工作，不循环排空队列、不等待整包发完。
- 使用经过检查的 `HAL_DMA_Start_IT` 和 TX 专属回调。本地旧 `HAL_UART_Transmit_DMA` 没有检查底层 DMA 启动结果，其通用错误回调还可能处理 RX，不能直接照搬。
- DMA 搬完内存后还要等 UART 最后一个字节真正发完，即 TC。当前 USART6 IRQ 原本只有接收处理，必须补 TX 收尾；仅换成 DMA API 会漏掉这一步。
- TX 收尾不调用全量 `HAL_UART_IRQHandler`，避免它在同时出现 RX 错误时停止原有接收 DMA。
- 异常恢复先请求停止 TX，后续确认 DMA EN 已清才收尾；不调用全口 abort、不强改 `RxState`，不夺取其他发送者的 BUSY 状态。无法确认硬件停止时保留缓冲并锁定错误状态。
- 每次实际启动，包括异常重试，用已有 DWT 周期计数保持至少 20 ms 间隔，上限 50 包/秒；DWT 不可用或时钟切换时保守回退到 21 个 HAL tick。不修改 DWT 初始化，也不使用共享的累计时间函数。调度迟到不补发突发包。
- 100 ms 只作 DMA 异常看门狗，不能理解为新的阻塞发送时间；重试次数有界。

USB 协议保持 32 B 自瞄控制帧和 309 B 的 `0x0310` 视频外层帧；300 B 数据段、CRC、原始载荷不变。每图最多两包、压缩与颜色处理仍由上位机完成，C 板不解析图像内容。

原始记录的 SHA256 为 `2638b3c1a15b5c4914fa5b7877da630a61c49ce5cfdfd0ca97925f1549da8a7d`。逐包数据严格校验长度、CRC8、CRC16；内外序号按各自位数处理回绕。

采集从发送中途开始，最前面有 **37 B** 残段，之后 2391 个完整包连续通过。视频接收器要等后续关键帧才恢复出图；中途开始接收不应要求第一段立即解码。尾部 flush 才吐出的图像不计实时更新，也不拿不完整尾帧作展示。

上述帧率是**按照包原来到达 Windows 的时刻，离线解码统计可用图像的更新情况**；不是实际屏幕刷新率、线上精确逐包时间或相机到屏幕延迟。CH340 经 USB 成批上报，主机时间不能冒充串口线上的逻辑分析仪时间。

之后又进行了两轮 CH340 复测，分别在 **51.4876 s**、**47.8672 s** 出现接收端 `Overrun`，均提前结束，不能写成两轮 60 s 全通过。用户认为目前不影响正常使用，决定暂不继续追查这两次采集端溢出；这一项记录保留。
