## 一、根因（两个，叠加）

### 根因 A：上位机发 16 字节，下位机按 32 字节解析（**主因**）

| 位置 | 实际情况 |
|---|---|
| 上位机 `configs/standard3.yaml` | `three_order_enable: false` |
| 上位机 `gimbal.cpp:240` | 关闭时发送 `VisionToGimbal` = **16 字节** |
| 下位机 `Self_aim.c:48` | 判定 `temp_received == sizeof(RECEIVE_DATA)` = **32 字节** |
| 下位机 `Self_aim.h:49` | `RECEIVE_DATA_SIZE 32 //12之前的数据长度` |

**后果**：32 字节里只有 16 字节是真帧，另外 16 字节来自下一帧。所有字段整体错位。

实测推演（用你们真实的结构体和字节序）：

| 条件 | 上位机想发 | 下位机读到 |
|---|---|---|
| **无目标**（control=false） | yaw=0, pitch=0 | yaw=0.0000 → **云台不动** |
| **有目标** | pitch=-17.2°, yaw=68.8° | yaw=-17.2°（其实是 pitch）<br>yaw_vel=1.200（其实是 yaw）<br>pitch=9.37e-38（垃圾） |

这正好解释了现象：**视野里没目标时不出问题，有目标就转到固定视角或疯转**。

### 根因 B：我上一版下位机代码让两个解析器同时扫同一份字节

```c
VideoForward_Feed(data, length);        // 按 0xA5 找视频帧
process_usb_data_packet(data, length);  // 按 0xFF 找控制帧
```

视频载荷里随机出现的 `0xFF` 会被控制解析器当成帧头，把后面 32 字节随机数据当成一帧云台指令。

仿真（10 秒真实流量，2000 控制帧 + 400 视频包）：

```
控制帧接受 2371（真实 2000）→ 垃圾帧 371，误帧率 18.6%
```

**每 5 帧就有 1 帧是垃圾角度。** 即使修好根因 A，这一条仍会让云台抖动。

## 二、改动清单

### 2.1 上位机（Jetson）：改一个配置

文件：`autoaim/my_lf_INF_20261025/configs/standard3.yaml`

```yaml
# 改前

# 改后
three_order_enable: true    # 必须 true：下位机按 32 字节三阶帧解析（RECEIVE_DATA=32）
```

改完后上位机发送 `VisionToGimbal3`（32 字节）：

```
[0]     head = 0xFF
[1]     fire
[2:6]   yaw         (float, 度)
[6:10]  yaw_vel     (float, 度/秒)
[10:14] yaw_acc     (float, 度/秒²)
[14:18] pitch       (float, 度)
[18:22] pitch_vel   (float, 度/秒)
[22:26] pitch_acc   (float, 度/秒²)
[26:30] distance    (float, 米)
[30]    crc8 = 0
[31]    tail = 0x0D
```

**与下位机 `RECEIVE_DATA` 逐字节对齐**（已用 C 结构体验证）：

```
VisionToGimbal3 大小 = 32  == RECEIVE_DATA 大小 = 32
InputData 偏移 = 1，FrameTailer 偏移 = 30
上位机发送: yaw=68.75 pitch=-17.25 dist=2.5 fire=1
下位机读到: yaw=68.75 pitch=-17.25 dist=2.5 fire=1
帧尾: 0x0D
```

> ⚠️ **单位已核对**：下位机 `QuaternionEKF.c:217` 的 `YawTotalAngle = 360.0f * YawRoundCount + Yaw`，
> `Yaw`/`Pitch` 都乘了 `57.295779513f`（弧度转度），所以**下位机内部就是度**，
> 与三阶帧的"度"一致，不需要任何换算。
>
> ⚠️ 速度/加速度前馈系数 `KFF_VEL = 0.0f`、`KFF_ACC = 0.0f`，目前未启用，
> 所以 vel/acc 的单位即使有偏差也不会影响控制。

### 2.2 下位机：`application/Self_aim.c` 改成单一状态机

核心变化：**一段字节只解析一次**，由帧头决定进哪个分支。

```c
void process_usb_data_packet(uint8_t* data, uint16_t length)
{
    static uint8_t  buf[VIDEO_FRAME_BYTES];   /* 309，两路共用 */
    static uint16_t idx = 0;
    static uint8_t  kind = 0;                 /* 0=找帧头 1=视频 2=控制 */

    if (data == 0) return;

    for (uint16_t i = 0; i < length; i++) {
        uint8_t b = data[i];

        if (kind == 0) {
            if (b == VIDEO_SOF)          { buf[0] = b; idx = 1; kind = 1; }   /* 0xA5 视频 */
            else if (b == FRAME_HEADER_FF){ buf[0] = b; idx = 1; kind = 2; }  /* 0xFF 控制 */
            continue;
        }

        if (idx < VIDEO_FRAME_BYTES) buf[idx++] = b;

        if (kind == 1) {
            if (idx >= VIDEO_FRAME_BYTES) {                 /* 收满 309 */
                kind = 0; idx = 0;
                (void)VideoForward_PushFrame(buf);          /* 校验 + 入队 */
            }
        } else {
            if (idx >= CONTROL_FRAME_BYTES) {               /* 收满 32 */
                kind = 0; idx = 0;
                if (buf[CONTROL_FRAME_BYTES - 1u] == CONTROL_TAIL) {   /* 帧尾 0x0D */
                    memcpy(&inputdata, buf + sizeof(FrameHeader), sizeof(InputData));
                }
            }
        }
    }
}
```

**新增了帧尾校验**：只有最后一字节是 `0x0D` 才写入 `inputdata`。
即使发生错位，垃圾数据也不会进入云台，宁可某一帧不更新（云台保持上一目标），
也不会让云台跳到随机角度。

### 2.3 下位机：`application/video_forward.c` 去掉内部解析器

原来它自己也维护一个状态机，现在删掉，只保留"校验 + 入队 + 转发"：

```c
/* 旧接口 */
void VideoForward_Feed(const uint8_t *data, uint16_t len);   // 已删除

/* 新接口：喂**一整帧** 309 字节，返回 1 表示有效并入队 */
uint8_t VideoForward_PushFrame(const uint8_t *frame);
```

`VideoForward_Init()` / `VideoForward_Task()` / 三个计数器接口保持不变。

## 六、设计说明（为什么这么做）

**为什么用单一状态机而不是两个解析器？**
USB CDC 是字节流，没有消息边界。两个独立解析器各自找帧头，必然互相污染。
单一状态机保证每个字节只被一个逻辑消费一次，这是唯一正确的做法。

**为什么加帧尾校验？**
即使解析正确，串口也可能丢字节。没有校验时，错位的 32 字节会被当成合法指令；
有 `0x0D` 校验后，错位帧被丢弃，云台保持上一次目标，**行为可预测**。

**为什么宁可丢帧也不更新？**
丢一帧 = 云台目标晚 5ms 更新（上位机 200Hz 发送），几乎无感。
错误帧 = 云台跳到随机角度，可能打坏机械结构。
两害相权，丢帧远优于错帧。

**为什么要求分两步验证？**
协议问题和视频问题都会表现为"云台不正常"。
同时打开时无法区分，会浪费大量调试时间。先关视频验证云台，是成本最低的路径。
