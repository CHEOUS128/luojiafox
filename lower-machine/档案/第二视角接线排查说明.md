## 二、代码实际用的是哪个串口（已核对源码）

`application/video_forward.c` 第 25–26 行：

```c
extern UART_HandleTypeDef huart6;
#define VIDEO_VT03_HANDLE      (&huart6)
```

`Src/usart.c` 中 `MX_USART6_UART_Init()`：

| 参数 | 值 |
|---|---|
| 实例 | USART6 |
| 波特率 | **921600** |
| 数据位 | 8 |
| 停止位 | 1 |
| 校验 | 无 |
| 硬件流控 | 无 |

`Src/usart.c` 中 USART6 引脚复用：

```
PG14  ------>  USART6_TX   ← 视频数据从这里发出
PG9   ------>  USART6_RX   ← SBUS 遥控输入（remote_control.c 在用）
```

**结论：视频数据固定从 `PG14` 输出，921600 8N1。**

## 三、必须接的三根线

| STM32 端 | VT03 端 | 作用 | 是否必须 |
|---|---|---|---|
| **PG14**（USART6_TX） | **RX**（接收） | 视频数据 | ✅ 必须 |
| **GND** | **GND** | 共地 | ✅ 必须 |
| 5V / 12V | VT03 电源 | 供电 | 视 VT03 型号 |
| ~~PG9~~ | ~~TX~~ | 不需要接 | ❌ 可选 |

**⚠️ 最重要的一条：PG14 是"发送"，必须接 VT03 的"接收"（RX）。**

这是最常见的错误。如果接成 `PG14 → VT03 的 TX`，两边都在发送、都在等对方发，结果谁也收不到。

**⚠️ 第二条：必须有共地线。**
只接信号线、不接 GND，串口通常不通，或者时通时不通（表现为画面偶尔闪一下）。

## 四、如何确认接线真的对（三种方法，按可靠度排序）

### 方法 1：用示波器/逻辑分析仪量 PG14（最可靠）

**这是唯一能 100% 确定的方法。**

1. 机器人上电，Jetson 跑自瞄程序
2. 探头接 **PG14**，地夹接 **GND**
3. 观察波形

**正常应有的波形**：

| 特征 | 说明 |
|---|---|
| 空闲时高电平（3.3V） | 串口空闲状态 |
| 有密集的数据突发 | 每 25ms 左右一次，持续约 3.4ms |
| 突发长度约 309 字节 | 309 × 10 bit ÷ 921600 = 3.35ms |
| 波特率换算约 921600 | 一个 bit 约 1.08μs |

**如果 PG14 完全没有数据** → STM32 没在发，是固件问题（回来找我们）
**如果 PG14 有数据** → 数据发出去了，问题在接线或 VT03

### 方法 2：直接量 VT03 的 RX 脚

探头接 **VT03 模块上的 RX 引脚**（不是 STM32 的 PG14）：

- **有同样的波形** → 线接对了，问题在 VT03 配置
- **没有波形** → 线断了、接错脚、或者中间有转接板

**这一步能区分"STM32 没发"和"线没接对"。**

### 方法 3：万用表通断测试（最简单，不用示波器）

1. 断电
2. 万用表打到"蜂鸣/通断"档
3. 一根表笔点 **STM32 的 PG14 焊盘**，另一根点 **VT03 的 RX 引脚**
4. 听到蜂鸣 = 这根线是通的 ✅
5. 再量 **GND 到 GND** 是否通

**注意**：通断测试只能证明"线连着"，不能证明"接的是对的脚"。
如果 PG14 接到了 VT03 的 TX，通断也会响，但数据不通。

## 五、逐项排查清单

请按顺序确认，每一条打勾：

### □ 1. VT03 的 RX 到底接在哪个引脚？

**必须亲眼看到实物接线**，不要凭记忆。找到 VT03 模块，看它的线排：
- 哪根线是 RX（可能标 `RX` / `RXD` / `R`）
- 顺着这根线找到 STM32 板上的哪个焊盘/排针

**必须落在 PG14。** 如果落在别的地方，两种选择：
- 改线，挪到 PG14
- 或者告诉我们实际接在哪，我们改代码里的 `VIDEO_VT03_HANDLE`

### □ 2. 有没有接 GND？

STM32 的 GND ↔ VT03 的 GND，必须连通。

### □ 3. VT03 的波特率是多少？

查 VT03 说明书或型号。RoboMaster 图传发送端标准是 **921600**。

如果你们用的型号是 115200，需要告诉我们，我们改 `usart.c` 里的 `huart6.Init.BaudRate`。

### □ 4. USART6 是否被遥控占用冲突？

`remote_control.c` 里 `USART6_IRQHandler` 在用 USART6 的 **RX（PG9）** 接收 SBUS 遥控信号。

- **TX（PG14）和 RX（PG9）是独立的**，一个发一个收，理论上互不影响
- 但需要确认遥控是否真的在用 SBUS。如果遥控改用了 DBUS（USART3），USART6 的 RX 就是空的，更安全

**请确认：遥控器现在接的是 USART6（SBUS）还是 USART3（DBUS）？**

### □ 5. 线材质量

921600 是比较高的波特率，对线材有要求：
- 建议线长 **小于 30cm**
- 用**双绞线**或者至少是信号线 + 地线成对走
- 不要和电机线、电源线捆在一起走（干扰）

如果线很长（比如半米以上）且没有屏蔽，921600 可能误码率很高，表现就是画面卡顿或完全收不到。

## 六、如果接线全部确认无误，还是收不到

### 请读这三个计数器

在调试器里看（`video_forward.c` 内的 static 变量，或者通过接口函数）：

```c
VideoForward_GetForwarded()   // 成功转发给 VT03 的帧数
VideoForward_GetCrcError()    // 收到但 CRC 校验失败的帧数
VideoForward_GetOverflow()    // 队列溢出丢弃的帧数
```

让车跑 30 秒，然后看数值：

| 观察 | 含义 | 结论 |
|---|---|---|
| `forwarded` 持续增长（30 秒约 300） | STM32 收到了视频帧、CRC 正确、并且调用了 `HAL_UART_Transmit` | **问题在 PG14 之后的物理链路**（线、VT03、VT03 波特率） |
| `forwarded = 0`，`crcError = 0` | 一个 0xA5 帧都没收到 | **STM32 没从 USB 收到视频帧**，查 `usbd_cdc_if.c` 是否传了 `*Len` |
| `forwarded = 0`，`crcError` 在涨 | 收到字节流但 CRC 不对 | **帧被截断或损坏**，查 USB 接收是否丢数据 |
| `overflow` 在涨 | 队列满，转发太慢 | VT03 没在接收（HAL 超时）或波特率不对 |

### 还可以增加一个"心跳"测试

如果怀疑 PG14 到底有没有输出，让电控临时加几行调试代码：

```c
// 在 VideoForward_Task() 里，每转发一帧就翻转一个 LED
static uint32_t frame_count = 0;
frame_count++;
if (frame_count % 20 == 0) {
    HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);  // 用板载 LED
}
```

**每转发 20 帧 LED 翻转一次 = 2 秒翻转一次（10fps × 20 帧）。**
如果 LED 在闪，说明代码在跑、在调用发送；LED 不闪说明根本没走到这一步。

## 附：为什么不用 USART1（裁判系统）转发

有同学可能会问：能不能通过裁判系统的 USART1 转发？

**不能。** 原因：

| 串口 | 波特率 | 每秒可传字节 | 视频需求 |
|---|---|---|---|
| USART1（裁判系统） | 9600 | 约 960 B/s | **12,000 B/s** |
| USART3（DBUS 遥控） | 100000 | 约 10,000 B/s | 12,000 B/s（不够） |
| **USART6** | **921600** | **约 92,000 B/s** | 12,000 B/s ✅ 充裕 |

视频走裁判系统串口，带宽差 12 倍，物理上不可能。
这就是为什么必须单独用 USART6 直连 VT03。
