# 第一部分：先搞懂这条链路

## 1.1 视频从哪来，到哪去

```
  Jetson（上位机，视觉负责）
     │  工业相机 1280×1024
     │  缩放到 300×240，H.264 编码
     │  每帧装进 309 字节的 0x0310 包
     ▼
  USB 转串口（/dev/ttyACM0）           ← 这条线你已经在用了（云台控制也走它）
     ▼
  STM32 主控（电控，你负责）            ← 本手册的全部内容
     │  ★ 任务：认出来、别改、转发出去
     ▼
  USART6 → PG14 引脚，921600 波特率
     ▼
  VT03 图传发送端（车上）
     │  无线
     ▼
  VT13 接收端（操作间）
     ▼
  官方选手端
     │  MQTT 的 CustomByteBlock 频道
     ▼
  自定义客户端（按 H 键看）
```

## 1.2 你在这一段只需要做三件事

| # | 做什么 | 一句话解释 |
|---|---|---|
| 1 | **识别** | 从 USB 收到的字节流里，把 `0xA5` 开头的 309 字节视频帧单独挑出来 |
| 2 | **校验** | 检查这一帧没被破坏（CRC） |
| 3 | **转发** | 原样从 `PG14` 发出去，一个字节都不要改 |

**不要做的事**：不要解析 H.264、不要改 data 段、不要重算 CRC、不要改长度字段。

## 1.3 为什么要区分两种帧

USB 这条线上有两种东西混在一起（协议规定，不是我们自创）：

| 帧类型 | 帧头 | 长度 | 谁发的 | 用途 |
|---|---|---|---|---|
| 控制帧 | `0xFF` | 32 字节 | Jetson | 云台角度指令 |
| 视频帧 | `0xA5` | 309 字节 | Jetson | 图传画面 |

**靠帧头区分，这就是全部原理。**

# 第二部分：视频帧长什么样（协议原文）

## 2.1 外层：0x0310 帧

协议表 1-41 规定：命令码 `0x0310`，数据段长度 **300 字节**。
加上帧头帧尾，完整一帧是 **309 字节**。

```
偏移      长度    内容                          说明
[0]       1      0xA5                         帧头（SOF）
[1:3]     2      0x2C 0x01                    数据长度 = 300，小端
[3]       1      seq                          包序号 0~255 循环
[4]       1      CRC8                         前 4 字节的 CRC8
[5:7]     2      0x10 0x03                    cmd_id = 0x0310，小端
[7:307]   300    data                         视频数据（见 2.2）
[307:309] 2      CRC16                        前 307 字节的 CRC16，小端
```

> **CRC8 参数**：多项式 `0x8C`，初值 `0xFF`，覆盖 `[0]`~`[3]`
> **CRC16 参数**：多项式 `0x1189`，初值 `0xFFFF`，覆盖 `[0]`~`[306]`

## 2.2 内层：data 段的 300 字节

**你没有必要理解这一层**，只要原样转发。但知道结构能帮你排查：

```
data (300B) =
  [2B 内层长度，大端][2B 内层序号，大端][H.264 数据片段，≤296B]
  ...（剩余补 0）

内层长度 = 2 + 载荷长度，最大 298
```

## 2.3 我们代码里已经写好的部分

`application/video_forward.c` 已经包含完整的校验和转发逻辑，**你不需要改**。
需要确认的只有接线（第三部分）和编译烧录（第四部分）。

# 第三部分：接线（本手册最关键的部分）

## 3.1 必须接的三根线

```
┌────────────────────┐              ┌────────────────────┐
│    STM32 主控       │              │    VT03 图传发送端   │
│                    │              │                    │
│  PG14 (USART6_TX) ─┼──── 信号线 ──┼─→ RX               │  ← 必须
│                    │              │                    │
│  GND          ─────┼──── 地线 ────┼─→ GND              │  ← 必须
│                    │              │                    │
│  PG9  (USART6_RX)  │   （不接）    │    TX              │
│                    │              │                    │
│  5V / 12V     ─────┼── 供电线 ────┼─→ VCC              │  ← 看模块规格
└────────────────────┘              └────────────────────┘
```

## 3.2 三个最容易犯的错误

### ❌ 错误一：TX 接 TX（最常见）

`PG14` 是**发送**脚，必须接对方的 **RX（接收）**。

```
✅ 正确： STM32 PG14  →  VT03 RX
❌ 错误： STM32 PG14  →  VT03 TX     ← 两边都在发，谁也收不到
```

**这是 RoboMaster 队伍最高频的接线错误。接反了表现为"完全没反应"。**

### ❌ 错误二：没有共地

只接信号线、不接 GND，串口可能：
- 完全不通
- 或者时通时不通（画面偶尔闪一下）

**必须 STM32 的 GND 接到 VT03 的 GND。**

### ❌ 错误三：用了长线或劣质线

921600 波特率下，一个 bit 只有 **1.08 微秒**。

| 要求 | 说明 |
|---|---|
| 线长 | **≤ 30cm**，超过 50cm 风险很高 |
| 走线 | 不要和电机线、电源线捆在一起 |
| 类型 | 双绞线最佳；短距离普通杜邦线可以 |

## 3.3 用万用表验证（必须做）

**只靠肉眼看不出来，必须用万用表通断档验。**

### 第一步：断电

拔掉主控所有电源。

### 第二步：验证正确的连接

```
万用表打到 "蜂鸣 / 通断" 档
表笔 A → STM32 的 PG14 焊盘
表笔 B → VT03 的 RX 引脚
```

**听到蜂鸣 ✅ 说明接对了。**


**应该【不响】。如果响了 = 接反了 ❌，必须改线。**

### 第四步：验证共地

```

表笔 B → VT03 的 GND
```

**必须蜂鸣 ✅**

# 第五部分：验证视频链路

## 5.1 三个计数器（最重要的一步）

代码里有三个计数器，**接调试器或串口打印都能看**：

```c
VideoForward_GetForwarded()   // 成功转发给 VT03 的帧数

```

**让车跑 30 秒**，然后记录：

| 计数器 | 30 秒预期 | 实际读数 |
|---|---|---|
| Forwarded | 约 **300**（10fps × 30s） | ______ |
| CrcError | **0** | ______ |
| Overflow | **0** | ______ |

### 结果判读表

| 你的读数 | 说明 | 下一步 |
|---|---|---|
| Forwarded ≈ 300，CrcError = 0 | STM32 收到并正确转发了 | **问题在 PG14 之后的线或 VT03** → 看 5.2 |
| Forwarded = 0，CrcError = 0 | 一个视频帧都没收到 | USB 接收有问题 → 看 5.3 |
| Forwarded = 0，CrcError 在涨 | 收到了但校验失败 | 帧损坏 → 看 5.3 |
| Overflow 在涨 | 队列满了，转发太慢 | VT03 没接收 → 看 5.2 |

## 5.2 用示波器量 PG14（最可靠）

| 设置 | 值 |
|---|---|
| 探头 | PG14 |
| 地夹 | GND |
| 时基 | 10 ms/格 |
| 电压 | 1 V/格 |

**正常波形**：

```
     ┌──┐  ┌──┐        ← 每 25ms 一次数据突发
高 ──┘  └──┘  └── ...  ← 突发持续约 3.4ms
低
     │← 3.4ms →│← 21.6ms →│
     309字节@921600      等待下一帧
```

| 波形 | 结论 |
|---|---|
| 有密集方波突发，间距约 25ms | ✅ STM32 在正常输出 → 问题在接线或 VT03 |
| 完全没有波形 | ❌ STM32 没在发 → 回看 5.1 计数器 |
| 有波形但幅度不足 / 畸变 | ❌ 引脚配置或硬件问题 |

**没有示波器怎么办**：让视觉组在 Jetson 上抓 USB 串口数据，
确认 Jetson 端确实在发 309 字节帧（这一步他们可以独立完成）。

## 5.3 如果 Forwarded = 0

检查 `Src/usbd_cdc_if.c` 的 `CDC_Receive_FS`：

```c
static int8_t CDC_Receive_FS(uint8_t* Buf, uint32_t *Len)
{
  usbd_cdc_receive_handle(Buf, (uint16_t)(*Len));   // ← 必须这样写
  ...
}
```

**不能是**：
```c
memcpy(Usart_Receive,Buf,40);      // ❌ 写死 40 字节，视频帧 309 被截断
usbd_cdc_receive_handle();         // ❌ 不知道真实长度
```

## 5.4 已知的潜在问题（如果其他都对但还不通）

`MX_USART6_UART_Init()` 里注册了 **TX DMA**（`hdma_usart6_tx`），
而 `VideoForward_Task()` 用的是**阻塞式** `HAL_UART_Transmit`。

某些 HAL 版本下两者会冲突，`HAL_UART_Transmit` 返回 `HAL_BUSY`，帧发不出去。

**症状**：`Forwarded` 一直是 0，但 `CrcError` 也是 0（说明收到了帧，只是发不出去）。

**解决**（二选一，需视觉组确认后改）：

```c
// 方案 A：断开 DMA 关联
huart6.hdmatx = NULL;    // 放在 MX_USART6_UART_Init() 之后

// 方案 B：改用 DMA 发送
HAL_UART_Transmit_DMA(VIDEO_VT03_HANDLE, frame, 309);
```

# 第七部分：常见问题速查

| 现象 | 可能原因 | 怎么查 |

| 物理接口 | 波特率 |
|---|---|

“8 位数据位，1 位停止位，无硬件流控，无校验位。”

“机器人可以通过图传链路向自定义客户端发送自定义信息”
数据段：300 字节
注：“由于数据量较大，该协议无重传机制。”

**频率上限**（原文）：
“机器人发送给自定义客户端的数据，频率上限为 **50Hz**”
