## 二、每处改动的原因

### 2.1 `usbd_cdc_if.c`：USB 回调改用真实长度

**原来**：

```c
memcpy(Usart_Receive,Buf,40);
usbd_cdc_receive_handle();
```

问题：无论实际收到多少字节，都固定拷 40 字节，且函数不知道真实长度。
视频帧 309 字节 > 40，会被截断。

**现在**：

```c
usbd_cdc_receive_handle(Buf, (uint16_t)(*Len));
```

`*Len` 是 STM32 USB 库给出的实际接收字节数。**不再拷贝**，直接把 DMA/端点缓冲交给解析器，省一次 40 字节拷贝。

> `Usart_Receive[40]` 这个全局变量已经不再使用，但保留未删，避免影响其他地方（已确认没有别的引用）。

### 2.2 `Self_aim.c`：USB 数据分流

**原来**：

```c
void usbd_cdc_receive_handle(void)
{
    process_usb_data_packet(Usart_Receive, 40);
}
```

**现在**：

```c
void usbd_cdc_receive_handle(uint8_t *data, uint16_t length)
{
    if (data == 0 || length == 0) return;
    VideoForward_Feed(data, length);      /* 只认 0xA5 + 309 字节 */
    process_usb_data_packet(data, length); /* 只认 0xFF + 32 字节 */
}
```

同一批字节喂给两个独立状态机，各认各的帧头，互不干扰。

### 2.3 `Self_aim.c`：控制帧解析修正（**这处不只和图传有关**）

原实现有个真 bug：

```c
if (temp_received == sizeof(RECEIVE_DATA)) {
    memcpy(&inputdata, ...);
    temp_received = 0;
    return;          // ← 直接退出整个函数
}
```

**问题**：一次 USB 回调里如果包含多帧（或先有视频帧、后有控制帧），`return` 会把后面的字节全部丢掉。
USB CDC 是流式的，一次收到多帧很常见。

**修正**：把 `return` 改成继续循环（`temp_received = 0` 后接着解析剩余字节）。

这一条即使不开图传也是正确的修复——理论上现在的 32 字节控制帧也可能因为 USB 分包而被丢。

### 2.4 `Self_aim.c`：任务里调用转发

`Self_aim_task` 原本是 200Hz 循环，只做 `USART1_SEND()`。现在：

```c
void Self_aim_task(void const *pvParameters)
{
    VideoForward_Init();
    while(1)
    {
        USART1_SEND();
        VideoForward_Task();   /* 把队列里的视频帧发给 VT03 */
        osDelay(5);
    }
}
```

`VideoForward_Task()` 每次最多发一帧 309 字节（约 3.4ms @921600），
每秒最多 40 帧，不会把 200Hz 任务拖垮。

### 2.5 `video_forward.c`：核心逻辑

**解析**：逐字节扫描，遇到 `0xA5` 开始收集，收满 309 字节校验一次。
一旦开始收集就**不再找帧头**（视频数据里可能含 0xA5/0xFF），收满后再继续找下一帧。

**校验**（任一不过就丢弃并计数）：

- 帧头 `0xA5`
- 长度字段 = 300（`0x2C 0x01`）
- cmd_id = `0x0310`（`0x10 0x03`）
- CRC8（前 4 字节，查表法，初值 0xFF）
- CRC16（前 307 字节，查表法，初值 0xFFFF，小端存放）

**转发**：校验通过 → 入队（深度 8）→ `HAL_UART_Transmit` **原样**发到 VT03。
队列满时丢最老的帧（保证延迟不累积），并计数。

**不修改任何字节**：不重算 CRC、不改长度、不动 data 段。

> CRC 表说明：模块内置了与视觉端 `autoaim/.../tools/crc.cpp` 完全一致的两张表。
> **没有**使用工程里的 `CRC8_CRC16.c` ——那边小写的 `wCRC_table` 实测与标准表不一致（只有第 0 项相同），
> 用它校验会全部失败。工程自己的协议不受影响，无需修改。

## 三、需要电控确认的唯一硬件问题：VT03 接在哪

### 3.1 现状（已核对源码）

| UART | 波特率 | 引脚 | 当前代码用途 |
|---|---|---|---|
| USART1 | 9600 | PB7(RX) / PA9(TX) | 裁判系统 |
| USART3 | 100000 | PC11(RX) / PC10(TX) | 遥控 DBUS（偶校验） |
| **USART6** | **921600** | PG14(TX) / PG9(RX) | **SBUS 遥控**（`remote_control.c` 里 `USART6_IRQHandler` + DMA） |

`usart.c` 里 USART6 已经是 **921600**，正好是 VT03 的标准波特率。
而且 `MX_USART6_UART_Init()` 配了 TX（PG14）和 **TX DMA**，可以直接发。

### 3.2 当前代码默认值

```c
extern UART_HandleTypeDef huart6;
#define VIDEO_VT03_HANDLE      (&huart6)
```

### 3.3 请按实物确认

| 情况 | 处理 |
|---|---|
| **A. VT03 接 USART6（PG14），且遥控不再用 SBUS** | 代码不用改。但要确保 `remote_control.c` 里的 USART6 接收不会干扰——目前它只做接收和空闲中断，TX 不冲突，**可以共存** |
| **B. VT03 接 USART6，但遥控还在用 SBUS** | TX/RX 是独立的：SBUS 只用 RX（PG9），视频只用 TX（PG14），**理论上可以共存**。但 SBUS 的 DMA 空闲中断会频繁触发，需实测确认不影响视频发送 |
| **C. VT03 接其它 UART** | 改 `video_forward.c` 顶部的 `VIDEO_VT03_HANDLE`，并确认该 UART 已初始化、波特率 921600 |

> 最省事的判断：**看 VT03 模块的 RX 线接到 STM32 哪个脚**。
> 如果接在 PG14（USART6_TX），代码一个字都不用改。

## 七、可能的坑与排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `s_crc_error` 一直涨 | CRC 表不对 / 帧被截断 | 确认用的是 `video_forward.c` 内置表，不要替换成 `CRC8_CRC16.c` 的实现 |
| `s_forwarded = 0`，`crc_error = 0` | 没收到 0xA5 / 没收到数据 | 检查 `CDC_Receive_FS` 是否已改成传 `*Len` |
| `s_overflow` 增长 | VT03 发送太慢 / 波特率不对 | 确认 VT03 串口 921600；检查 `HAL_UART_Transmit` 返回值 |
| 客户端花屏 | 帧被破坏 | 检查是否有人对 data 段做了“整理”；确认是原样透传 |
| 云台异常 | 视频帧被控制帧解析器吞了 | 确认 `process_usb_data_packet` 已改成不 `return` 的版本 |
| 遥控失灵 | USART6 冲突 | 见第三节，改用其它 UART 或在实测确认后共存 |

## 九、设计取舍说明（为什么这么做）

**为什么不直接解析视频、只做透传？**
主控没有硬编码理由去理解 H.264。理解得越少，出错概率越低。只做“找帧头 + 校验 + 原样发”。

**为什么用队列而不是在中断里直接发？**
USB 回调在中断上下文，`HAL_UART_Transmit` 会阻塞（309 字节约 3.4ms），
在中断里阻塞会拖慢 USB 接收、甚至触发端点溢出。所以解析在回调里，发送在任务里。

**为什么队列满要丢最老帧？**
视频是实时流，丢新帧会让画面越来越旧。丢最老帧保证“看到的永远是最新画面”。

**为什么单独拷一份 CRC 表？**
工程 `CRC8_CRC16.c` 的小写 `wCRC_table` 与标准表不一致（实测第 1~255 项全部不同），
复用它会让所有视频帧校验失败。新模块自带表，不影响工程原有的裁判系统协议。
