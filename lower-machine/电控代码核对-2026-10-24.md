## 十二、第三轮抓包 + 固件补丁（10-24 傍晚，当前）

### 12.1 拔掉 VT03 之后的抓包：尾巴整段没了

`listen0310_COM7_20261024_162026.bin`（60 秒，CH340 只挂板子的 TXD + GND）：

| 项 | 数值 |
|---|---|
| 收到字节 | 9,442 |
| 0xA5 总数 | 68（34 个帧头 + 34 个在 H.264 负载里的 0xA5） |
| `A5 2C 01` 且 cmd=`10 03` | **34 个** |
| 其中 CRC8 正确 | **34 / 34**（0 个 CRC8 错） |
| **H.264 负载完整** | **33 / 34**（只有第 8 帧缺尾） |
| 每帧短少 | **16 ~ 74 字节**（中位 29），**没有一个超过 74** |

把每帧按「内层声明的长度」切开，逐个看缺在哪：

```
帧头在、内层长度对、payload 一字不差、payload 最后一个非零字节之后 → 直接跳到下一个 A5
```

也就是**缺的永远是 payload 之后的那一截：零填充 + 2 字节 CRC16**。
53 份历史抓包里都一样（12:37 那 11 帧、12:38 那 21 帧，短少范围也都是 15~74）。

**为什么这不像「线上随机丢字节」**：随机丢字节应该把**非零**的 H.264 数据丢掉、把零保留下来；
现在正好相反 —— 非零的一个不丢，全零的整段消失。这是**被切掉**，不是**被丢掉**。

### 12.2 还剩两种可能，计数器一次分开

| # | 谁把尾巴吃了 | 如果是它，会看到什么 |

| A | **STM32 根本没发完**：`HAL_UART_Transmit` 中途返回 `HAL_BUSY`/`HAL_TIMEOUT`，`VideoForward_Task` 当没事发生、静默走人 | `s_forwarded` 涨得慢，`s_tx_error` 同步涨，`s_tx_stuck` > 0 |

## 九、决定性实测：板子在发真视频帧，只是被截短了

### 9.1 抓包内容

60 秒、CH340 直接并到板子的 3pin 数据线上（不经 VT03），共 5,687 字节、
**21 个帧头**、20 个完整帧间隔。

```
0000  A5 2C 01 D5 40 10 03 00  F5 45 D5 00 00 00 01 67   ← A5 2C 01 = 架构对
0010  42 C0 0B DC 28 56 84 00  00 03 00 04 00 00 03 00   ← 67 42 C0 0B DC 28 = 真 H.264 SPS
```

逐条验：(1) `A5 2C 01` 对；(2) `10 03` = cmd 0x0310 对；(3) 序号 `D5 40` =
CRC8(`A5 2C 01 D5`) 对；(4) data 区 `00 F5` = 内层长度 245，`45 D5` = 内层序号
17877 —— 和 Jetson 的 `成帧` 计数吻合；(5) data[2..5] = `00 00 00 01`，data[6] = `67`。

**结论：板子的 USB 接收、0x0310 封装、CRC 计算、USART6 发送全程正确。**

### 9.2 唯一的异常：每帧都少几十字节

| 项 | 数值 |
|---|---|
| 帧间隔 | 中位 **278** 字节（应 309），范围 238~291 |
| 每帧缺失 | 18~71 字节（平均 31） |
| 数值变短的原因 | 是**内层包本身**变短了（233~261 字节），不是丢在一帧的固定位置 |
| 60 秒总收 | 5,687 字节（应约 21 帧 × 309 ≈ 6,489 字节，约 88%） |

缺失位置不固定、每帧都缺一点，**不像固定的 64 字节 USB 整包丢**，更像
**CH340 在高波特率下按字节丢**（CH340 在 921600 本来就勉强），或者它自己缓冲溢出。

### 9.3 这个现象**不能**反过来推 STM32 的 USB 接收

抓包是接在 **STM32 的串口输出线**上的，所以「帧变短」只说明 **TX 线路上丢了字节**，
跟 STM32 从 USB 收到了什么**是两件事**（USB 侧丢字节的话，CRC16 校验不过，那一帧根本不会上线，
线上就只剩别的完整帧，不会表现出「每帧都缺一点」）。
所以 USB 侧现在既没被证明有问题，也没被排除。

### 9.4 为什么「21 帧 / 60 秒」不能算板子的账

内层序号从 17877 走到 18143，说明这 60 秒里 Jetson 一共喂了 **266 帧**，
而 CH340 只看到 21 帧（7.9%），每帧还少 10% 的字节。

**但「CH340 驱动溢出」这个解释现在站不住**：用抓包里各帧的内层长度反推，
**平均每 4 个帧头才留下 1 个**；而每帧缺的字节（中位 31B）远小于丢掉的帧数。
缓冲溢出应该是「成片地少收几个帧头」，且丢得越狠帧内缺得越多，两者比例对不上。
所以更可能是**这根线上真的在丢**（接触/共地/长线/两端同时驱动）。
测量工具本身的局限是另一层，混在一起，暂时分不开。

**要分清只有一条路**：让 STM32 自己说（见 9.6 的计数器）。

### 9.5 那客户端为什么一条都没有

板子 60 秒里确实往 3pin 的 TXD 上发了 21 个帧头/帧，客户端是 **0 条**。
两种可能，现在还没法分开：

1. **VT03 根本没往无线里转** —— 线在 VT03 那一端接错了脚 / VT03 的串口输入不是 921600 /
   VT03 只转官方格式。11:15 那次灌包证明「VT03 收得到就能转得到」，
   但那次是**定长内层 298**，这次是**变长**，形状不一样。
2. **VT03 转出去了，但客户端把包丢了** —— 客户端解析器 `unpack_transport_packet_spans()`
   在结构不对时是**整包抛异常**（不是跳过），所以只要被打包成一次多包/截断，就一条都不剩。

这正好是**实验三**要区分的东西：同样的线、同样的 VT03、同样的灌包方式，
只把「内层长度」从 298 改成 STM32 的真实值（233~261）。

### 9.6 下一步

## 十、实验三：把 STM32 的真实形状灌进 VT03（现在做这个）

### 10.1 为什么是这个实验

已知：

| 实验 | 走的路径 | 内层长度 | 客户端结果 |
|---|---|---|---|
| 11:15 灌包 | PC → CH340 → VT03 → … → 客户端 | **恒定 298**，内容是 `RM26` 假数据 | **281 条，全通** |
| 板子实时 | Jetson → STM32 → VT03 → … → 客户端 | **233~261 变化**，内容是**真 H.264** | **0 条** |

两条路径之间**只差两个变量**：内层长度变不变、内容是不是真 H.264。
实验三把「真 H.264 + 变化长度」按板子的形状灌进去，就把变量压到一个：

- **通了** ⇒ VT03/客户端这一跳对形状无所谓 ⇒ 问题在 **STM32 实际发出了什么**

- **不通** ⇒ **VT03 或客户端对变长内容有意见** ⇒ 那就把 Jetson 的每一包统一补零到
  **恒定 298**（改一行，且 11:15 已验证这个形状能过整条链）。

### 10.2 样本是怎么来的

`诊断工具\H264镜头样本.bin`：从 **12:38 那份抓包**里直接抠出来的 21 帧真 H.264

233, 236, 244, 245, 246, 247, 249, 250, 251, 252, 256, 257, 261。

### 10.5 顺带确认的一件事：客户端解包是**大端**

我把客户端的 `custom_byte_block_video_decoder.cpp` 逐行对了一遍：

std::uint16_t read_u16_be(const std::uint8_t *input) {   // ← BE

constexpr std::size_t kMaxInnerPacketBytes = 300 - 2;     // = 298

## 八、开发板 C 型手册原文（决定性）：丝印 UART1 = STM32 的 UART6

`RoboMaster 开发板 C 型用户手册.pdf`（`小改电控代码` 目录下）两处原文：

> 开发板集成了 2 路 UART 接口，映射到 STM32 的 UART1 与 UART6。其中 UART1 为 **4-pin** 对外接口，
> UART6 为 **3-pin** 对外接口……

> • 需要注意，UART6 接口线序与裁判系统电源模块一致，因此开发板与电源模块通信时需要将线材的 TX 与 RX 线序交叉；
> • **开发板的外壳丝印（UART1 与 UART2）与 STM32 的实际串口配置并不对应，外壳丝印 UART1 对应
>   STM32 的 UART6，外壳丝印 UART2 对应 STM32 的 UART1。**

结论：**代码里的 `huart6` 是对的，它物理上就是板上丝印 `UART1` 那个 3pin 口。**

两边说的其实是一回事，只是命名的层不一样，别再来回改：

| 说法 | 指的东西 |
|---|---|
| 板子上丝印 **UART1**（CH 看到的，3pin） | = STM32 的 **USART6**（PG14/PG9）= 代码里的 `huart6` ✅ |
| 板子上丝印 **UART2**（4pin） | = STM32 的 **USART1**（PA9/PB7）= 代码里的 `huart1` |
| 电控说的「UART1 是 4pin」 | 他按 **STM32 侧**命名，指的就是上表第二行那个 4pin |

手册附表的对应关系也是这么写的：`UART 接口（3-pin）→ UART6_TX PG14 / UART6_RX PG9`，
`UART 接口（4-pin）→ UART1_TX PA9 / UART1_RX PB7`。

### 8.1 3pin（板上丝印 UART1 = STM32 USART6）引脚顺序

```text
3pin : 1 = GND | 2 = TXD（板子发出去）| 3 = RXD（板子收进来）
4pin : 1 = RXD | 2 = TXD | 3 = GND   | 4 = 5V
```

视频是「板子发 → VT03 收」，所以 **板子的 2 号脚（TXD）必须进 VT03 的 RXD**。

### 8.2 手册明确写的坑：TX/RX 必须交叉

> • 需要注意，**UART6 接口线序与裁判系统电源模块一致，因此开发板与电源模块通信时需要将线材的 TX 与 RX 线序交叉**；

直连的话就是 TXD 对 TXD，两边都在发，谁都收不到。**这是现在的头号嫌疑。**

### 8.3 为什么「平时图传正常」不能证明这根线是通的

日常用的图传是相机 → VT03 → 无线 → VT13 → 选手端，**根本不走这根串口线**。
所以那根串口线（板子 TXD → VT03 RXD）以前从来没被真正用过，接反了也看不出来。

### 8.4 下一步就一件事

让电控把 3pin 的 **2、3 脚对调**（或者确认 VT03 的 RXD 确实接在板子的 2 号脚上），
然后开客户端按 H 看画面。**这是免费、可逆、两分钟的事**，比改固件快得多。

如果对调后仍然黑屏，再让电控加计数器打印（见 7.4），区分是「板子没收到」还是「收到了没发出去」。

## 三、最可疑的点：UI 和视频抢同一个 USART6 发送

新版比仓库原来的代码多了两样东西：

1. `my_UI/RM_Cilent_UI.c` —— 通过 **0x0301** 在客户端画图，注释写明「经 USART6 DMA 发送」；
2. `bsp_usart.c` 新增 `usart6_tx_dma_enable()`，且 `stm32f4xx_it.c` 里补了 `DMA2_Stream6_IRQHandler`。

**它们和视频用的是同一个 USART6、同一个 DMA2_Stream6。**

现在仓库版里 UI 的调用方 `referee_usart_task` 是被注释掉的：

```c
// osThreadDef(REFEREE_UART_TASK, referee_usart_task, osPriorityNormal, 0, 256);
// can_task_handle = osThreadCreate(osThread(REFEREE_UART_TASK), NULL);
```

如果电控在新版里把它打开了，那么 referee 任务每 **1 秒**会调两次 `UI_ReFresh`，
每次都 `usart6_tx_dma_enable()`：

```c
__HAL_DMA_DISABLE(&hdma_usart6_tx);          // ← 正在发的视频帧被直接掐断
while (hdma_usart6_tx.Instance->CR & DMA_SxCR_EN);
```

同时 `VideoForward_Task` 每 5ms 用 `HAL_UART_Transmit`（阻塞轮询）发 309 字节，
两者都没有互斥。**结果就是视频帧被反复截断，VT03 收到的是残帧 → 全部丢弃。**

`bsp_usart.c:108` 在 `usart6_init()` 里还给 TX DMA 设了 `PAR = &USART6->DR`、`M0AR = NULL`、`NDTR = 0`，
意思也是「既然用了 DMA 输出，轮询发送就靠边站」。

> 这一条是**推断**，不是已确认。仓库里 UI 是关的；需要看电控手上那份 `freertos.c` 到底打没打开这个任务。

- VT03 的 TX 线是不是真的接在 **PG14**（USART6_TX）。
- VT03 和 SBUS 遥控接收机是不是抢同一个引脚（两个都往 PG14 发 → 一定会打出乱码）。
- 用示波器/逻辑分析仪量 PG14，看有没有 309 字节的 0xA5 帧。
