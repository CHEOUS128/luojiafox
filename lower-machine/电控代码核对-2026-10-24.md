# 电控代码核对 + 10-24 实测结果（2026-10-24）

> **最新结论（10-24 下午）**：板子丝印的图传接口是 **UART1**，而固件把视频发在 **USART6(PG14)**。
> 两个不是同一个物理口 ⇒ 683 包全发到了没人接的引脚上，所以在图传口听 60 秒是 0 字节。
> 已把 10.24 那份代码改成 `&huart1` + USART1 921600，等烧录验证。详见「六」。

## 六、端口不一致（当前头号结论，未烧录验证）

### 6.1 事实

| 项 | 值 |
|---|---|
| 板子上图传链路的接口丝印 | **UART1**（集成板，只有一个 3pin 座） |
| 固件 `video_forward.c` 发的口 | **USART6 / PG14**，921600 |
| 固件 USART1 | PA9(TX)/PB7(RX)，**9600**（裁判系统） |
| 固件 USART3 | PC10(TX)/PC11(RX)，100000 + 偶校验（DBUS） |
| 在图传口用 CH340 听 60 秒 | **0 字节** |

`video_forward.c` 的注释本身就写明了前提：「**If VT03 is wired to USART6**…」。
集成板上 PG14 上没接图传，那就一个字节都到不了 UART1 座。

### 6.2 已做的改动（`10.21-2\26赛季全向轮步兵\gimbal_project`）

```c
// application/video_forward.c
extern UART_HandleTypeDef huart1;
#define VIDEO_VT03_HANDLE      (&huart1)

// Src/usart.c  MX_USART1_UART_Init()
huart1.Init.BaudRate = 921600;   // 原 9600
```

USART1 上没有别的发送者（`usart1_tx_dma_init` 没被调用、`sbus_to_usart1` 的调用点是注释掉的、
`referee_usart_task` 在 freertos.c 里是注释掉的），所以不会和视频抢。

### 6.3 试验顺序

1. **先看 Jetson 成帧在不在涨**（不涨就是根本没发，跟端口无关 —— 10-23 踩过这个坑）
2. 烧 `&huart1` 版 → 在图传口 `listen0310.bat COM7 -Seconds 60`
3. 有帧 ⇒ 口就是 UART1，改动定下来
4. 还是 0 字节 ⇒ 换 `&huart3`（要同时把 `MX_USART3_UART_Init` 改成
   `BaudRate=921600 / Parity=UART_PARITY_NONE`）再烧一次；USART6 已经排除过，不用再试

> 这份测试固件会占掉 USART1（裁判系统）和 USART3（DBUS），**只能台架测，别上场**。

### 6.4 关于「9 针裁判系统口」

协议表 1-1 要求「图传发送端←→机器人 **921600**」。如果集成板的 UART1 座其实是指 9 针裁判系统口，
那上面就应该能直接出 921600 的裁判系统数据。用 CH340 听那个 9 针口（只接 GND + 数据），
**能收到东西 ⇒ 那是 921600 的图传口；收不到 ⇒ 它是 115200 的电源管理口，不是我们要的**。
这条能一次分清，不用烧固件。

用 CH340 从 PC 直接灌进 **VT03 的 RX**（跳过 STM32），约 300 帧 @5Hz、921600 8N1。
客户端会话 `luojiamaster/程序/logs/20261024_111519_702`：

| 判据 | 结果 |
|---|---|
| `CustomByteBlock` 条数 | **281**（发了约 300 帧，93.7%） |
| 负载长度 | **300 字节 × 281**，无一例外 |
| 内层序号 | **0 → 280，无缺口、无重复、无乱序** |
| 负载内容 | 与 `inject0310.ps1` 重建的帧**逐字节一致**（281/281） |

有帧就说明 STM32 在发且线通，没有就往回查。

## 一、实测结果：Jetson 发了 683 帧，客户端收到 0 条

Jetson 日志：`成帧` 2780 → 3463，约 2 分钟内发了 **683 帧**（≈4.8 帧/秒，每帧 ≤296 字节）。

对应客户端会话 `luojiamaster/程序/logs/20261024_102425_614/network_capture.bin`（10:24:25–10:26:11）：

| 项 | 数值 |
|---|---|
| `CustomByteBlock`（客户端收到的） | **0 条** |
| `RobotDynamicStatus` | 802 条（≈11 条/秒） |
| `GameStatus` 等其余 17 个主题 | 各 81 条（≈1 条/秒） |
| UDP 官方视频 `video-stream` | 62235 包 |

另一个会话 `20261024_101759_383`（10:17–10:21，187 MB）也是 `CustomByteBlock = 0`。

作为对照，历史上真的收到过 0x0310 的会话：
`20261021_212133_501` → 9 条、`20261022_163900_759` → 4 条（都是真 H.264，但通过率 0.16%–0.64%）。

**结论：客户端在正常连、正常订阅、正常收别的主题；不是客户端的问题，也不是 MQTT 的问题。**
0x0310 这一路是从 `选手端 ← 无线 ← VT03 ← STM32` 中某处断掉的。

## 三、最可疑的点：UI 和视频抢同一个 USART6 发送

新版比仓库原来的代码多了两样东西：

1. `my_UI/RM_Cilent_UI.c` —— 通过 **0x0301** 在客户端画图，注释写明「经 USART6 DMA 发送」；
2. `bsp_usart.c` 新增 `usart6_tx_dma_enable()`，且 `stm32f4xx_it.c` 里补了 `DMA2_Stream6_IRQHandler`。

**它们和视频用的是同一个 USART6、同一个 DMA2_Stream6。**

现在仓库版里 UI 的调用方 `referee_usart_task` 是被注释掉的：

```c
// osThreadDef(REFEREE_UART_TASK, referee_usart_task, osPriorityNormal, 0, 256);
// can_task_handle = osThreadCreate(osThread(REFEREE_UART_TASK), NULL);
```

如果电控在新版里把它打开了，那么 referee 任务每 **1 秒**会调两次 `UI_ReFresh`，
每次都 `usart6_tx_dma_enable()`：

```c
__HAL_DMA_DISABLE(&hdma_usart6_tx);          // ← 正在发的视频帧被直接掐断
while (hdma_usart6_tx.Instance->CR & DMA_SxCR_EN);
```

同时 `VideoForward_Task` 每 5ms 用 `HAL_UART_Transmit`（阻塞轮询）发 309 字节，
两者都没有互斥。**结果就是视频帧被反复截断，VT03 收到的是残帧 → 全部丢弃。**

`bsp_usart.c:108` 在 `usart6_init()` 里还给 TX DMA 设了 `PAR = &USART6->DR`、`M0AR = NULL`、`NDTR = 0`，
意思也是「既然用了 DMA 输出，轮询发送就靠边站」。

> 这一条是**推断**，不是已确认。仓库里 UI 是关的；需要看电控手上那份 `freertos.c` 到底打没打开这个任务。

### 1. 问电控三个问题（一句话一个）

1. **`referee_usart_task` 打开了吗？**（新版 `freertos.c` 里那两行 `osThreadDef(REFEREE_UART_TASK, ...)` 是不是被取消注释了）

3. **SBUS 遥控接收机还在用 USART6 吗？**（`remote_control.c:148` 的 `USART6_IRQHandler` 是 SBUS 的接收中断）

### 2. 做一次「关掉 UI」的对照实验（5 分钟）

在电控的工程里，把那两行注释**保持注释**（或者临时注释掉 `referee_usart_task.c` 里的 `UI_ReFresh` 调用），重新烧录，
然后：

```bash
# Jetson 上
grep -a "1包/帧" ~/my_lf_INF_20261025/logs/autostart.log | tail -n 3
```

```powershell
# 客户端正常打开跑 60 秒，退出后在诊断工具目录
python rm0310.py dump "C:\Users\CH\Desktop\robot记录\luojiafox\luojiamaster\程序\logs\<最新会话>\network_capture.bin"
```

- `CustomByteBlock` 有数了 → **就是 UI 抢 DMA 造成的**，进第 3 步。
- 还是 0 → 不是软件问题，进第 3 步的硬件检查。

### 3. 如果 UI 必须留着（要画弹道/准星）

把视频转发也从轮询改成 DMA，两者共用一个 TX DMA 通道（同一时刻只允许一帧在发），
或者把 UI 挪到另一个空闲串口。**这属于改电控代码，等电控自己改，我们不动 STM32。**

### 4. 如果关掉 UI 后还是收不到，查硬件

- VT03 的灯：**绿 1Hz = 已连上接收端**；红 = 没对上频；蓝 = 对频中；紫 = 没激活。
- VT03 的 TX 线是不是真的接在 **PG14**（USART6_TX）。
- VT03 和 SBUS 遥控接收机是不是抢同一个引脚（两个都往 PG14 发 → 一定会打出乱码）。
- 用示波器/逻辑分析仪量 PG14，看有没有 309 字节的 0xA5 帧。
