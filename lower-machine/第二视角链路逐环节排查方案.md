## 零、先明确一件事：我们到底在验什么

### 0.1 链路与已验/未验

```
大恒相机 → Jetson 编码 → USB CDC → STM32 → UART 921600 → VT03 →⋆无线⋆→ VT13/选手端 → MQTT → 客户端
   ✅?        ✅            ✅        ✅         ✅           ❓        ✅           ✅       ✅
```

| 跳 | 证据 | 结论 |
|---|---|---|
| ① 相机 → Jetson 编码 | 日志 `[VideoSender] 已启用（300x240 @10fps 90kbps）`，无"串口写失败" | ✅ |
| ② Jetson → STM32 USB CDC | Jetson 侧 `try_send_raw()` 未报错 | ✅ |
| ③ STM32 收帧/校验 | 调试计数 `Forwarded` 在涨，`CrcError = 0` | ✅ |
| ④ STM32 → VT03 的 **UART 发出** | `Forwarded` 增长 = `HAL_UART_Transmit()` 返回 `HAL_OK`（能写到 PG14 的 DR，DMA/寄存器层面成功） | ✅ 但只到"芯片认为发出去了" |
| ⑤ **VT03 无线 → VT13 → 选手端** | 协议规定应该转发；实测 `mqtt_probe.py` 60 秒 **0 条** | ❌ **唯一断点候选** |
| ⑥ 选手端 → MQTT → 客户端 | probe 能连、能订阅；客户端的血量/状态正常 | ✅ |
| ⑦ 客户端解码/显示/H 键切换 | 模拟器画面正常 | ✅ |

> 注意区分两件事：**官方图传画面正常**（VT03 自己的相机 → 无线 → VT13 → 选手端）
> 只证明无线 + 接收端 + 视频链路好；它**完全不经过 UART**，所以对我们这条链路没有任何证明力。

### 0.2 关键事实（都已在源码/协议里核实，不是推测）

1. **协议表 1-41**：0x0310 = 300 字节 data，**上限 50Hz，无重传**；
   **表 1-1**：图传发送端 ←→ 机器人 的串口是 **921600 8N1**。
   → 所以 40Hz × (309 字节) = 12.4 kB/s ≈ 124 kbps，远低于 921.6 kbaud（92 kB/s）。
     **"STM32 发的太快、UART 塞不下"这个猜测不成立。**
2. **单包没有端到端校验**：309 字节外层的 CRC8/CRC16 在 STM32 那一跳就校验并剥掉了；
   进入 CustomByteBlock 的是裸 300 字节。
   → **"客户端收到了 CustomByteBlock"不等于"包是对的"**，唯一证据是内层序号连续。
3. **客户端只认 300 字节**：`custom_byte_block_video_decoder.cpp:8`
   `kMaxSupportedPacketBytes = 300`；`should_try_transport_first()` 只在包长 300 时走 transport 解析。
   → 如果 VT03 把 309 字节原样透传，客户端会**直接丢弃**；但 RoboGo 的抓包文件仍会记下 `309`。
     这个长度数字本身就是判断依据。
4. **内层长度不能超过 298**（`custom_byte_block_video_decoder.cpp:100-105`），
   且长度 0 之后的字节必须全 0。
5. **VT03 自己的串口每 14ms 输出 21 字节遥控帧**（说明书第 15 页，`0xA9 0x53` 开头）。
   这是"VT03 活着 + 已对频 + 你的 PC 真的接在它引脚上"的**免费探针**——不用额外仪器。
6. **协议原文（1.3 节）**：*"图传链路由裁判系统选手端和图传模块进行数据转发，
   **从图传模块（发送端）的串口接收数据**"*；**表 1-1** 又规定"图传发送端←→机器人 921600"，
   且串口性质为 **8 数据位 / 1 停止位 / 无校验 / 无硬件流控**。
   → 也就是说：**机器人从串口发给"图传发送端"的裁判系统帧，由发送端经无线转发出去**，
     这是协议规定的系统行为。我们让 STM32 往 VT03 的 RX 发 309 字节 0x0310 帧，方向是对的。
7. 但是：**VT03 的产品说明书只描述了 21 字节遥控帧，没有写"会解析/转发 0x0310"**。
   官方图传画面走的是 VT03 自己的相机（内部链路），**不经过 UART**。
   → 所以"官方图传画面正常"只能证明 **无线 + 接收端 + 选手端视频** 是好的，
     **完全不能**证明 UART 这一侧。协议说它应该转发，说明书没写 —— 这正是必须实测的原因。
8. **STM32 的 USART6 是收发都在用的**：`RC_Init()`（`bsp_rc.c`）给 USART6 开了 **RX DMA + IDLE 中断**，
   PG9 接的是 **SBUS 遥控接收机**，PG14 才是接 VT03 的 TX。
   → 所以 **VT03 的 TX 绝对不能接到 PG9**（会和 SBUS 抢同一根线）。
   → 另外 `RC_unable()` / `RC_restart()`（会 `__HAL_UART_DISABLE`）**在全工程里没有任何调用**
     （`detect_task.c` 里对应的钩子是注释掉的），可以排除"SBUS 掉线把串口关了"这条嫌疑。

|---|---|---|
| 紫 常亮 | 未激活 | 需要 DJI Assistant 2 激活 |
| 紫 1Hz | 未启动 | |

**判读**：

- 红 / 蓝 → 先解决对频；这一步没绿，后面所有实验都白做。
- 紫 → VT03 没被主控/裁判系统激活，先解决激活。

同时请录像确认：**VT03 上电、对频、插好线之后，无人碰车的情况下，官方图传画面正常**（已知正常，用来确认 VT13 侧没问题）。

说明裁判系统认为 VT03 **不在线 / 安装不规范**（`RobotModuleStatus.video_transmission`：0=离线，1=在线，2=安装不规范）。
正常比赛时这一行**不应该出现"图传"**。这是一秒钟就能看到的旁证，和灯是互相印证的关系。

## 二、需要准备的硬件（一次买齐，后面都要用）

| 物品 | 规格 | 用途 |
|---|---|---|
| USB-TTL 模块 | CH340 / CP2102 / FT232 都行，**必须能选 3.3V 电平** | 扮演 STM32 / 扮演接收端 |
| 杜邦线 | 母-母、公-母各若干 | 接 VT03 的 3pin UART |
| 万用表 | 带通断档 | 量线序、量共地 |
| （可选）示波器 / 逻辑分析仪 | ≥1MHz | 量 PG14 波形（最硬的证据） |

⚠️ **三条安全底线，务必先读**：

1. **VT03 的 UART 是 3.3V 电平**。USB-TTL 跳到 **3.3V**，**绝对不要用 5V 打到 VT03 的 RX**。
2. **VT03 必须用它自己的 12V 供电**。**不要**用 USB-TTL 的 5V 给它供电（电流也不够）。
3. 做"电脑扮演 STM32"的实验时，**必须先把 STM32 的 PG14 从 VT03 的 RX 上拔掉**。
   两个发送端顶在一根线上，会互相打架，结果不可信，严重时可能损伤引脚。

VT03 的 UART 接口是 3 pin：**TX / GND / RX**（说明书第 4 页部件图第 6 项，旁边还有第 7 项"航空转接线接口"）。
插头比较小，可能要用转接线或细杜邦插针。**先把三根线的定义用万用表确认清楚再插**。

## 三、四个实验（按顺序做，每个都能独立下结论）

> 所有命令都在 `诊断工具` 目录下执行（即 `lower-machine/诊断工具/`）。先跑一次自检，确认工具本身没问题：
>
> ```
> python rm0310.py selftest
> ```
> 期望最后一行：`=== 自检结果：24 通过，0 失败 ===`

### 实验 1：先证明"我们这边在发"（5 分钟，什么都不用拆）

**目的**：把 ④ 从"芯片认为发出去了"升级成"线上真的有波形"。

方法 A（有示波器/逻辑分析仪，最硬）：
探头接 **PG14**，地夹接 GND，跑自瞄程序。
正常波形：空闲高电平 3.3V；每 25ms 一次突发，突发约 **3.35ms**（309 字节 × 10bit ÷ 921600），
位宽约 **1.08µs**（= 921600）。

方法 B（没有示波器，用 PC 当记录仪）：
把 **PG14 那根线从 VT03 拔下来**，接到 USB-TTL 的 **RX**，GND 共地，然后：

```
python rm0310.py recv COM7 --seconds 20
```

期望输出（节选）：

```
  0x0310 帧: 800 个  (40.00 帧/秒)
  CRC8 错: 0   CRC16 错: 0
  内层序号: 包=800 唯一=800 丢=0 重复=0
  21B 遥控帧: 0 个
```

| 结果 | 结论 |
|---|---|
| 40 帧/秒、CRC 全对、序号连续 | ①②③④ 全部 OK，**断点在 VT03 及之后**，跳到实验 3 |
| 帧率明显低于 40，或大量 CRC 错 | STM32/线材问题（干扰、线太长、共地不良） |
| 一帧都没有，但 21B 遥控帧很多 | 你接的其实是 VT03 的 TX（或 C 板 PG9），不是 PG14 |
| 什么都没有 | 线没接对 / 波特率不对 / 这个口不是信号 |

> ⚠️ 方法 B 要让车"不带图传跑"，如果比赛在即、不想拆线，可以只做方法 A。
> **更推荐：旁听法** —— 不拆 PG14，把 USB-TTL 的 RX 直接并在 PG14 这根线上（双接收、单发送是安全的），
> PC 和 VT03 同时听同一个信号，VT03 照常工作。详见 4.2。

### 实验 2：让 PC 扮演接收端，读 VT03 的 TX（判断 VT03 有没有在"回东西"）

**目的**：确认 VT03 活着（绿色灯对频），并确认它的 TX 会按 921600 输出。
> 这一步**不能**证明 RX 一定收到了我们的数据——只能证明线序/接地/芯片是好的。

接线：USB-TTL **RX ← VT03 的 TX**，USB-TTL **GND ↔ VT03 GND**，VT03 自己的 12V 照常供电。

```
python rm0310.py recv COM7 --seconds 20
```

| 结果 | 结论 |
|---|---|
| **21B 遥控帧 ≈ 71 帧/秒**（无 0x0310） | ✅ 引脚定义、共地都对；VT03 活着且已对频 → 做实验 3 |
| 0x0310 帧也有 | VT03 的 TX 在回吐视频数据 → 说明它**收到并解析/透传**了 UART 数据（罕见的回环模式） |
| 什么都没有 | 引脚认错了 / 线没接对 / VT03 没对频（回去看灯） |
| 满屏乱码但偶尔有 0xA9 0x53 | 波特率不是 921600（说明这根线是数据线，但参数不对） |

**"什么都没有"时，先别急着换线，用万用表量一下电压**（VT03 上电、静止时，黑表笔接 GND）：

| 引脚 | 电压（对 GND） | 说明 |
|---|---|---|
| VT03 **TX** | **≈ 3.3V**（串口空闲为高电平） | 说明这个脚在输出、是 TX、VT03 已上电 |
| VT03 **RX** | 浮动（被外部驱动时才会变化） | RX 自己不驱动电平，量到的值不代表 VT03 |
| VT03 **GND** | 0V | 参考点 |

> 如果 TX 上量到 **0V 或 5V**，基本可以断定这个脚不是串口 TX（或已被拉死）。
> 这一步**不用接任何东西**，就能先把 3 pin 的定义定死。

> 这个小实验特别好用：**它顺手把"GND 有没有共地"这个问题一起验了**。

### 实验 3：让 PC 扮演 STM32，直接往 VT03 的 RX 灌包（本方案的核心）

**这就是"用一台电脑代替接收端和云台板相连"那套思路的落地版，也是把"STM32 有没有发好"从嫌疑名单里彻底拿掉的办法。**

#### 3.1 接线

```
   PC (USB-TTL)                         VT03
   ┌──────────┐                        ┌──────────┐
   │ TX   ────┼──── 杜邦线 ────────────┤ RX       │
   │ GND  ────┼──── 杜邦线 ────────────┤ GND      │
   │ (RX 可悬空)                        │ TX  (不接)│
   └──────────┘  3.3V 电平             │ 12V 由原电源供电 │
                                       └──────────┘

   ★ STM32 的 PG14 必须从 VT03 RX 上拔下来（两个发送端不能顶在一起）
```

#### 3.2 发送

```
python rm0310.py ports                                   # 先确认端口号
python rm0310.py send COM5 --style alt --hz 1 --seconds 120
```

`--style alt` = **交替**发两种包，一次实验同时验证 VT03 的两种可能行为：

| 类型 | 字节数 | 内容 |
|---|---|---|
| `canon` | 300 | 我方口径：`[len=298][seq][RM26][beat][0…]` = 客户端里的 CustomByteBlock data |
| `frame` | 309 | 完整 0x0310 帧：`A5 len seq crc8 0310 data crc16`（= STM32 原样发出的东西） |

发送时看回读那一行：

```
[  5.0s] 已发 5 包 (1.00/s)  回读: 遥控帧 356  其他 0B
```

`遥控帧 > 0` 说明 **你的 RX 也接在 VT03 的 TX 上了**（更省事：TX→RX、RX→TX、GND→GND 三线全接，
一次同时验收和发）。

#### 3.3 判定（打开客户端，跑满 120 秒，**不要关**）

退出客户端后，用客户端自己的抓包文件判定（**不会踢掉任何客户端**）：

```
python rm0310.py dump "C:\...\logs\<最新会话>\network_capture.bin"
```

| dump 输出 | 含义 | 下一步 |
|---|---|---|
| `CustomByteBlock` **0 条** | VT03 根本没把 UART 上的任何数据送进无线 | **VT03 不转发自定义数据** → 现有方案的前提就错了，见第五节"如果 VT03 不转发" |
| 长度分布 `{300: N}` + `内容类型 {'RM26': N}` | ✅ **VT03 会转发，而且会剥掉 0x0310 外壳**（这正是我们要的） | 那么断点回到 **STM32 → VT03 的连线/信号**（实验 1 的方法 B 能确认） |
| 长度分布 `{309: N}` | VT03 **原样透传整帧**，不解析协议 | 客户端因 300 字节限制直接丢弃；**这就是画面出不来的根因** |
| 长度分布 `{300: N}` + `（无内层包）` | 转了 300 字节，但内容不是我们的格式 | VT03 在改数据/加头，抓一条原始 payload 发回来分析 |
| 有包，但序号大量重复/缺失 | 无线丢包严重 | 降 `--hz` 到 0.5 再试；仍丢 → 干扰/距离/天线 |

> 关于"`{309: N}` 这种情况怎么修"：**让 STM32 只发 300 字节 data**（去掉 `0xA5` 外壳和 CRC16），
> 而不是发 309 字节整帧。改一行即可，见第五节。

#### 3.4 这个实验能同时证伪的东西

- VT03 的 RX 引脚到底存不存在 / 是不是这个脚
- 3.3V 电平能不能被 VT03 识别（如果能识别，STM32 的 3.3V 也一定可以）
- 921600 是不是 VT03 的实际波特率
- VT03 到底会不会转发自定义数据（**这是当前最大的未知**）

### 实验 4：跑真链路 + 2Hz 计数（不拆任何东西，10 分钟）

**目的**：确认"真链路"上到底有多少包到了客户端，而不是只有"一个包都没有"这种粗结论。

1. Jetson 上改 `autoaim/my_lf_INF_20261025/configs/standard3.yaml`：

   ```yaml
   video_send_rate_hz: 2.0      # 每秒最多放 2 个包，好数
   ```

   > 这一项是**上限**（令牌桶）。如果 2Hz 时实际出包更慢，属正常。**做完记得改回 `40.0`。**

2. 重启自瞄服务，让它跑 60 秒（客户端同时开着）。
3. 停掉，然后：

   ```
   python rm0310.py dump "C:\...\logs\<最新会话>\network_capture.bin"
   ```

| 结果 | 含义 |
|---|---|
| 0 条 | 和 40Hz 时一致 → 不是带宽/拥塞问题，是"根本没通" |
| ~120 条（2/秒），序号连续 | 通了！那 40Hz 时收不到就是**带宽/丢包/节拍**问题 |
| 有少量、序号有大缺口 | 通但丢得厉害 → 无线链路质量 |

> 这一步的价值：**把"完全不通"和"通了但丢包/带宽不够"分开**。这两种情况的修法完全不同。

## 四、如果我判断错了：还有两个容易被忽略的地方

### 4.1 遥控键鼠和 0x0310 抢同一个 UART（已排除，保留记录）

VT03 的 UART **也在往外送 21 字节遥控帧（14ms 一帧）**。
如果 VT03 是"半双工共用一根线"，而 STM32 的 PG14（TX）在 VT03 说话的时候把线拉低/拉高，
就会互相打架。

STM32 的 `USART6` 同时开着收发：`bsp_rc.c` 的 `RC_Init()` 给 USART6 开了 **RX DMA + IDLE 中断**，
但那是给 **PG9 上的 SBUS 遥控接收机**用的，TX 才是 PG14 → VT03 的 RX。
所以**只要 VT03 的 TX 没有接到 PG9，就不会有电气冲突**；如果 VT03 的 TX 真的接到了 PG9，
那 SBUS 遥控会先失灵（而车现在遥控正常、控制正常），基本可以把这一条排除。

**怎么区分**：
- 万用表量 VT03 的 TX 和 STM32 的 PG9 是不是通的（断开时不通 = 两根独立线，问题排除）。
- 如果 UART 是 3pin 独立 TX/RX，则天然无冲突。
- 另外：`RC_unable()` / `RC_restart()`（会 `__HAL_UART_DISABLE(&huart6)`）在整个工程里**没有被调用**
  （`detect_task.c` 里的钩子是注释掉的），所以不存在"SBUS 掉线把 USART6 关了、连 0x0310 也发不出去"的情况。

### 4.2 真链路正在发送时，PC 插不进同一个节点

实验 3 需要**把 PG14 从 VT03 RX 上拔掉**，这在"车上正在跑"时做不到。
如果拆线不方便，可改做**旁听**（双接收、单发送，安全）：

```
PC(USB-TTL) 的 RX 接到 VT03 的 RX 这个节点上（和 PG14 同一根线）
```

这样 PC 和 VT03 **同时**接收 STM32 的信号。PC 能收到 → 线上有信号、电平、波特率都对，
问题只能出在 VT03 内部（不转发/不解析）。
**这是零破坏的版本，推荐先做这个。**

## 五、如果结论是"VT03 不转发自定义数据"

那就不是接线问题，是**方案前提**问题。三条出路，按代价从低到高：

1. **改 STM32 只发 300 字节**（顺带解决"透传 309"这个可能）
   在 `application/video_forward.c` 的 `VideoForward_Task()` 里，把
   `HAL_UART_Transmit(handle, frame, 309, 20)` 改成
   `HAL_UART_Transmit(handle, frame + 7, 300, 20)`
   —— 只发 data，不发 `A5/len/seq/crc8/cmd/crc16`。
   **这对我们是安全的**：外层 CRC 在 STM32 已经校验过了，下游不再需要它。

2. **用 30 字节通道做判定实验**：0x0309（机器人→自定义控制器，30B，≤10Hz）是**同样性质**的图传链路数据
   （协议 1.4.1 节），如果 VT03 连 30 字节都不转发，就说明它压根不碰机器人发来的自定义数据；
   如果 0x0309 能通、0x0310 不通，那就是 VT03 固件只认 30 字节通道。
   代价很小（STM32 侧加一个 30 字节发送即可），但**不能承载视频**，只用来定性。
   > 0x0302 是反方向（自定义控制器→选手端→机器人），不能拿来测"机器人往客户端发"。

3. **换回传路径**：裁判系统常规链路（电源管理模块 User 口，9600）带宽不够视频；
   剩下的是运营商的 4G/5G 或者自建图传。

## 四点五、复盘：之前一次"MqTT 上有包"其实没证明客户端（保留记录）

2026-10-23 复盘了两次 `probe` 输出（121s / 60s 各收到 22 条），发现两件事，**都不是客户端的问题**：

1. **那 22 条里带着 `RM26` 标记**——那是 `rm0310.py send` 灌进去的心跳测试包，
   不是真视频。它只证明"VT03→VT13→选手端→MQTT 会把 300 字节原样转出去"。
2. **那几次客户端根本没在场 / 没收到**：客户端自己 `logs/<会话>/network_capture.bin`
   里 `CustomByteBlock(rx) = 0`，而同时段 `RobotDynamicStatus / GameStatus` 等主题
   一直在收——说明 MQTT 是通的，只是 0x0310 没到客户端。

另外注意 `probe --host 127.0.0.1` 探的是**本机**模拟/自建服务端；
实车走的是 `192.168.12.1`（选手端）。两边不是同一份数据，别混着比。

**再补一条（2026-10-23 第二次复盘）**：这两次 probe 是**电控在他们自己那台电脑上**跑的
（路径 `D:\A_club\RM\...`、`--host 127.0.0.1`），而且 probe 会顶掉同 ID 的客户端。
所以它证明的只是「**那台电脑**这一路能把 300 字节内容送到**本机** MQTT」，
既不代表我们现场 `192.168.12.1` 的链路，也不代表客户端。

还有一个容易看反的点：`send --style alt` 默认 `--start-seq 0` 时，
**偶数序号 = canon（300B 裸包，开头不是 `0xA5`）、奇数序号 = frame（309B 整帧，`0xA5` 开头）**。
收到的 22 条全是**奇数**、`send` 总共发了约 44 包 → 过去的是 **frame（309B 整帧）** 那一半，
canon 那一半被丢了。说明这一路**只认带 `0xA5` 外壳的 0x0310 帧**（裸 300 字节不认），
这恰好是 STM32 现在实际发的形态，所以 `{309}` 那条修法**暂时不要动**。

结论文档：[`第二视角当前结论-2026-10-23.md`](第二视角当前结论-2026-10-23.md)。

**以后判断"是不是客户端的问题"，只看三样东西：**

```
① 同一场次里客户端 log 里有没有 "MQTT消息解析成功 topic=CustomByteBlock"
② 同一场次里 network_capture.bin 里 CustomByteBlock(rx) 有多少条、长度分布
③ 如果收到了但内层长度全是 300 且序号连续，还不出画面，才轮到解码/显示
```

新版的 `rm0310.py probe` 跑完会自动去客户端日志目录找同一时间窗的会话，
直接把 ①② 打出来（第 ①③ 条自动，第 ② 条需要你跑 `dump`）。

> ⚠️ 客户端有两份 exe：`源码/build/release/luojiamaster.exe`（最新）和
> `程序/luojiamaster.exe`（有时是旧版，旧版一丢包就重置解码器，画面永远出不来）。
> 实测 2026-10-22 两份一致，但**每次更新后都要确认跑的是 build/release 那份**。
