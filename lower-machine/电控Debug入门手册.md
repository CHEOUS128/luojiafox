> 写给第一次接手这条链路的电控同学。

## 零、先说结论：现在卡在哪

一句话：**数据已经到了 VT03 的串口，但 VT03 之后什么都没有。**

```
Jetson 编码 ✅ → USB ✅ → STM32 校验 ✅ → PG14 发出 ✅ → VT03 ❓ → 无线 → VT13 ✅ → 选手端 ✅ → 客户端 ✅
```

**已经没有嫌疑的**（都有实测证据，不用再怀疑）：

| 环节 | 证据 |
|---|---|
| Jetson 在发 | 日志显示 VideoSender 已启用，没有“串口写失败” |
| USB 线没问题 | STM32 的 `Forwarded` 在涨 = 它确实收到了视频帧 |
| 帧格式没问题 | `CrcError = 0` = 309 字节帧的 CRC8/CRC16 全对 |
| 波特率/带宽没问题 | 40 帧/秒 × 309 字节 ≈ 124 kbps，远低于 921600 的 92 kB/s |
| SBUS 没有抢串口 | `RC_restart()`/`RC_unable()` 全工程没有任何调用 |

**唯一没验过的**：VT03 收到串口数据后，到底有没有把它放进无线。

这不是随便猜的：VT03 的产品说明书**只写了** 21 字节遥控帧，**从没写**它会转发 0x0310。
协议说它应该转发，说明书没说会。所以必须实测。

## 一、Debug 的第一原则：一次只改一个变量

新手最容易犯的错误不是“不会”，而是**同时动好几样东西**：

> 换了根线、改了波特率、重烧了固件、又换了块板子 —— 然后好了。
> 下次再出问题，你还是不知道为什么。

正确的做法是：**每做一次改动，都要能回答“改之前是什么、改之后是什么、为什么”。**

本手册和排查方案里所有的实验，都是按这个原则设计的：

- 每个实验只改一个东西（换一根线 / 换一个接收方 / 降一个速率）
- 每个实验都有**明确的判读标准**（看到什么 = 什么结论）
- 每个实验的结论**不被上一个实验的假设影响**

## 二、先分清：你在看“证据”还是“推测”

这是 Debug 里最重要的一条分界线。

| 推测（不能当结论用） | 证据（可以拿来定位） |
|---|---|
| “应该发出去了吧” | `HAL_UART_Transmit()` 返回 `HAL_OK` |
| “线接的是对的” | 万用表通断档量过，蜂鸣 |
| “VT03 应该会转发” | 抓包/收包**实际看到**了数据 |
| “波特率应该是 921600” | PC 收到 21 字节帧且 `0xA9 0x53` 开头 |
| “代码里写了就会执行” | 打断了点/看计数器，确实执行了 |

**排查方案里的每一条判定，都是在把“推测”换成“证据”。**

举例：`Forwarded` 在涨，能证明什么？

- ✅ 能证明：STM32 收到了帧、校验通过、`HAL_UART_Transmit()` 返回了 `HAL_OK`
- ❌ **不能**证明：PG14 的线上真的有波形
- ❌ **更不能**证明：VT03 收到了

`HAL_OK` 只说明数据写进了芯片的发送寄存器。如果引脚配置错、线断了、被别的外设拉住了，
数据照样“发出去了”，只是没人收到。

这就是为什么方案里有“用 PC 旁听 PG14”这个实验——**它是把“寄存器写了”升级成“线上真的有时序”的唯一办法**。

## 三、三种调试手段，以及它们各自能证明什么

### 手段 1：Keil 调试器看变量（最方便，但只能看“你以为的东西”）

**怎么做**：Keil 里 `Debug` → 打断点 → 在 `Watch` 窗口加变量 → 全速跑 → 看变量值。

这条链路里最值得看的四个变量：

```c
VideoForward_GetForwarded()    // 成功转发的帧数
VideoForward_GetCrcError()     // 校验失败的帧数
VideoForward_GetOverflow()     // 队列溢出丢弃的帧数
huart6.Instance->SR            // USART6 的状态寄存器
```

**能证明什么**：代码有没有执行到、分支走没走对、计数对不对。

**不能证明什么**：**电信号有没有真的从引脚出去。** 这是新手最容易搞混的一点。
程序里 `HAL_UART_Transmit()` 返回 `HAL_OK`，你打断点看到 `Forwarded = 100`，
**完全不代表 VT03 收到了任何东西。**

**注意事项**：

- 打断点会让程序停在原地。如果断在 200Hz 的任务里，整体会明显变慢，
  这会改变视频帧的节拍，可能导致你观察到“转发很慢”的假象。
- 想看实时增长的计数，**不要打断点**，用 `Live Watch`（`View → Watch Windows → Live Watch`），
  或者干脆用手段 2。
- 打断点的时候 USB 还在往 STM32 送数据，队列会溢出——看到 `Overflow` 在涨不一定是 bug。

### 手段 2：串口打印（最实用，但会占用一个串口）

STM32 可以把调试信息从另一个串口打出来，电脑用串口助手看。

**关键限制：USART6 不能用来打印。** 它现在是 921600 专职给 VT03 发视频帧的，
你在里面打一行 `printf` 就会插进视频帧中间，把那帧弄坏。

**这块板子上已经占掉的口**（`Src/usart.c` 里能看到初始化）：

| 串口 | 波特率 | 用途 | 能不能拿来打印 |
|---|---|---|---|
| USART1 | 9600 | 裁判系统 | ❌ 不要动 |
| USART3 | 100000 | DBUS 遥控 | ❌ 不要动 |
| USART6 | 921600 | VT03 视频转发 + SBUS | ❌ 会弄坏视频帧 |

**所以本链路不推荐用打印调试。** 优先用手段 1 的 Live Watch（不占口、不打断执行）。

如果一定要打印，两条路：

1. **临时**在 `VideoForward_Task()` 开头加 `return;` 把视频转发停掉，
   再往 USART6 打日志。**测完必须删掉这两行**，否则视频永远发不出去。
2. 找一个板子上**没用到的 UART**（看原理图确认引脚是空的），重新 `MX_UARTx_UART_Init()` 一个调试口出来。
   这是干净的做法，但需要改工程。

无论走哪条路，**改了什么都要记下来，并写进提交说明里**。

**打印格式建议**（不要只打一个数字，要让人看得懂）：

```c
printf("[VF] fwd=%lu crc=%lu ovf=%lu head=%u tail=%u\r\n",
       s_forwarded, s_crc_error, s_overflow, s_head, s_tail);
```

### 手段 3：让 PC 扮演设备（最硬，能证明“线上真的有东西”）

这就是排查方案里的实验 1/2/3。它的价值在于：

| 实验 | 电脑扮演谁 | 能证明 |
|---|---|---|
| 实验 1 | 一个**旁听的记录仪** | PG14 线上真的有 309 字节帧、CRC 全对、40 帧/秒 |
| 实验 2 | 一个**读 VT03 的电脑** | VT03 活着、TX 在按 921600 输出 21 字节帧 |
| 实验 3 | **STM32 本身** | VT03 会不会转发自定义数据（这一步跟 STM32 完全无关） |

**为什么实验 3 最重要**：它是**唯一一个把 STM32 排除掉**的实验。
如果电脑直接灌数据进 VT03、客户端还是收不到，那再怎么改 STM32 都没用。

### 三种手段对比

| | 能证明代码执行 | 能证明线上有信号 | 需要额外硬件 | 会干扰现有链路 |
|---|---|---|---|---|
| Keil 看变量 | ✅ | ❌ | 调试器 | 打断点会 |
| 串口打印 | ✅ | ❌ | 串口模块 | 会（占口） |
| PC 扮演设备 | ❌ | ✅ | USB-TTL | 实验 1 旁听不干扰 |

**结论：前两种证明“软件对不对”，第三种证明“电信号有没有”。两类证据缺一不可。**

## 四、动手前必须知道的五件事

### 4.1 串口电气基础：TX 接 RX，GND 必须共地

```
设备 A                        设备 B
 TX  ──────────────────────►  RX     （A 说，B 听）
 RX  ◄──────────────────────  TX     （B 说，A 听，可选）
 GND ───────────────────────  GND    （必须接！这是参考电平）
```

**不共地的后果**：两边的“高电平”和“低电平”参照物不一样，接收方会收到一堆乱码或者什么都收不到。
这是新手接线最常见的错误，症状是“程序全对但收不到数据”。

**TX 接 TX 的后果**：两个输出脚顶在一起，谁也听不见谁，严重时会损坏引脚。

### 4.2 电平必须匹配

VT03 的 UART 是 **3.3V 电平**。USB-TTL 模块上通常有个跳线选 3.3V/5V，**必须选 3.3V**。

5V 打到 VT03 的 RX 上，轻则收不到，重则烧掉那个脚。

**怎么确认**：用万用表量 VT03 的 TX 对 GND，空闲时应该读到 **≈3.3V**（串口空闲是高电平）。
如果读到 5V，说明你量的不是 3.3V 串口；如果读到 0V，说明这个脚可能不是 TX 或者被拉死了。

### 4.3 两个发送端不能接在同一根线上

做实验 3（电脑扮演 STM32）时，**必须先把 PG14 从 VT03 的 RX 上拔下来**。
PC 和 STM32 同时驱动同一根线，结果完全不可信，严重时两个引脚都可能受损。

反过来，**两个接收端可以接在同一根线上**（比如 PC 旁听 PG14）——这是安全的，
因为 RS-232/TTL 串口的输入是高阻抗的，不会互相干扰。

### 4.4 波特率要对，但“看着像乱码”≠ 波特率错

921600 是这条链路的波特率。如果波特率不对，串口助手会显示一堆乱码。

但**乱码也可能是别的原因**：电平不对、地没共、线太长受干扰、引脚不是串口。
排查顺序建议是：**先量电压和通断 → 再确认波特率 → 最后才怀疑芯片**。

### 4.5 别用“改了以后能用了”当结论

如果你改了三个地方然后好了，你不知道是哪一个起的作用。
下次再坏，你也修不好。

**正确做法**：改一个地方 → 测一次 → 记下“改之前什么现象、改之后什么现象” → 再改下一个。
哪怕慢一点，也比“蒙对了但不知道为什么”强。

## 五、跟着做：一次完整的排查怎么走

下面是本链路的标准流程。**每一步做完都要有明确结论，再往下走。**

```
第 0 步  看灯
         VT03 绿色 1Hz = 已连接收端（正常）
         红色/蓝色 = 没对上频，先解决这个，后面都别做
         ↓
第 1 步  确认我们这边在发（实验 1）
         PC 旁听 PG14，看到 40 帧/秒、CRC 全对、序号连续？
         是 → 跳到第 3 步       否 → 第 2 步
         ↓
第 2 步  查 STM32 → PG14 这一段
         线断了？引脚配错了？被别的外设占了？
         （这一步用万用表 + Keil 看变量就能定位）
         ↓
第 3 步  确认 VT03 是活的（实验 2）
         PC 读 VT03 的 TX，看到约 71 帧/秒 21 字节帧？
         是 → 第 4 步           否 → 引脚定义/接地有问题，回到接线
         ↓
第 4 步  确认 VT03 会不会转发（实验 3，核心）
         PC 代替 STM32 往 VT03 的 RX 灌包，客户端抓包看结果：
           - 0 条            → VT03 不转发自定义数据（方案前提不成立）
           - {300: N} + RM26 → 会转发且剥壳（正常），断点回到 STM32→VT03 的线
           - {309: N}        → 透传整帧，客户端丢弃（改 STM32 只发 300 字节）
         ↓
第 5 步  根据第 4 步结论，改对应的东西
```

**为什么顺序不能反**：

- 第 0 步没绿灯就去做第 4 步，等于在问一台没连上的设备“你收没收到”
- 第 1 步没做就做第 3 步，你分不清“VT03 没转发”和“STM32 根本没发”
- 第 4 步不做就改 STM32 代码，是在**没确认前提**的情况下改实现

## 六、常见的误判，以及正确的判断方式

| 你可能会想 | 为什么不对 | 正确的判断方式 |
|---|---|---|
| “`Forwarded` 在涨，说明 VT03 收到了” | `Forwarded` 只证明 `HAL_UART_Transmit` 返回了 `HAL_OK` | PC 旁听 PG14，看到真实波形/数据 |
| “官方图传画面正常，说明 VT03 没问题” | 官方画面走 VT03 **内部的相机**，不经过 UART | 用 PC 读 VT03 的 TX，或做实验 3 |
| “VT03 说明书没说会转发，所以肯定不会” | 说明书是产品文档，不一定覆盖全部协议行为 | 做实验 3 实测，不要猜 |
| “帧率低说明带宽不够” | 124 kbps 远低于 921600 baud 的 92 kB/s | 看抓包，确认是“完全不通”还是“通了但丢包” |
| “改了能用了，问题解决了” | 不知道是哪个改动起的作用 | 一次只改一个，改完记录现象 |
| “串口助手显示乱码，肯定是波特率错了” | 也可能是电平/接地/引脚错 | 先量电压和通断，再确认参数 |
| “我已经把代码改对了，硬件应该没问题” | 代码和电气是两回事 | 代码用 Keil 验，电气用示波器/PC 验 |

## 七、怎样给出一个“能直接定位”的结论

排查完之后，**不要只说“还是不行”**。一个好的结论长这样：

> 做了实验 1（PC 旁听 PG14，20 秒）：收到 803 个 0x0310 帧，40.1 帧/秒，CRC8/CRC16 全对，
> 内层序号连续、无重复。VT03 灯是绿色 1Hz。
> 结论：STM32 到 PG14 这一段完全正常，断点在 VT03 及其之后。

**判断标准**：看这句话的人，能不能**不看你的操作过程**就知道下一步该做什么。
如果不能，说明结论还不够具体。

**三个必须包含的东西**：

1. **你做了什么**（哪个实验、什么命令、接了什么线）
2. **你看到了什么**（具体数字：帧数、速率、正确/错误数量）
3. **你据此得出什么**（哪一段是好的，哪一段还不能确定）

**不要包含的东西**：

- “应该是……”、“可能是……”、“感觉……”，（这些是推测，不是结论）
- 大段截图（贴文字输出更好，可搜索、可复制）
- 同时说好几件事（一次只下一个结论）

## 八、附：本链路的关键参数速查

| 项目 | 值 | 出处 |
|---|---|---|
| STM32 → VT03 串口 | USART6，921600，8N1，无流控 | 协议表 1-1 |
| 视频帧总长 | 309 字节（7 头 + 300 数据 + 2 CRC） | 协议 1.2 节 + 表 1-41 |
| 外层 CRC | CRC8 覆盖前 4 字节（多项式 0x8C 反射），CRC16 覆盖前 307 字节（0x1189） | `video_forward.c` |
| 发送节拍 | 40 包/秒（协议上限 50） | `standard3.yaml` 的 `video_send_rate_hz` |
| VT03 遥控帧 | 21 字节，`0xA9 0x53` 开头，约 71 帧/秒 | VT03 说明书 |
| 客户端接受的包长 | 必须 ≤300 字节 | `custom_byte_block_video_decoder.cpp` |
| 内层格式 | `[2B 长度 BE][2B 序号 BE][H.264 ≤296B][补 0]`，长度 ≤298 | 同上 |

**引脚**：

| 信号 | STM32 引脚 | 接到 |
|---|---|---|
| 视频帧 TX | **PG14**（USART6_TX） | VT03 的 RX |
| SBUS 遥控 | **PG9**（USART6_RX） | 遥控接收机的 TX（**不是 VT03**） |
| 地 | GND | VT03 的 GND（**必须接**） |

## 九、最后

这条链路里最容易让人困惑的一点是：**四个环节看起来都“对”，但整体就是不通。**

原因在于，“对”分很多种层次：

- 代码写对了 ✅ → 不代表执行了
- 执行了 ✅ → 不代表引脚有信号
- 引脚有信号 ✅ → 不代表对方收到了
- 对方收到了 ✅ → 不代表它会转发
- 它会转发 ✅ → 不代表格式是客户端能认的

**排查的本质，就是把这条“不对”的链条，从某一环开始切掉，看剩下的部分还能不能自洽。**

如果不知道该切哪里，就从中点切——本方案的实验 3，就是整条链路的中点。
