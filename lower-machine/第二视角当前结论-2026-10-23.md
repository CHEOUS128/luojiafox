# 第二视角（0x0310）当前结论 — 2026-10-23

> 一句话：**整条链路是通的，但真视频只过来 0.16%–0.64%（约 99% 以上的包在路上丢了）。**
> 所以现状不是"哪里都没问题"，也不是"完全不通"，而是"**通了，但每秒钟只过得去半个包**"，任何解码器都出不了画面。
>
> 电控那组 `probe` 证明的是「电控那台电脑上，309 字节整帧能被他们那侧的图传链路收下、并以 300 字节的样子出现在他们**本机**的 MQTT 上」；它既没有证明我们现场车上的链路，也没有证明客户端有问题。
> 这次不需要改固件、不需要改客户端。

---

## 零、最重要的新发现（复核 10-21 / 10-22 客户端自己的抓包）

之前只看 10-22 22:28 那一次（那次 `CustomByteBlock(rx)=0`），所以以为"真视频从来没到过客户端"。
把**所有**历史会话都过一遍后，发现 10-21 和 10-22 各有一段是**真的收到了相机视频**（不是测试包）：

| 会话 | 服务器 | 收到的包 | 时间跨度 | 发送端同时在发 | 通过率 | 最长连续包 |
|---|---|---|---|---|---|---|
| 10-21 21:24 | `192.168.12.1` | 9 条（真 H.264） | 34.5 s | ~40.4 包/秒 | **0.64%** | 2 个 |
| 10-22 16:42 | `192.168.12.1` | 4 条（真 H.264） | 65.3 s | ~38.4 包/秒 | **0.16%** | 1 个 |

具体数字：

- 10-21：序号 3534 → 4930，中间发送端一共发了 **1397 个包**，客户端只收到 **9 个**。
- 10-22：序号 4802 → 7307，中间一共发了 **2506 个包**，客户端只收到 **4 个**。
- 两次的内容类型都是 `H264 SPS / H264 P帧 / 未知`，**没有 `RM26`** → 确认是真视频，不是灌包。
- 最长的一段连续包只有 **2 个**（10-21）和 **1 个**（10-22）。

**这三条同时成立意味着什么**：

1. **每一跳都活着**：Jetson 发 → STM32 转 → VT03 无线 → VT13 → 选手端 → MQTT → 客户端，整条路至少各通过一次。
   → 不存在"某一个零件彻底坏了"。
2. **但通过率低到没有意义**：H.264 要出画面，至少要一个完整的 IDR 帧（通常切成好几个连续包）。
   我们最长只拿到 2 个连续包，而且全程只有 1 个 SPS、没有完整访问单元 → **任何解码器都不可能出画面**。
   → "看不到画面"是**包不够**造成的，不是客户端解包/解码的 bug。
3. **断点不在客户端、也不在 MQTT**：同一时段里 `RobotDynamicStatus / GameStatus` 等主题都在按正常频率收，
   说明客户端和服务器之间的连接是好的。丢包发生在 **选手端 → VT13 → VT03 无线这一段，或者 0x0310 通道本身的带宽/转发配额**。

和电控那次实验对照，结论更清楚：

| 实验 | 发送节奏 | 通过率 |
|---|---|---|
| 电控本机 probe（frame 那一半） | ~1 包/秒 | **100%**（22/22） |
| 现场真车（10-21 / 10-22） | ~40 包/秒 | **0.16%–0.64%** |

→ 低频能过、高频崩掉 = **这条通道有一个很低的吞吐上限**（或者是高频率时只保留极少数包）。
这就是下一步唯一要测的东西：**上限到底是多少包/秒**。

## 一、先搞清楚：那组日志是"谁"跑的

原始输出里的命令行是：

```
D:\A_club\RM\luojiafox-main\luojiafox-main\lower-machine\诊断工具>rm0310.bat probe --robot 3 --host 127.0.0.1 --seconds 60
```

三个关键点，每一个都限定了它的结论范围：

| 看到的东西 | 含义 | 影响 |
|---|---|---|
| 路径 `D:\A_club\RM\...` | 这是**电控那台电脑**，不是我们的比赛电脑 | 结果只属于那台机器 |
| `--host 127.0.0.1` | **本机**。连的是那台电脑自己跑着的 MQTT 服务（模拟/自建裁判系统） | 不是实车的 `192.168.12.1`（选手端） |
| `probe` 本身 | 同一个机器人 ID 只能有一个 MQTT 客户端，probe 会**把同 ID 的客户端顶掉** | 这一轮里装在那台电脑上的 RoboGo 根本收不到 |

所以这组数据**没有客户端参与**，不能拿来判断客户端好坏。

## 二、那组数字到底证明了什么（一条一条翻译）

两次运行（121 秒 / 60 秒）都收到 22 条，数字完全对得上：

**1. `CustomByteBlock: 22 条`、`负载长度分布: {300: 22}`**
→ 到了 MQTT 的**全是 300 字节**，没有 309 字节的。说明这一路会把内容裁到/剥到 300 字节。

**2. `内层 seq=7 RM26` 里的 `RM26`**
→ 这是 `rm0310.py send` 灌进去的心跳测试包（内容固定 `RM26` + 心跳计数），**不是相机视频**。
→ 真视频的内层是 H.264 数据，在 dump 里会显示成 `H264…`，不会是 `RM26`。

**3. 序号 `7,9,11…45` / `25,27,29…63`，隔一个出现一次**
→ 在 `--style alt` 下，每发一包序号 +1，两种样式交替;按默认 `--start-seq 0`：
  - **偶数序号 = canon（300B 裸包，第一字节不是 `0xA5`）**
  - **奇数序号 = frame（309B 整帧，`0xA5` 开头，正是我们 STM32 现在实际发出去的形态）**
→ 这次收到的**全是奇数**，而且 `send` 总共发了约 44 包、到的是 22 包，正好一半。也就是说：
  - ✅ **frame 那一半过去了**（309 字节整帧 → 经过无线 → 到 MQTT 时已经是 300 字节，说明 309 的外壳被正确地剥掉了）
  - ❌ **canon 那一半（300 字节裸包）没过去**
→ 这个方向和"VT03 只认 300 字节"正好相反。更合理的解释是：这一路**只认带 `0xA5` 外壳的合法 0x0310 帧**，
  裸的 300 字节它不认、直接扔了。对我们来说这是**好消息**：我们发 309 帧的写法本来就是对的。

> ⚠️ 一个技术细节：309 字节在无线里**不太可能原样裸传**（带宽和协议都不支持把整帧塞进去）。
> 所以更可能是"发送端/接收端把 `A5 … CRC16` 外壳剥掉、只把 300 字节 data 发出来"。
> 这也解释了为什么到 MQTT 的全是 300 字节。不管具体是哪一跳剥的，结论不变：
> **只有 frame 这种形态能过，canon 那种形态过不去。**

**4. `22 条之后不再增长`**
→ `send` 先结束、`probe` 还多跑了一会儿，数据停了。这是正常现象，不是链路断了。

**5. 旧版工具结尾写的「问题在客户端侧或格式」**
→ **这句话是错的**（旧文案），因为这一轮客户端根本不在场。新版工具已经改掉了。

## 三、那我们要不要改接口？现在别改

- 协议 1.3 原文：图传发送端**从串口接收数据**并转发；表 1-1 规定这一跳是 **921600 8N1**。
- 我们 STM32 现在发 **309 字节整帧**，正好是协议要求的形态。
- 电控那边 frame 这一半能过，进一步说明**309B 整帧的写法是对的**。
- 只有一种情况才需要改成"只发 300 字节 data"：**我们自己现场实测时，MQTT 上看到的是 309 字节的包**（因为客户端只接受 300）。改法见 [`第二视角链路逐环节排查方案.md`](第二视角链路逐环节排查方案.md) 第五节，一行：
  `HAL_UART_Transmit(handle, frame, 309, 20)` → `HAL_UART_Transmit(handle, frame + 7, 300, 20)`

**结论：这次不改 STM32、不改客户端。**

下一步不是"修哪里"，而是**测出这条通道的吞吐上限**（见第五节 A 步），
再按上限重设发送端参数（见 B 步）。**在测出上限之前，不要改任何固件。**

## 四、客户端到底有没有问题（结论：没有证据，基本可以排除）

能确定的：

- 客户端代码路径是完整的：MQTT 订阅 `CustomByteBlock` → 取 `.data()` → 300 字节 transport 解析 → H.264 解码 → 显示。
- 10-22 22:28 那次：`RobotDynamicStatus / GameStatus` 一直在收，但 `CustomByteBlock(rx) = 0` → 那段时间 **0x0310 根本没送到客户端**。
- 10-21 / 10-22 两次真视频：客户端收到了 **9 条 / 4 条**，而且解析出了 `H264 SPS`、`H264 P帧` →
  说明**客户端的"收包 → 解 protobuf → 拆 300 字节 transport → 认 H.264"这一段是好的**。
- 客户端日志里从来没有"解码失败"的错误，只有 `检测到丢包，重置解码器`——那是**因为包本来就不连续**，不是解码器的 bug。

还不能确定 / 唯一已知的客户端缺点：

- **丢包后重置解码器**会让"偶尔来一个包"永远等不到完整帧。虽然诊断版已改成不重置，但**包少到这个程度，改什么也出不了画面**。
- 另一个还没测的点：如果将来测出通道上限只有 2~5 包/秒，那**必须**让发送端把一整个关键帧切得更少、或者降低分辨率/码率，
  让一个 IDR 能塞进 2~5 个包——这属于 B 步，等测出上限再定。

**判断客户端有没有问题，只看这三条（缺一不可）：**

```
① 客户端 log 里有没有 "MQTT消息解析成功 topic=CustomByteBlock"
② 同场次 network_capture.bin 里 CustomByteBlock(rx) 有多少条、长度是不是 300
③ 有数但不出画面 → 才轮到看解码/显示
```

现在 ①②都过了（有数、长度全对、内容是 H.264）→ **问题不在客户端，在"包来得太少"。**

## 五、下一步（我们自己做，不依赖电控）

### A0. 决定性实验：先确认丢包发生在 MQTT 之前还是之后（5 分钟）

这一步比 A 更重要，因为它把"客户端有没有关系"彻底钉死：

1. **关掉 RoboGo**（probe 会顶掉它）。
2. 车保持原来 40 包/秒的发送（`video_send_rate_hz: 40.0`，不改）。
3. 跑：

   ```
   python rm0310.py probe --robot 3 --host 192.168.12.1 --seconds 60
   ```

4. 看 `内层序号` 那行的通过率 = `唯一 / (末序号 − 首序号 + 1)`。

| probe 看到的通过率 | 含义 | 下一步 |
|---|---|---|
| 也很低（<5%） | 丢包发生在 **MQTT 之前**（VT03/VT13 无线、选手端、或 0x0310 通道限流） | 做 A 步测上限 |
| 很高（>80%），但客户端只有 0.5% | 丢包发生在 **MQTT → 客户端** 这一段（客户端订阅/处理） | 才轮到查客户端 |

> 上一次客户端记录的 0.64% / 0.16% 是"客户端这一端"看到的。
> **只有用 probe 测出 MQTT 这一层也是同样低**，才能说"不是客户端的问题"。
> 这一步花 5 分钟，能省掉后面几天的瞎猜。

### A. 先测通道上限（这一条决定后面怎么改）

目的：在**不改任何固件**的前提下，测出"每秒发多少包时，通过率还是高的"。

1. 在 Jetson 上改 `autoaim/my_lf_INF_20261025/configs/standard3.yaml`：

   ```yaml
   video_send_rate_hz: 5.0      # 先测 5 包/秒
   ```

   重启服务：`sudo systemctl restart autoaim-20261025`。

2. 客户端正常开着（**不要跑 probe**，probe 会顶掉客户端），车静止或跑起来都行，**跑 60 秒**。

3. 退出客户端，拆抓包看通过率：

   ```
   python rm0310.py dump "C:\...\logs\<最新会话>\network_capture.bin"
   ```

   判读：看 `内层序号` 那行的 **唯一数 / (末序号 − 首序号 + 1)**。
   - ≥ 90% → 5 包/秒能过。再把 `video_send_rate_hz` 改成 **10**，重做一次。
   - < 50% → 5 包/秒就不行，改成 **2** 再试。
   
   依次试 `5 → 10 → 2 → 1`，找到"唯一数 / 总数 ≥ 90%"的最大值，**记下来**。

4. 测完把 `video_send_rate_hz` **改回 40.0**（或者按测出来的上限设一个安全值），重启服务。

> 说明：这一步只验证"通道能吃多少包/秒"，不需要真画面。
> 只要通过率上去了、能连续看到几十个包，**画面自己就会出来**——因为客户端解码这一段已经证明是好的。

### B. 按上限重设发送端（等 A 有结果再做）

如果上限只有 1~5 包/秒：靠 300 字节/包传 300×240 H.264 是**不够**的。
可选方向（按代价从低到高，到时再选）：

1. **降分辨率 + 降帧率**：例如 160×120 @ 5fps，让每个关键帧只占 1~2 个包。
2. **加大关键帧间隔**（`-g`），减少 IDR 数量，但**每次关键帧仍然要能完整过去**。
3. **换更高效的编码参数**（更高 CRF 压缩，牺牲画质换包数）。
4. 如果上限确实只有 1~2 包/秒 → 这条路**做不了实时视频**，只能做"幻灯片式"低帧率画面，需要重新评估方案。

**在这些测出来之前，不要动客户端、不要动 STM32。**

### C. 如果 A 步结果是"一次都收不到"

那才回到排查方案里「PC 灌包进 VT03」的实验 3，检查 VT03 的灯和接线。

每次实测前后都按这个顺序，**不要跳步**：

```

# 4) 看这一行：内层序号: 包=N 唯一=M 丢=K ...
```

## 七、电控可以照着做的两句话

电控不用改任何代码。实测时只需要回答：

1. **VT03 的灯是不是绿 1Hz？**（绿=已连接接收端；红=没对上频；蓝=对频中；紫=没激活）
2. **开 debug 模式，念一下三个计数**：`Forwarded / CrcError / Overflow`（只要 `CrcError=0`、`Forwarded` 在涨就够）。
