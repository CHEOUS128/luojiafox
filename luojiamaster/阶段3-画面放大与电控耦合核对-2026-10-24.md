## 一、先给结论

| 问题 | 结论 | 依据 |
|---|---|---|
| 电控代码把「控制帧」和「视频帧」耦合了吗？ | **没有** | 全工程只有一个 `HAL_UART_Transmit`（`video_forward.c:244`），入队只有一个调用点（`Self_aim.c:67`），队列满只丢视频；控制帧和视频帧在同一个字节状态机里按帧头 `0xFF`/`0xA5` **互斥分流**，一个字节只会进一个解析器 |
| 遥控器会不会触发 `RC_restart()` 把 USART6 关一下？ | **不会** | `RC_data_is_error` / `slove_RC_lost` / `slove_data_error` 的注册在 `detect_task.c:298-300` 是**注释掉的**，全工程无调用点 |
| 裁判端 UI（0x0301）会不会抢 USART6 的 DMA？ | **不会（这版固件）** | `freertos.c:166-167` 的 `referee_usart_task` 创建被注释，`UI_ReFresh` 永不执行；10-21 22:25 那版 map 里 armlink 也把 `HAL_UART_Transmit_DMA/IT` 全 Removing 了 |
| 那为什么「动起来才有画面」？ | **通道 + 客户端恢复速度**，不是电控耦合 | 见 §二 的时序相关性 |
| 画面放大了能不能塞进 296B？ | **能，而且更宽裕** | 离线实测 480×480 全 I 帧中位 **227B**，比现在的 160×160（124B）只多 100B，p90 263B 仍未触顶 |

## 二、时序相关性（21:34 那场，600 秒，473,572 条记录）

先修正上一轮的一个口径错误：`KeyboardMouseControl` 在**没有输入的时候也照发**（内容不变），
所以「到达前 0.5 秒内有键鼠报文」这个指标被抬高了。这次统一改用**内容变化**作为「真实输入」。
会话统计：KBM 报文 **25.2 条/秒**，其中内容变化只有 **5.12 次/秒**（≈195 ms 一次）。

「到达帧距离上一次**内容变化**多久」的分布：

| 距离 | 帧数 |
|---|---|
| 0 – 50 ms | **136** |
| 50 – 100 ms | 31 |
| 100 – 200 ms | 21 |
| 200 – 300 ms | 3 |
| 300 – 500 ms | 2 |
| 500 ms – 5 s | **0** |
| > 5 s | 17 |

**没有一帧落在 0.5 秒到 5 秒这个区间**，然后突然又有 17 帧落在 5 秒以外。
中位偏移 **35 ms**。

### 对照组（同一时间轴、同样窗口）

| 窗口 | CBB 到达帧 | 随机时刻 | 随机 KBM 报文 | 随机 UDP 包 |
|---|---|---|---|---|
| 10 ms | **10.5 %** | 5.0 % | 20.3 % | 5.5 % |
| 50 ms | **64.8 %** | 22.2 % | 23.4 % | 22.7 % |
| 100 ms | **79.5 %** | 27.0 % | 25.7 % | 28.0 % |
| 200 ms | **89.5 %** | 31.5 % | 29.3 % | 32.9 % |

10 ms 窗口下是 **2 倍**，50 ms 窗口下是 **2.8 倍**，而且随着窗口收窄倍数反而变大
—— 这说明是「输入 → 几十毫秒内通道才打开」的**因果**，不是「同一时段一起忙」的相关。

### 但这不是「只有按键才放行」

`CustomControl`（客户端另一条自定义指令）也在 8.46 条/秒地发，到达帧 100 % 都落在
「上一条 CustomControl 之后 0.2 秒内」——**因为那玩意平均 115 ms 一条，什么时刻都躲不开**。
同理「5 秒以外的 17 帧」说明**不按键也能到**，只是低频。

所以准确的描述是：

> 0x0310 这条通道有**周期性**（约每 0.2 秒一个窗口，与 KBM 报文节拍同源），
> 帧要落进窗口才过得去；输入只是在提高「帧被发出」的密度，不是钥匙。

### 和 CH 说的「遥控器也能带出画面」怎么统一

遥控器走 DBUS 直连 STM32（USART6 RX，21 字节 `A9 53`），确实**不经过选手端和裁判端**。
但客户端这一端看到的「画面」是 **0x0310 这条数据通道**的结果，
而这条通道的窗口节拍由**选手端/VT03 的串口转发节奏**决定 —— 遥控器改变不了它。

CH 观察到遥控器转动也带出画面，有两种都能解释通的可能：
1. 操作手感不同（遥控器推杆是连续的，键鼠是点动的），真实输入密度差不多；
2. **官方图传本身就是「按键才动」**（V 键自瞄、F 键开火、拨杆切视野），转到那边的画面看起来也是输入触发的。

**这不是电控代码能改的东西。** 电控这边该查的都在 §一 表格里逐条核过了。

## 三、画面放大 ×9 的实际改动

### 改了什么

`configs/standard3.yaml`（Jetson 上运行的服务就是这个文件，`scripts/enable_video_service.sh:95`）：

```yaml
video_width: 480              # 原 160
video_height: 480             # 原 160
video_crop_size: 480          # 原 320
```

像素面积 **160² → 480² = 正好 9 倍**。
`keep_aspect: false` + `crop_size = 480` 意味着从 1280×1024 **中心裁 480×480、1:1 不缩放**，
所以是真正的「清晰度 ×9」，不是把小图拉到 480 再糊回去。
（旧配置是裁 320 再缩到 160，等于把 4 个原像素压成 1 个。）

### 怎么塞进 296 字节：靠编码器，不靠改代码

单包模式的硬约束在 `video_sender.cpp:164-172`：
`frame_cap = 296`，目标码率按 `296×8×5fps×0.85` 反推，VBV = 目标码率的一半。
编码器每一帧都被压在这个预算里，压不进去就整帧丢弃（`++stat_oversize`），**绝不会拆成半帧**。

### 离线实测（合成场景 + 真实相机噪声，100 帧，每帧独立传感器噪声 + 亮度漂移 + 平移）

| 分辨率 | 中位 | p90 | 最大 | 超 296B 被丢 |
|---|---|---|---|---|
| 160×160（当前） | 124 B | 155 B | 167 B | 0 / 29 |
| **480×480（新）** | **227 B** | **263 B** | 275 B | 0 / 29 |

⇒ 9 倍像素只多约 100 字节，**离 296B 上限还有 30~70 字节余量**。
真实工业相机画面细节比合成场景多，可能多吃 10~20 %，仍在安全区。
**万一超了，症状是「画面不动」而不是「画面坏掉」**——因为整帧被丢，客户端会一直显示最后一帧，
日志里 `超限丢弃` 会涨。判据在 §五。

## 四、电控代码核对清单（给电控看的，都是行号级）

工程：`lower-machine/26赛季全向轮步兵/gimbal_project`（与 `小改电控代码\26全向轮步兵10.24` 同源）

| 检查项 | 位置 | 结论 |
|---|---|---|
| 视频帧入队 | `Self_aim.c:67` → `VideoForward_PushFrame(buf)` | 唯一入口，只在凑满 309 字节且是 `0xA5` 帧头时调用 |
| 视频帧出队 | `video_forward.c:244` `HAL_UART_Transmit(&huart6, …)` | 全工程唯一一处 USART6 TX 调用 |
| 控制帧处理 | `Self_aim.c:69-74` | 只 `memcpy` 到 `inputdata`，**不碰串口** |
| 两个解析器会不会打架 | `Self_aim.c:40-84` 单一状态机 | `0xA5` → kind=1，`0xFF` → kind=2，一个字节只走一支 |
| 队列满 | `video_forward.c:219-225` | **丢最老的视频帧**（`s_overflow++`），控制帧不受影响 |
| USART6 TX DMA | `bsp_usart.c:114` `usart6_tx_dma_enable()` | 全工程无调用点（只有 `RM_Cilent_UI.c:153` 调用，而它所在任务被注释） |
| 遥控器线路重启 | `bsp_rc.c:52` `RC_restart()` | 全工程无调用点（`calibrate_task.c:681` 是注释掉的） |
| 遥控器错误检测 | `detect_task.c:298-300` | 三行注册全被注释 |
| USART6 收发共用 | `usart.c:83` `UART_MODE_TX_RX` | 接收走 DMA（`bsp_rc.c`），发送走轮询，两者用不同的寄存器位，不互相阻塞 |
| 遥控器抢总线 | `remote_control.c:148` `USART6_IRQHandler` | 只读 SR 清标志 + 搬 DMA 缓冲，**不写 DR** |
| 200 Hz 任务里有没有阻塞 | `Self_aim.c:145-150` | `USBD1` 回发 + `VideoForward_Task`（最长 20 ms 超时 × 3 次）+ `osDelay(5)`；队列空时是立即返回 |

**唯一值得提一句的**：`USART6_IRQHandler` 触发时会短暂 disable/enable 接收 DMA，
`HAL_UART_Transmit` 在这期间只等其他标志位，不冲突。
（之前修的那两行 `DMA1_Stream1` 笔误已改，SBUS 现在也没启用，跟视频无关。）

## 五、下一轮上机：怎么判读

改完只需要 **重启服务**（不动 C 代码，不用重编译）：

```bash
systemctl restart autoaim-20261025
```

然后看三行日志：

```bash
grep -aE "VideoSender|Current FPS" ~/my_lf_INF_20261025/logs/autostart.log | tail -n 30
```

| 日志 | 含义 | 该做什么 |
|---|---|---|
| `已启用（480x480 …）` | 新配置生效 | 等 10 秒看下一行 |
| `最近帧 200~290 字节`、`超限丢弃` 不涨 | 编码器压得进去 | 保持，去客户端按 H 看画面 |
| `超限丢弃` 每 5 秒涨 ≥2 | 480 太大塞不进 296B | 退到 `384/384/384`（面积 5.76 倍）；再不行 `320/320/320`（4 倍） |
| `成帧` 不涨 / `Recent FPS: 0.0` | 和视频无关，是相机或云台上行断了 | 看 `看门狗` 那行报的「卡在」 |

**客户端这一头已经改好了**（5 秒让位），这一轮不用再动客户端。
按 H 之后，断流时画面会**冻住**，最多 5 秒才切回官方图传。

## 六、还欠的一件事（诚实记账）

**8.4 % 的整帧到达率，本轮没有解决，只做了两件事：**
1. 客户端不再因为短暂断流来回抢主画面（`阶段2-…` 文档）；
2. 画面像素 ×9，让「偶尔来一帧」也能看清敌人在哪。

真正要提上去，得先回答「窗口为什么是 0.2 秒一个、为什么一帧只过一个」。
现在手上有三条能互相印证的事实：
- 15:57 从 PC 经 CH340 灌 VT03，**278/278 全过**，间隔 0.216 秒（那是灌包节奏，不是通道节奏）；
- 现场 STM32 发，**整包到达率 1 % ~ 8 %**；
- 到达帧**全部**落在「上次输入变化后 40 ms 级」的位置，0.5~5 秒区间是**空的**。

⇒ 下一步不是调参数，是把「窗口」这个东西**测出来**：
在 STM32 侧加一行「本帧入队时刻 / 本帧发出时刻」，和客户端到达时刻对齐，
看 40 ms 这个偏移是**固定的**（＝串口/无线排队延迟）还是**随机的**（＝每次重新建立转发）。
这个实验要做，得再改一次固件，等 CH 点头。
