# 阶段 4：找到「一到就连着到」这条线索 —— 闸门在 STM32 之后（2026-10-25 晚）

> 承接 `阶段3-画面放大与电控耦合核对-2026-10-24.md`。
> 这一版改掉了同目录上一版的两条结论（§三 的打折、§四 的测法），原因写在各节里。
> **所有现场动作只用 .bat，不需要 Python。**

---

## 一、先更正上一版的解析 bug

上一版算「内层长度/序号」取错偏移：`data[0]` 是 protobuf 的字段标记 `0x0A`，
真正 300 字节从 `0x0A + varint` 之后开始。按正确偏移重算（客户端会话 600 秒）：

| 项 | 值 |
|---|---|
| 内层序号 | 530 → 3023，单调 |
| 内层长度 | 142 / 233 / 298（最小 / 中位 / 最大） |
| 相邻序号差 | **+1 共 95 次**；+2 11 次、+3 18 次 |

⇒ 没有「0.2 秒门」，也没有「大帧过不去」的尺寸上限。

## 二、客户端收到的帧数是 0.35 帧/秒

同一会话 600 秒，客户端只收到 210 条 CBB = **0.35 帧/秒**；
而 Jetson 是 4.49 帧/秒。**84 % 的帧在到达客户端之前就没了。**

## 三、旁听数据：那两次线上只有 0.4~0.6 帧/秒（撤回上一版的「打折」，也撤回「线路没丢帧」）

> **先说时效**：12:37 / 12:38 / 16:20 这三次旁听都在 **10-24 21:00 上位机短写修复之前**、
> 也在 17:36 烧新固件之前。所以它们**不代表现在的链路**，只能说明「低帧率不需要用
> 『输入开闸门』来解释」，不能拿它给今天判死刑。今天必须重新听一次（§四）。

三次 CH340 旁听 PG14（都在 60 秒窗口），我用 `crc0310.ps1` 里同一张 CRC 表重数
（上一版用的是另一套 CRC 参数，数出来的「21/34 个帧头」不可信）：

| 文件 | 时间 | 完整帧头 | 完整 309 字节帧 | 帧/秒 |
|---|---|---|---|---|
| `listen0310_COM7_20261024_123726.bin` | 12:37 | 11 | **0** | 0 |
| `listen0310_COM7_20261024_123841.bin` | 12:38 | 21 | **0** | 0 |
| `listen0310_COM7_20261024_162026.bin` | 16:20 | 34 | **0** | **0.57** |

- **一个 CRC16 对的 309 字节帧都没有。** 34 个帧头就是 34 帧的开头，0 : 34 完整。
- 逐帧去看「帧头到下一个帧头的距离」，**多数帧比它声明的长度多几个字节**
  （`gap - ilen - 11` 的中位 +20 字节），而且多出来的部分基本都是 0。
  也就是说：**多数情况下，线上一帧 = 帧头 7 + 内层头 4 + 编码数据 + 若干 0**，
  下一帧紧跟着来。但也**不是全部**：12:38 那 19 个间隔里有 4 个是负的（少 1~34 字节），
  16:20 那 33 个里有 4 个是负的 —— 说明**偶尔确实丢一点 H.264**，只是不占多数。
- 12:38 那 60 秒 = **0.35 帧/秒**，和客户端一模一样。
- **一个重要限定**：缺的多数是「零填充 + CRC16 尾巴」。而 17:36 烧的固件批次里，
  客户端从没收到 299B/295B 的残包 —— 那一批 H.264 是完整的。
  两者拼起来最像的解释是：**发送被 64 字节边界切断（USB CDC 报文 / DMA 取整）**。
  这一条要用 `listen0310.bat` 新版（会把 `帧尾余量` 打出来）核实。

### 3.5 21:34 的客户端数据说明「闸门在 STM32 之后」

> 这一节是这一版真正的结论。

- 21:34 会话里，**相邻到达帧的内层序号 +1 的有 95 次**（+2 11 次、+3 18 次）。
  也就是说：**一到就是连着到**，断就是几秒一帧都没有。
- 如果 STM32 是「收到 4.5 帧、只转 0.35 帧」，它转发的帧之间序号会大幅跳号
  （530、547、591…），不会是 +1 连着。**+1 连着 ⇒ 那一批帧 STM32 全都转出去了。**
- ⇒ 21:34 那次的丢帧位置在 **STM32 的 PG14 之后**：VT03 → 无线 → 选手端 → MQTT。
- 那 12:38/16:20 旁听为什么只有 0.35~0.57 帧/秒？**因为那两次都在 10-24 21:00
  修上位机短写之前**，STM32 根本拼不出几帧，和 21:34 不是同一个状态。

**所以今天只差一个数：PG14 线上现在是不是 4.5 帧/秒。**
是 ⇒ 锅在 VT03→无线→选手端（代码改不了，只能靠 ×9 / 换发送方式）；
不是 ⇒ 锅回到 STM32 或 Jetson。

### 关于「灌包实验已排除 VT03」

按 CH 的确认：15:57 那次灌包实验人是**静止的**，Jetson 那边也证明静止时照样按 4.49 帧/秒发。
所以 **VT03 不是「有操作才转发」的**，这一点成立，不用打折。
但那次只证明了 **VT03 的转发不依赖操作**，没有证明 **VT03 转发不丢帧** ——
所以下一节把它和 STM32 一起测。

## 四、决定性测法（全部 .bat，不需要 Python）

**接线**（只接两根）：

```
CH340 的 RX  ->  板子 PG14（3pin 丝印 UART1、标 TX 的那根数据线）
CH340 的 GND ->  板子 GND                     ← 必须共地
CH340 的 TX  ->  悬空不接
3pin 里的 12V / 5V / 3V3  ->  ★一根都别碰★
```

**顺序：先插好线 → 开 Jetson 画面并等 10 秒 → 再开测。**

### 第 1 步：边操作边旁听（120 秒）

`诊断工具\listen0310.bat COM7 -Seconds 120` 开跑以后：

1. **拿遥控器让云台一直快速转动**，从头转到尾（这是 VT03 已确认会转发的那段）；
2. 到第 60 秒时，**在 RoboGo 里按一下 H** 进自定义流，让客户端那半边也在看同一段时间。

判读窗口里这两行：

```
  好帧头      N 个（X 帧/秒）
  完整帧      M 帧      残帧 ...
```

- `X` ≈ **4.5**（120 秒约 540）：线路满载 → 按 §3.5，丢在 **VT03 → 无线 → 选手端**
- `X` ≈ **0.3~0.6**（120 秒约 40~70）：**线路本身就砍了 7/8** → 回到 STM32 或 Jetson
- **`完整帧 M` 即使是 0 也别急着下结论**：按 §三 的账，线上一帧可能只有 230~270 字节
  （尾巴的零填充被切掉），计数器要凑满 309 才算「完整」，所以 M 本来就会偏低。
  这一轮要看的是 **`好帧头` 的帧/秒**，以及新版多打的那行 **`帧尾余量`**：
  - 中位 **40~65** ⇒ 帧是好的，可以放心；
  - 明显更小 ⇒ 帧尾被切；出现负数 ⇒ 编码数据本身就缺了；
  - 忽正忽负 + 乱字节多 ⇒ 接线/共地/波特率有问题，这次结果作废，重接。

### 第 2 步：同一次操作，看 Jetson 那一行

Jetson 那个跑程序的终端里，每秒一行：

```
[Serial] 控制帧 ... | 视频帧 完整 N 短写 M 跨轮 K 失败 F
```

- `完整` ≈ **4~5**：Jetson 确实把 4.5 帧/秒交出去了 → 锅在 STM32 之后
- `完整` 只有 0~1，`短写/跨轮/失败` 在涨：锅在**上位机→USB**，固件不动

### 第 3 步：同时开 RoboGo

跑完用 `诊断工具\dumpcap.bat`（它自己找最新会话）。把三个数排在一起：

| Jetson `视频帧 完整` | 旁听 `帧/秒` | 客户端 `CBB 条数/秒` | 结论 |
|---|---|---|---|
| 4~5 | 4~5 | 0.3~1 | 丢在 VT03 / 无线 / 选手端（固件改不了） |
| 4~5 | 0.3~0.6 | 0.3~0.6 | **丢在 STM32 解析或 USART6 发送**（电控改） |
| 0~1 | 0~1 | 0~1 | 丢在 Jetson→USB（上位机改） |

第二行是**最值得防**的情况（老旁听就是 0.35~0.57，但那是旧固件 + 旧上位机；
按 §3.5，**今天最可能落到第一行**）。真要落到第二行，电控那边
在 Keil 里 Watch 展开 `VideoForward_Debug` 就能一刀切开：

- `frames` 涨得很慢（≈0.5/秒）⇒ **USB 收包/拼帧就丢了**（USB 收到的是碎的）
- `frames` ≈ 4.5/秒、`forwarded` 只有 0.5/秒 ⇒ **USART6 没发出去**（`tx_error` / `tx_stuck` 会涨）

需要的话我再给电控一版「每 5 秒把那计数器从 USB 打回 PC」的 log 行，现场连 Keil 都不用。

### 第 4 步（只有落到第一行才做）：把发送帧率提上去

如果旁听是 4.5 帧/秒、客户端还是 0.3，说明闸门是**开/关两态**（§3.5：一组里连着到，
一关就是几秒）。那么**把发送帧率提高，开着的窗口里就能挤进更多帧**：

```
./build/standard_mpc configs/standard3.yaml --video-fps 20
```

`--video-fps` 是这一轮加的覆盖开关，**不用重编译**（改完 `systemctl restart` 或手动起程序均可）。
20 帧/秒 × 296 B × 8 = 47 kbps，单包上限没变，帧长也没变，不会撑爆。

客户端那边只数 `dumpcap.bat` 的 CBB 条数：**0.35 → 1.0 以上**就说明「开着的时长」是固定资源，
提高密度就是对的；**还是 0.35** 就说明它是按「每秒几个包」限流，加密度没用，那就只能等 ×9
让到了的帧看得清。

## 五、代码这一轮改了什么

只有一处，纯方便现场做对照，**不改任何默认行为**：
`src/standard_mpc.cpp` 加了 4 个命令行覆盖（`--video-fps / --video-width / --video-height / --video-crop`），
`io/video_sender/video_sender.hpp` 里上一版留的 `cli_*` 死字段连同 `<cmath>` 一起撤掉了。

```
./build/standard_mpc configs/standard3.yaml --video-fps 10
./build/standard_mpc configs/standard3.yaml --video-width 384 --video-height 384 --video-crop 384
```

> 上一版怀疑 `Self_aim.c` 的单状态机会被控制帧里的 `0xA5` 骗到 —— **这个怀疑是错的**：
> `kind==0` 只在两帧交界处存在一个字节，字节流严格交替，浮点里的 `0xA5` 不会被当帧头扫。
> 只有「一帧被截断」才会错位。旁听里确实有少数帧短了（19/33 个间隔里 4 个），
> 但那只占 1/5，解释不了 8/9 的帧不见。**固件解析这段不用动。**

## 六、×9 能不能用（能用）

- 480×480 全 I 帧离线实测中位 **227 B**、p90 263 B、最大 275 B（上限 296）；
- 线上实测帧长 142~298 B（中位 233），227 B 落在**已经证明能上线**的区间中段；
- 所以 ×9 只影响「到了的那一帧清不清楚」，不影响到达率。

## 七、诚实记账

- 到达率 8.4 % 这一轮**还没有解决**，但位置已经收窄到 **STM32 之后那一段**
  （依据 §3.5 的 +1 连号；上一版「输入打开通道 / 7 % 占空比」的模型不成立，
  它只建立在客户端数到 210 条这一个观测上）。
- 今天**必须**同时拿到三个数（Jetson `视频帧 完整` / 旁听 `好帧头` 帧/秒 / 客户端 CBB 条数）。
  如果旁听是 4.5 帧/秒而客户端只有 0.3，那就只剩 VT03→无线→选手端，
  **固件和代码都改不了这一段**，能做的只有让「到了的那一帧」更清楚（×9 已在 yaml 里）。
- 修好之后的理想上限是发送端帧率（现在 4.5 帧/秒），不是 25/30 帧。
