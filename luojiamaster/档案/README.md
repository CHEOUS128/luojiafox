## 已被推翻的结论（别再照着做）

| 当时的说法 | 现在的事实 |
|---|---|
| 「自定义流受官方图传带宽闸门控制」 | **错**。`20261025_192645_687` 实测：官方 UDP 全程 49~69 包/s 稳定，自定义流照样 2 包/s 到达。带宽既不是必要条件也不是充分条件 |
| 「要机器人动起来/有键鼠输入才转发」 | **错**。同一会话里只有 W/A/S/D 跑动，包连续到达；更早的会话无任何输入也有包 |
| 「480×480 撑大是因为你改了 UI」 | 是编码码率问题：全 I 帧 + 小 VBV，帧超 296B 被整帧丢弃。现在回退 160×160 |
| 「客户端把重复包丢了所以出不了图」 | 客户端对重复序号只打 DEBUG 日志，仍会喂给解码器，不是原因 |
| 「`DEVICE_REMOVED` 已解决 = 客户端不会再卡」 | 最新会话 0 次 `0x887A0005`，但**只是这版没问题**，GPU 掉设备属于环境/驱动，随时可能再现 |

## 「一动就有画面」到底怎么解释（如实记录可能性）

实测已经排除：带宽、键鼠输入、云台指令、客户端渲染。
唯一没被测过的一跳是 **STM32 USART6 → VT03 → 无线**。
CH 现场体感：开小陀螺（底盘持续转）时画面几乎不断。这与「通道对静止数据流不友好 /
发送端在某些状态下串口被短暂占用」这一类**可能性**一致，但**没有证据**，所以这里只记录，
不作为结论。要证实只能烧带 `VideoForward_Debug` 的固件后读 `frames` vs `forwarded`。

## 快捷键与行为（当前版本）

| 键 | 作用 |
|---|---|
| `H` | 主画面在 UDP 官方 / 自定义流之间切换 |
| `I` | 官方 UDP 画面 180° 反转 |
| `W A S D` / 鼠标 | 操控实车（走 CustomControl 通道） |
| `CTRL` | **不要按**。见下面「已知坑」 |

## 已知坑

1. **CTRL 会整车复位**（固件行为，不是客户端）。表现：云台不再跟随、粘着底盘，图传和选手端
   一起重启，必须重开客户端。避免按 CTRL（含 Ctrl+Space 切输入法）。
2. **小窗判活 3 秒**（`kCustomVideoLiveTimeout`）。自定义流平均 2 包/秒、最长空档约 2.4 秒，
   所以按 1 秒判死会「一闪就没」。**这一项只影响显示保持，不碰接收/解码/渲染。**
3. **主画面偏好会自动切**。官方 UDP 一断就临时让给自定义流，UDP 恢复再切回来。
   手动按 H 只改「偏好」，不改当前显示。
