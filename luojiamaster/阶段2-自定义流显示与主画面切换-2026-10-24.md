# 阶段 2：自定义流为什么「一动才有画面」，以及主画面怎么才不闪

日期：2026-10-24 晚
数据来源：客户端会话 `20261024_213442_894`（21:34–21:45，601 秒）
——`robogo.log` + `network_capture.bin`（614 MB，473,572 条记录）

---

## 0. 结论先说

1. **「有画面」和「有输入」强相关，这一点你的观察是对的，而且已经量化了：**
   自定义帧到达前 0.5 秒内有键鼠动作的比例 = **91.9%**；全会话有动作的时间只占 **20.0%**。
   这不是巧合。

2. **但原因不在「运动」本身，而在丢包成段：**
   发送端从头到尾稳定在 **4.49 帧/秒**（内层序号 530→3023，554 秒），**完全不看画面动不动**。
   `成帧` 计数、单包编码、IDR 生成都是正常的 —— 「静止时不编码」这个猜想被数据否掉了。

3. **客户端长时间不出画面，是三个原因叠在一起，跟时间顺序有关：**
   ① 你的电脑这一侧，观众端收到的 300B 包有 **成段的 2~3 秒断口**（键鼠 MQTT 本身是一直通的）；
   ② 客户端只有「**解码出新帧**」才刷新「最后一帧时间」，断口里没有新帧；
   ③ 老代码用 **1 秒**判定自定义流不可用 → 断口超过 1 秒就切回官方图传，
   而官方图传恰好属于你「**按着键才动**」的那类画面，所以看起来就是「我动一下才有画面」。

4. **顺带一个必须说的事实：** 按键超过约 0.23 秒才可能收到一帧。
   会话里帧间隔 <1 秒的那 128 个间隔，中位数 **0.232 秒**；≥1 秒的 81 个，中位 **2.9 秒**。
   所以「按 H 之后车静止没有任何画面」在**最理想情况下**也要 0.2 秒才出一帧——
   这已经不满足操作手要的实时性，但它**不是这次的元凶**，只是让问题看起来更像「按了才有」。

## 1. 数据：发送端没变，变的是到达

### 1.1 发送端恒定 4.49 帧/秒

| 指标 | 数值 |
|---|---|
| 会话跨度 | 554 秒 |
| 内层序号 | 530 → 3023（前进 2493） |
| 换算 | **4.49 帧/秒**，与配置 `video_fps: 5.0` 相符 |
| 自定义帧长度 | 内层 142~298 字节，分布连续，无异常 |

关键：**这一段的序号前进速度和键鼠活动无关**。
如果编码器「静止不编码」，序号会在静止时停住——实际没有。

### 1.2 客户端只收到 4.6%

| 指标 | 数值 |
|---|---|
| 客户端收到 `CustomByteBlock` | 210 条 |
| 到达率 | 210 / 2493 = **8.4%**（按条数）；0.38 帧/秒 |
| 同一会话官方图传 | 434,686 包 = **724 包/秒** |
| 同一会话键鼠上行 | 15,393 条 = **25.6 条/秒**（贯穿全场） |

**这两个数字很关键**：
- 官方图传 724 包/秒 全通 → 带宽、无线、选手端都不是瓶颈；
- 键鼠 25.6 条/秒 也从没断过 → 这条路本身是通的。

### 1.3 相关性量化

- 自定义帧到达前 0.5 秒内有键鼠动作：**193/210 = 91.9%**
- 基线（全会话有动作的时间占比）：**20.0%**
- 有输入时段内收到 158 帧 / 152 秒 = **1.04 帧/秒**；无输入时段 0.17 帧/秒

结论：**强相关成立**，但它是「按着键的时候你恰好更容易注意到画面」+「断口成段，
而动作也是成段的」叠出来的现象，不是因果关系。

### 1.4 为什么「有输入时」更容易看到

一个容易漏掉的事实：客户端只有**解码出新帧**才更新 `last_custom_frame_time`。
自定义流 0.38 帧/秒的平均到达率，意味着任何 1 秒的超时窗口里**大概率什么都没有**。
老逻辑于是几乎全程停在官方图传上；只有动作那几秒，键鼠事件的节奏、观众端处理、
以及恰好挤进来的自定义帧重合，才让自定义流「抢到」主画面 1 秒以上，被你看见。

## 2. 改了什么（客户端）

只改了 3 个文件，**只动显示逻辑，不动解码、不动发包、不动上位机**。

### 2.1 `src/main_window.h`

```cpp
inline constexpr auto kUdpVideoFallbackTimeout   = std::chrono::milliseconds(250);
inline constexpr auto kCustomVideoLiveTimeout    = std::chrono::milliseconds(1000);  // 新：小窗/提示用
inline constexpr auto kCustomVideoFallbackTimeout= std::chrono::milliseconds(5000);  // 改：1s → 5s，主画面让位用
```

### 2.2 `src/app/application.cpp`

`UpdateVideoLayoutPreference()` 不再自己算时间，改为接收三个现成的布尔量：

```cpp
void UpdateVideoLayoutPreference(State &state,
                                 const bool udp_video_display_ready,
                                 const bool custom_video_display_ready,   // 1 秒：给提示
                                 const bool custom_video_hold_as_main,    // 5 秒：还继续当主画面
                                 bool &prefer_custom_video_as_main,
                                 bool &using_custom_video_as_main);
```

判断主画面只用「5 秒」这一档：

```cpp
const bool should_use_custom_video_as_main =
        custom_video_hold_as_main && (prefer_custom_video_as_main || !udp_video_display_ready);
```

主循环里三个量在同一次迭代、同一个 `now` 上算好，再传给 UI：

```cpp
const auto now = std::chrono::steady_clock::now();
const bool udp_video_display_ready = IsVideoDisplayReady(..., kUdpVideoFallbackTimeout, now);
const bool custom_video_display_ready = IsVideoDisplayReady(..., kCustomVideoLiveTimeout, now);
const bool custom_video_hold_as_main  = IsVideoDisplayReady(..., kCustomVideoFallbackTimeout, now);
```

### 2.3 `src/main_window.cpp`

- `ShowMainWindow()` 多一个参数 `custom_video_hold_as_main`；
- 主画面绘制改用 `main_image_available`（自定义流 5 秒、UDP 250ms）；
- 英雄部署模式的标尺也改用同一个量。

**效果：** 自定义流断包时，主画面保持最后一帧（最多 5 秒），
屏幕变「冻」，不再「消失→变成官方图传→又抢回来」。

### 2.4 模拟结果（用这场真实抓包回放）

| 超时 | 600 秒内主画面自动切换次数 | 主画面显示官方图传的时间占比 |
|---|---|---|
| 1 秒（改前） | **164 次** | 79% |
| 5 秒（改后） | **52 次** | 50% |

切换次数降到 1/3。**注意 52 次仍然不少**——这是断口本身太大（中位 2.9 秒）导致的，
不是阈值问题。要真正稳，必须把通道吞吐做上去（见第 4 节）。

## 4. 还没解决的（下一阶段）

**5 秒只是止血，不是治本。** 真要让自定义画面稳定，必须解决 0.38 帧/秒的到达率。

### 4.1 通道像是有「保活」：输入一停，几秒后就关

把到达序列按 1 秒间隔切成 82 个突发段：

| 现象 | 数值 |
|---|---|
| 突发段 | 82 个，长度中位 1 帧、最长 26 帧 |
| 多帧突发 | 34 个 |
| **多帧突发的结束点，距最近一次输入结束** | 中位 **+3.45 秒**，**0 个在输入还没停时就结束** |
| 起点完全没有输入的 多帧突发 | **5 个**（说明也会自己开） |
| 突发段内平均帧间隔 | 中位 0.296 秒 = **3.38 帧/秒**（发送端 4.49） |

读法：**通道打开时，帧几乎不丢（3.38 / 4.49 ≈ 75%）；通道关闭时，一帧都到不了。**
而且是「有输入 → 开」「输入停了 → 再过几秒关」的形状，像是有个保活计时器。
但这条链路上官方图传（724 包/秒）和键鼠本身（25.6 条/秒）都没有被限速，
所以**限流的对象只可能是 0x0310 这条自定义通道**，位置在客户端之上（VT03 / 无线 / 选手端）。
这一条是**推断**，还没有直接证据。

### 4.2 下一轮实测（决定性的，很便宜）

固定发送端 5 Hz 不动，只改变「有没有键鼠输入」，各跑 60 秒，数客户端收了多少条：

1. **A 组（静默）**：什么都不按，60 秒；
2. **B 组（持续输入）**：一直小幅左右点鼠标 + 按住 W/A/S/D 之一，60 秒；
3. 客户端看 `CustomByteBlock(rx)` 条数（`dumpcap.bat` 或 `robogo.log` 里搜 `topic=CustomByteBlock`）。

判读：
- **B 组条数 ≫ A 组** → 保活假设成立，问题在选手端/VT03；
  解决方案是让人为制造「假输入」（客户端按固定节奏发一条无害的
  `KeyboardMouseControl`，按键位全 0、鼠标位移也为 0；但这需要现场验证空包算不算「有输入」）。
- **两组差不多** → 和输入无关，回到纯粹的通道吞吐问题，改测发送速率拐点：
  `video_send_rate_hz` 从 5 提到 10、20，看客户端收到多少。

### 4.3 在此之前

不要调帧率/画质/码率——优先级仍是先跑通。

### 与 0x0310 / CustomByteBlock 的关系

协议 PDF《RoboMaster 2026 高校系列赛通信协议 V2.0.0》写死：

- `0x0310` 数据长度固定 **300 字节**，走图传链路；
- `CustomByteBlock` 最大 **2.4 kbit（300 字节）**，频率 **50 Hz**，由机器人经图传链路发到选手端再转 MQTT。

也就是说 50 Hz × 300 字节 = 15 KB/s 的协议能力，**协议上限远高于我们现在 1.4 KB/s 的用量**；
现实瓶颈不在协议文本。
