## 一、三条视频链路（互不干扰，各自独立）

客户端里同时存在三条视频路径。**它们共用同一块 GPU 纹理槽位体系，但队列、解码器、
线程都是分开的** —— 改其中一条不会连带另一条，这是压片战争最需要知道的结构前提。

```
                   ┌──────────────── 官方图传（主路）────────────────┐
 选手端 UDP 3334 ──► VideoStreamReceiver ──► VideoShardsManager ──┬─► VideoDecoder(HEVC) ──► 主纹理
                   │  (20MB socket buf)      (乱序缓存 20 帧)      │
                   │                                              └─► raw_frame_callback ──► 队友转发
                   │
                   └──────────────── 第二视角（自定义流）──────────┘
 选手端 MQTT CustomByteBlock ──► CustomByteBlockVideoDecoderWorker ──► 解码线程 ──► 二视纹理（H 键切）
                                (队列 256，满了直接报错不入队)

                   ┌──────────────── 队友视角（2027）──────────────┐
 对端 TCP 47700 ──► TeammateVideoReceiver ──► HEVC 软解 ──► 队友纹理（K/L/滚轮）
```

### 1.1 官方图传（UDP 3334）

- 收包：`VideoStreamReceiver`，`receive_buffer_size` 设 **20 MB**，每包一收就交给分片层。
- 分片头 8 字节**大端**：`u16 frame_id | u16 shard_id | u32 frame_bytes`，后面跟负载。
- 分片管理：`cache_frame_size = 20`；`shard_id` 必须稠密 `0..N-1`；
  按 `collected_frame_bytes == frame_bytes` 判齐；齐了按 shard 顺序拼成一帧。
  - `delta_frame_id < -20` → 判定为陈旧数据，`reset_stream_state()`。
  - `frame_id` 回绕用 `delta_frame_id <= -100 && frame_id < 20` 识别。
  - 重复分片会计账（`delete[]` + 扣字节），不会重复拼接。
- 解码：`VideoDecoder`，优先 `hevc_cuvid`，失败回退软解。等 IDR / 参数集（NAL 32/33/34）才认为「流就绪」。
- **原始码流旁路**：分片齐了、解码**之前**，原始 HEVC 会通过 `raw_frame_callback`
  交给 `TeammateLink::push_frame()`。所以队友画面和主画面是同一份字节，没有二次编码。

> 这一条是**纯接收**，客户端不控制它的码率。压片战争要动的是下一条。

### 1.2 第二视角 / 自定义流（MQTT `CustomByteBlock`）

**线格式（客户端里是真源码，不是推测）**：

```
CustomByteBlock.data  →  300 字节定长 transport packet
  [0:2]  u16 BE  内层包长度 inner_len（= 2 字节序号 + H.264 字节数，≤298）
  [2:4]  u16 BE  内层序号 inner_seq（跨帧递增，u16 回绕）
  [4:..] H.264 Annex-B 字节（长度 = inner_len - 2）
  剩余补 0
```

- **两种线格式都认**，自动探测并回退：
  - `SerializedPacket`：整个 300 B 就是 `[2B 序号][H.264]`（老格式）。
  - `TransportBundle`：`[2B 长度][2B 序号][H.264]` 可以首尾串联多段，
    长度 0 且后面全 0 = 填充结束。**这是现在用的格式。**
    例：串两个内层包时每段是 `[2B 长度][2B 序号][146B H.264] = 150B`，两段正好 300B。
  - 探测规则：整包正好 300 B → 先按 bundle 试；否则看首 2 字节像不像合法内层长度。
    解析失败会自动换另一种格式再试一次，两种都失败才丢弃。
- **解码器是 H.264 软解**（`AV_CODEC_ID_H264`），不是 HEVC。
- **丢包策略**：内层序号不连续 → 打 `丢包（等下一个关键帧）`，置 `waiting_for_keyframe`，
  **跳过后续非 IDR 帧**，直到下一个 I 帧。这样最多花屏一个 GOP，不会无限花屏。
  - 短时间内的乱序/重复（`backward_distance ≤ 2048` 且距上一包 < 800 ms）只打 DEBUG，**仍送解码器**。
  - 空闲超过 800 ms 或倒退超过 2048 → 判定序列重同步，同样等关键帧。
- **线程模型**：`CustomByteBlockVideoDecoderWorker` 独立解码线程，输入队列 256，
  入队失败（满了）会打 `CustomByteBlock 解码队列入队失败`。解码结果进
  `custom_video_frame_queue_`，主循环取**最新一帧**（旧帧直接丢，不排队显示）。
- **解码线程里的硬上限**：
  - 单包 > 300 B 直接判非法（`wire packet exceeds 300 bytes`）。
  - 单个访问单元 > `max_access_unit_bytes = 512 KB` 丢弃并重置解码器。
  - 单帧像素上限 `4096 × 4096`。
- **显示侧三档超时**（`main_window.h`）：
  - `kCustomVideoLiveTimeout = 3000 ms` —— 双画面模式下，超过 3 s 没新帧只把这一格标不可用。
  - `kCustomVideoFallbackTimeout = 5000 ms` —— 主画面模式下，超过 5 s 才让位给官方 UDP。
  - `kUdpVideoFallbackTimeout = 250 ms` —— 官方 UDP 判活的宽松档。
  - **这三个数只影响「显示保持」，不碰接收/解码/渲染**。改它们不会让画面更流畅。

### 1.3 队友视角（TCP 47700）

- 线格式（大端）：
  ```
  握手 8 B：'R''M''T''M' + version(1) + flags(1) + reserved(2)；flags bit0 = 发送端画面倒置
  每帧：payload_bytes(4) + flags(4) + payload
  ```
- 每帧都带 flags，所以**任一方按 I 翻转，对面立刻跟着翻**，不用重连。
- 晚连上来的一方缺 VPS/SPS/PPS，服务端在握手后**先把缓存的参数集补发一遍**。
- 发送队列深度 8，满了丢最旧；`TCP_NODELAY`；断线 1 s 重连，连接超时 2 s。
- **监听端口占用是现场常态**（第二个实例、别的客户端）：自动往上试 `47700 + 0..9`，
  都占不到就每 5 s 重试。
- 解码：独立的 `TeammateVideoReceiver`，**HEVC 软解**，队列 16、满了丢最旧，
  参数集变化时重建上下文。**不用主路的 `VideoDecoder`**，原因写在头注释里：
  主路解码器没有 drain、cuvid 拿到不完整参数集会直接终止进程。
- 角色：`队友视角.ini` 里 `role=A/B`、`peer=host:port`、`listen=port`；
  优先级 `--teammate-*` > `peer=` > `role=` > 内置默认 A（找 `10.77.0.2:47700`）。
  `peer=off` 表示彻底关闭（不出小窗、不监听、不注册 K/L/滚轮）。
- 标题条标签：`[默认A]`（没写过 ini）→ 点一下变 `[B]` 并写回 ini；
  写过之后显示 `[A]` / `[B]`。两种都算对。

## 二、输入链路（键鼠 → 实车）

### 2.1 `KeyboardMouseControl`（75 Hz）

- 采样间隔 **13 ms**（`publish_interval`），只有 `Esc` 切进比赛模式后才发。
- **按键必须用 `IsKeyDown`**，不能用 `IsKeyPressed`。后者只在按下的那一帧为真，
  而这里 75 Hz 反复采样 → 原版 ACE 键盘掩码恒为 0。这是本项目最关键的一处修复。
- 位掩码（32 位 proto 字段，实际用到低 16 位）：

  | bit | 键 | bit | 键 |
  |---|---|---|---|
  | 0 | W | 8 | R |
  | 1 | S | 9 | F |
  | 2 | A | 10 | G |
  | 3 | D | 11 | Z |
  | 4 | Shift（左右） | 12 | X |
  | 5 | **Ctrl（左右）** | 13 | C |
  | 6 | Q | 14 | V |
  | 7 | E | 15 | B |

- 鼠标：`mouse_x`（右正）、`mouse_y`（**取反后发送**，所以屏幕向上 = 云台上）、`mouse_z`（滚轮）。
  位移用「平台层每帧回中前累积的真实位移 × 灵敏度」，避免光标顶到边缘后丢输入。
- 灵敏度默认 **0.4**，范围 0.05–3.0；滑块在**登录面板上常驻**，不在设置面板里。
- **`Ctrl` 是雷区**：固件把 Ctrl 当整车复位（按住约 2 个控制周期 → `reset_flag=1`）。
  客户端只是如实上报，**不要在客户端侧拦截**（那会掩盖固件行为）。现场协议：不要按 Ctrl。

### 2.2 `CustomControl`（10 Hz）

- 10 字节：5 个敌方机器人血量（`u16` × 5，小端）+ 空中支援呼叫标志 + 倒计时冷却字节 + 调试计数。
- 只要 `RobotStaticStatus` 和 `GlobalUnitStatus` 都有数据才发；间隔 **100 ms**。
- 与视频链路**完全无关**，不要拿它当「保活」手段（历史结论，见 §六 已作废第 2 条）。

### 2.3 其它上行

- `MapClickCmd`：标记模式下点地图触发，一次一条，发完自动退出标记模式。
- 登录面板上登录后的四行操作（装弹部署 / 复活 / 标记 / 飞镖与空中支援）走 `PublishProto`。
- 「进入比赛」按钮**只调 `enter_game_mode()`、不发 MQTT**；和按 `Esc` 是同一条路。

## 三、UI 与状态机

- **登录面板**（750×500 居中）：连接状态 → MQTT 服务端输入 → 队伍（红/蓝）→
  机器人（英雄 / 工程 / 3号步兵 / 4号步兵 / 云台手）→ 登录目标（`红队 / 英雄 (ID 1)`）→
  登录后才出现的四行（装弹部署 / 复活 / 标记 / 飞镖与空中支援）→ **鼠标灵敏度滑块（常驻）** → 登录 / 进入比赛。
- 机器人 ID：红方 `{1,2,3,4,6}`，蓝方 `{101,102,103,104,106}`。MQTT `clientID` = 机器人 ID 字符串。
- **`Esc` 切比赛模式**：进入后 `ClipCursor` + 隐藏光标 + 隐藏登录面板 + 显示准星 + 开始发键鼠。
  「进入比赛」按钮也是同一条路。**没有 `P` 设置面板** —— 那是官方选手端的键；
  本客户端的灵敏度滑块常驻登录面板。
- **`H` 切主画面**：官方 UDP ↔ 自定义流。它只改「偏好」；实际显示还看两路是否可用：
  自定义流可用（5 s 内有过帧）且偏好为自定义 → 主画面用自定义；
  否则官方 UDP 优先；UDP 断了临时让给自定义流。
- **`I` 主画面 180° 翻转**：GPU UV 翻转（不是 CPU 逐像素），同时通过队友链路 flags 同步给对面。
- **`K`** 队友小窗折叠/展开；**`L`** 队友画面占主画面（滚轮 1x–4x）。
  只有队友视角启用时才注册这三个。

## 五、日志里怎么看

会话目录 `程序/logs/<YYYYMMDD_HHMMSS_mmm>/robogo.log`（relative path，`ROBOGO_LOG_ROOT` 可覆盖）。

**每秒一行的视频探针**（最有用的一行）：

```
视频探针 udp_in=+21 custom_in=+0 udp_total=286 custom_total=0 udp_ago=48ms custom_ago=... loop=21/s |
         cbb pkt_in=+0 pkt_taken_total=0 frames_out=+0 bytes_in=+0
```

判读：`udp_in` = 官方图传解出帧/秒；`custom_in` = 自定义流解出帧/秒；
`cbb pkt_in` = 每秒进了几个 CustomByteBlock 包；`frames_out` = 解码出几帧。
**`pkt_in` 涨而 `frames_out` 不涨 = 包到了但解不出来**（等关键帧 / 坏包），不是链路问题。

**队友探针**（只在启用队友视角时出现）：

```
队友探针 发=…帧/…KB 丢=… 队列=… 连=… | 收=…帧/…KB 连入=… | 解=…帧 重建=… 错误=… WxH peer=…
```

**关键日志行**：

| 行 | 含义 |
|---|---|
| `队友链路：正在监听端口 47700` | TeammateLink 建起来了；**没有这行 = 队友功能没启用** |
| `队友链路：监听端口 … 被占用（…），自动往上换一个` | 端口冲突，已自动换，但对面连的仍是 47700 → 收不到 |
| `CustomByteBlock 视频流已开始` | 自定义流第一次解出帧 |
| `CustomByteBlock 丢包（等下一个关键帧）` | 内层序号断了，正在等 I 帧 |
| `CustomByteBlock 输入包格式切换 old_format=… new_format=…` | 线格式探测换了一次，确认发送端用的是哪种 |
| `视频探针 … cbb pkt_in=+0` | **一个包都没到**，先查发送端，不要改客户端渲染 |

## 六、作废结论（别再照着做）

这些是走过的弯路，留着是为了不再走一遍。**新阶段不要引用它们。**

| # | 当时的说法 | 现在的事实 |
|---|---|---|
| 1 | 「自定义流受官方图传带宽闸门控制」 | **错**。`20261025_192645_687` 65 s 实测：官方 UDP 全程 49–69 包/s 稳定，自定义流照样 1–5 包/s 到包。带宽既不是必要条件也不是充分条件 |
| 2 | 「要机器人动起来 / 有键鼠输入才转发」 | **错**。同会话只有 WASD 跑动，包连续到达；更早会话无任何输入也有包。`CustomControl` 频率高只是巧合 |
| 3 | 「0x0310 通道有约 0.2 s 的窗口，帧要落进窗口才能过」 | **错，是解析 bug**。当时把 protobuf 的 `0x0A + varint` 当成 300 B data 的起点，长度/序号全错位。正确偏移下序号单调、无门控 |
| 4 | 「`480×480 撑大是因为改了 UI`」 | 是编码码率问题：全 I 帧 + 小 VBV 压不进 296 B，整帧被丢。现已改回小分辨率 + I+P 拆包 |
| 5 | 「客户端把重复包丢了所以出不了图」 | 客户端对重复序号只打 DEBUG，**仍会喂给解码器** |
| 6 | 「STM32 USART6 → VT03 那一跳已经排除」 | **打折**。灌包测试时若通道本来就是开的，不能证明无条件转发。**这一跳至今没有干净的对照实验** |
| 7 | 「CH340 抓包能代表 STM32 实际发出多少」 | 不能。CH340 在 921600 下自己就丢字节；「每帧缺一点」只说明 TX 线路上丢，不代表 USB 侧 |
| 8 | 「一帧一包是最终形态」 | 只是**过渡形态**。I+P 拆包版已落地，单包模式保留为回退档 |
| 9 | 「`DEVICE_REMOVED` 已解决 = 客户端不会再卡」 | 最新会话 0 次 `0x887A0005`，但 GPU 掉设备属于环境/驱动，随时可能再现 |

## 七、压片战争的**已知接口**（只列事实，不展开方案）

下面这些是下一阶段会碰到的、**客户端这边已经定死**的东西。方案留到讨论时再展开。

**客户端侧的包格式解析是固定常量**：

```cpp
constexpr std::size_t kSerializedPacketHeaderBytes = 2;   // u16 BE 序号
constexpr std::size_t kMaxSupportedPacketBytes   = 300;    // 单包硬上限
constexpr std::size_t kTransportLengthPrefixBytes = 2;     // u16 BE 内层长度
constexpr std::size_t kMaxInnerPacketBytes       = 298;    // 300 - 2
```

- 内层 `[2B 长度][2B 序号]` 的**顺序不可换**：长度在前，序号在后。
- 一个 `CustomByteBlock` 的 300 B 里，**串包只会减少 H.264 净载荷**：
  单包能给 296 B；串两个各 146 B 的内层包，合计只有 **292 B** —— 比单包少 4 B。
  所以「多个内层包塞进同一个 300 B」不带来任何容量增益，多包一帧必须靠**多个 `CustomByteBlock` 包**，
  不能靠「一个包里串多条」。
- 客户端解码器是 **H.264 软解**，解析器 `av_parser_parse2` **跨包保留状态**，
  所以「一帧拆多包」在客户端侧天然支持（发送端要保证同一帧的包按序、连续、不被别的帧插队）。
- 发送端「整帧原子释放」已经实现：令牌够 N 个才一起放，不够就攒着。
  这条是 I+P 拆包版的关键，压片战争若改包结构，这个语义要保住。

**与压片战争直接相关的既有数字**（来自 `autoaim/my_lf_INF_20261025`，是真车发送端）：

| 项 | 值 | 出处 |
|---|---|---|
| 协议上限 | 50 Hz × 300 B = **15,000 B/s ≈ 120 kbps 毛重** | 协议 V2.0.0 表 1-41 |
| 发送节拍 | `video_send_rate_hz: 40.0`（包/秒），令牌桶 85% = **34 包/秒** | `standard3.yaml` |
| 码率预算 | `34 × 296 × 8 ÷ 1.35 ≈ 59.6 kbps`（日志显示 59） | `video_sender.cpp:226` |
| 当前档位 | `192×152` 全视野、GOP 10、灰度、I+P 拆包、`max_frame_packets: 8` | `standard3.yaml` |
| 实测 | 60 kbps → 35.5 包/秒（88.8% 桶）、中位 312 B、最坏一帧 6 包、SSIM-Y 0.9853 | `档案/包率85%+灰度版` |
| 结构开销 | SPS 21 B + PPS 4 B + 两个 IDR 切片头 ≈ 10 B 固定 | `档案/阶段3` |
| 灰度真实价值 | 同码率亮度 SSIM **+0.0012**（不是网上说的省 2/3） | `档案/包率85%+灰度版` |

> ⚠ **一处需要先对齐的口径**：压片战争说的「300 字节、50 Hz」，按协议换算 **毛重**是
> 15,000 B/s（120 kbps）。但真正能当"码率"花的是扣掉每帧封包开销后的**净载荷**，
> 而且客户端每包固定吃 4 B（2 B 长度 + 2 B 序号）。当前发送端用的是 40 Hz（不是 50 Hz）
> 的令牌桶。**开始设计方案时先把这三件事定下来**：目标是不是 50 Hz、单包算不算 300 B 毛重、
> 每帧至少要吃多少字节的封装开销。否则预算会算错 20% 以上。
