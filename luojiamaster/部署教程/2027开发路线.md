# luojiamaster 2027开发路线

本版重新复核：2026-11-18；仓库 `c0d8677dba0cfb091c0c935034b40238926cce20`。本文件是待分阶段实施的方案，不是新版功能已经完成的说明。现有程序怎么运行仍看[客户端README](../README.md)，换电脑、换车和DMA/Jetson经验看[部署教程](README.md)。以后在这一份路线里更新状态，不为每次讨论再建一份规划。

**2026-11-18 里程碑 · 2027 联盟赛单屏基础版已可交给队员试用（M3）。** 一个 EXE 有三个入口。2026 超级对抗赛保留实车参考版本；2027 高校联盟赛可用步兵或重装身份进入同一套正式、试用比赛界面，切换两路本车视频，看新地图、双方控制度、六台车血量和倒计时；2027 超级对抗赛目前保留基础界面。2026 工业相机全链路已有实车记录。本版的 2027 比分、换队和队友小窗在 Windows 本机验证，现场官方联调另验。

**现阶段的实车验证入口是「2026 超级对抗赛 → 正式登录」。** 现有裁判端和选手端只具备 2026 实车联调条件。图传显示、窗口操作和队友互看等跨赛季功能，开发时共用实现，并在 2026 入口安排验证。下一阶段的队友自动配对也要能用现有设备做双机有线训练测试。联盟赛控制度、3V3 地图和按 2027 身份开放的岗位，先用 2027 入口的回放核对，真实裁判数据待同赛季设备联调。

## 1 先做哪一版，队员打开后是什么样

**参赛范围：联盟赛只做 3V3。** 选择联盟赛后直接选重装或步兵，不再加选赛项的页面。超级对抗赛保留独立的后续路线。

**首个交付叫「2027 联盟赛 · 3V3 离线体验版」。** 一位没看过教程的队员，在普通 Windows 笔记本上打开一个 EXE，能自己选步兵，看一段真实双路录流，认出哪路是本车工业相机，看到暂停、换边、下一局。画面和比赛消息分别标明“历史录流”和“2027样例”。这一小段先做通，后续每个版本都有同一把尺子。

一个程序保留 2026 实车入口，两个 2027 赛事分别进入，登录后按岗位换界面。不开三个兵种 EXE。首次启动欢迎页用珞珈狐队标、产品名、赛事卡片；RM标识使用前核对允许的素材与场合。第二次打开记得上次选项，但让队员确认本场身份。选择赛事自动过滤岗位；确认一次后，比赛界面和队内身份共用这个选择。离线体验无需登录；正式身份冲突要提示，不抢号、不冒用。未做完的赛事注明进度，不把空界面当功能。

| 队员实际要做什么 | 建议打开后看到什么 | 优先级 |
| --- | --- | --- |
| 本队参加 UL 3V3 | 单屏就看全。步兵首屏是本车视频，比赛时间和队友入口固定；重装仍是同一套操作习惯，可切工业相机大画面 | 首发；正式联调单独验收 |
| UC 重装、步兵 | 步兵一屏可用；重装有额外屏时，可一屏看完整工业相机画面，另一屏放地图、比赛时钟和状态；屏幕用途可对换 | UL基础稳定后；先做真实双屏试验 |
| UC 指挥席 | 首版先做二维赛事总览＋按来源命名的队友画面。额外屏可展开一路画面；某路断开只影响该卡片。三维先做离线场馆浏览 | 确认席位数据和显示边界后开放；不作为 UL 发布条件 |

**7V7 顶栏安排**　按 2027 超级对抗赛规则 §5.6.1、§5.8，基地主条初始 10000，R、B 两座前哨站各 1000。前哨站以场地位置命名，当前归属单独显示。双方基地均存活且时间耗尽时先比累计控制度，要给这个分数留位置。通信协议 §2.2.4 将基地阵地控制状态与基地血量分开，旧字段名中的 shield 不应画成护盾血条。本轮交付联盟赛顶栏，7V7 进入后续开发。

**留住已经验证过的东西。** 26全向轮步兵是实测参考车，自定义客户端不绑车型。保留现用EXE和当前部署教程作为回退，保留 B 档彩色完整视野、Jetson 自启动、云台 DMA 整包转发的经验。不为改登录、地图或屏幕布局重编固件、重做压片。当前真实录流的回放测的是电脑显示；不能用回放结果宣称车到屏延迟。现存长测观察项以客户端 README 为准。

## 2 已核实的规则和硬件变化

下表页码均为手册页脚印刷页；本地比赛规则、制作规范与通信协议的物理页为印刷页加1，参赛手册单独按其页码。来源及版本在第15节。官方后续更新需重新核对，不能将本文件视为永久规则。

| 项目 | RMUL | RMUC | 对软件的影响 |
| --- | --- | --- | --- |
| 主要操作岗位 | 3V3重装1号、步兵3号各1操作手；哨兵7号全自动、无操作手。 | 重装1名、步兵2名、指挥手1名，另有空中安全员 | 登录页按赛事提供合法岗位，不把所有协议ID都变成可选操作席 |

| 额外显示器 | 规则未承诺UC同样的额外屏 | 重装操作手、指挥手各额外提供1台1920×1080、仅HDMI输入的屏，并提供HDMI公头线用于连接自定义终端 | UC可规划自有终端屏＋官方额外屏；UL以单屏完整可用为基本要求 |
| 操作席关系 | 两个主要人工操作席 | 地面操作手与指挥手有物理隔离 | UC需要真正的有线协同，不能靠直接看别人屏幕 |
| 终端互联 | 允许终端之间有线连接通信 | 同样允许 | 可以共享合法取得的画面、状态、任务，不由此推导跨车键鼠接管 |
| 官方口 | 每台官方操作设备至多1个RJ45，UL设备节写1GbE | 同样至多1个RJ45 | 官方接入与队内互联分别布线、选网卡，不能把多个官方固定地址网段直接桥接 |

### 2.1 双屏到底怎么接

官方原有屏连接官方电脑；额外HDMI屏可连接我们的终端。不要把“现场有两块官方屏”理解成“我们随意接管官方电脑与全部显示输出”。建议使用有自身屏幕的笔记本作终端，再把额外HDMI屏接到这台笔记本；如果采用无屏主机，需要另行确定自有主屏、视频输出和供电。

Windows使用“扩展这些显示器”，才能放不同内容；“复制”只会在两块屏显示同一张画面。程序检测实际屏幕，而不是写死“显示器2一定存在”。外接屏断开时，重要面板回到主屏；不同分辨率、缩放比例、屏幕左右位置均需覆盖。

硬件先登记，再选最终负载：

| 必须登记 | 为什么要知道 |
| --- | --- |
| 终端CPU、GPU、显存、内存、驱动和系统版本 | 判断能同时解几路视频、三维能画多复杂 |
| 本机屏与外接屏尺寸、分辨率、刷新率、缩放 | 决定字号、视频区域、地图比例与跨屏行为 |
| HDMI/DP/USB-C实际视频输出能力 | 有USB-C口不代表一定能输出视频；转接器也要实测 |
| 独立有线网卡数量与速率 | 官方口与队内口应明确分开，列出转接器及驱动 |
| 终端、交换机和扩展器供电及续航 | 规则不允许擅自用官方设备电源给自备设备供电 |
| 正式输入设备、桌面可放置范围、线缆长度 | 确定接线能落地、没有遮挡或拉扯 |

终端制作还要核S46–S50：30V、600×600×600 mm收纳、桌面固定方式、裸露导线、官方接入预检和无线收发限制。S60开源操作系统条款的对象是“机器人上搭载的运算平台”，不能据此直接要求独立Windows终端整体改Linux。当前继续以Windows主线规划，Linux是后续有明确需求才评估的部署目标。

### 2.2 已发现、必须向官方或实机确认的事项

- UC指挥手正式接入空中系统/飞镖时，实际选手端版本、clientID与权限组合；是否能在一个终端会话中完成相应职责。不能造一个“指挥手ID”，也不通过重复登录挤掉本车会话。
- UL哨兵表列有终端，但没有操作手且要求全自动，其终端摆放、观察权限和登录用途需确认；初版不新增“哨兵操作手”。
- 笔记本内置无线模块的检录处理方式、队内交换机与线缆布置、供电和外接设备条件；终端S50不能直接套用雷达S99的禁用例外。
- UL无需官方定位时，哪些位置字段有真实有效值；没有数据就显示未知。
- 制作规范对42mm模块仍有“七分钟”备注，而UL是五分钟，执行时机按UL专章核对并提问。
- 2027协议雷达消息示例存在结构不完整问题；以官方字段表准备兼容层，拿实际官方数据或勘误定案。
- `robot_bullets`弹量数组在本版协议中未像血量那样明确完整顺序，取得可靠定义或实际包后再按身份显示，不凭长度猜。
- 已找到11月更新答疑的公开转录，其中#447讨论指挥席有线取队友信息，#516讨论机库链路无图像但可收发数据。官方轻流原始链接本轮无法读出正文，列为待核线索，不据此承诺额外视频源。链接见第15节。

## 3 欢迎页、身份与开局流程

### 3.1 推荐的队员操作顺序

```text
欢迎使用 luojiamaster
  珞珈狐标识＋RM标识＋简洁背景
            ↓
选择赛事：高校联盟赛 / 超级对抗赛
            ↓
选择岗位：该赛事允许的重装 / 步兵 / 指挥手
            ↓
确认身份和设备：红蓝方、号码、官方连接、主副屏预览
            ↓
连接并核对身份、画面和状态 → 自动加入本队协同
            ↓
进入工作台 → 操作手明确启用本车操控
```

“选岗位”放在登录之前，决定用哪套界面；“确认身份”紧接在同一条开局流程里，决定真正连接哪个官方身份。对UL重装/步兵可以根据岗位填好号码，让用户确认红蓝方即可；UC两名步兵还要选号码。指挥手先选择工作台，官方业务连接按已核实通道配置，不强填一个地面机器人ID。

登录成功后同步到队内协同，无需再找隐藏菜单选A/B。身份确认来源要明确：本地选择、官方反馈和队内声明分别保存；若官方没有可靠身份回显，显示“已连接，身份待核”，不要自动声称服务器已验证。

再次使用时提供“按上次配置进入”，显示赛事、岗位、阵营、号码和屏幕缩略图。换赛事、换车、换岗位必须退出本次控制状态，清空按键与未完成动作，再建立新会话。配置可记住，上一局动作不能重放。

### 3.2 界面要漂亮，但步骤要少

- 欢迎页有明确的luojiamaster和珞珈狐品牌；RM标识使用真实授权/官方发布素材，队标使用队内原图。先核素材出处，不临时生成近似标志当正式标志。
- 制作规范S42不允许终端硬件、软件和UI展示赞助商品牌、标识或广告语。欢迎页使用队伍与赛事视觉，不加入赞助广告。
- 深色底、少量强调色、统一字号与留白；红蓝队色只表达阵营，绿色/黄色/红色分别表达正常/注意/故障，不靠颜色单独区分。
- 所有岗位沿用相同的顶部连接区、底部提示区和操作反馈；岗位差异放在中间工作内容。
- 首次用户无需输入端口、线程数、协议版本；这些放进“连接设置”。仍保留一处能查看真实连接、来源和版本的维护入口。
- 提供“离线体验”入口，用固定样本演示角色布局；醒目标明演示，禁止演示模式发布车辆命令。
- 开局无强制动画和网络加载；所有图标、地图、字体随发行包提供，赛场断网仍能启动。

## 4 不同岗位的工作台

以下是首轮推荐布局，需让实际操作手看静态稿后再定位置，不把个人喜好写死进底层。

| 岗位 | 主屏主要内容 | 第二屏/辅助区域 | 首版重点 |
| --- | --- | --- | --- |
| UL步兵 | 本车主视角，血量、热量、弹量、功率/模式、关键提示 | 单屏内可收起的小地图、队友视角；双屏为自有设备可选能力 | 看得清、操作连续、少遮挡 |
| UL重装 | 驾驶/射击时主视角；装配时可切工业相机为重点 | 工作台任务状态、机械臂反馈、队友掩护提示；单屏必须完整 | 模块对接需要什么画面和状态，就展示什么 |

| UC重装 | 主视角＋驾驶/射击状态；进入装配模式可交换重点画面 | 官方额外屏：独立工业相机窗口＋少量机构状态；地图/任务可停靠 | 双屏随驾驶/装配任务切换，保留明确输入对象 |
| UC指挥手 | 战术地图、队伍状态、资源窗口、任务与事件 | 官方额外屏：重点队友画面，其他来源按需预览/切换 | 先二维能指挥，再加入三维高差与可视区域 |

UC重装可以采用用户提出的“工业相机独立一屏，另一个窗口放地图与信息”。建议主屏仍保留一键返回主视角，因为驾驶和装配对画面的需求不同。先提供“驾驶、装配、态势”三个预设，再允许调整面板，避免让新队员面对空白画布自行拼界面。

两屏共享应用会话，窗口标题显示同一岗位；具体官方业务连接由核心统一管理。视频窗、地图窗、任务窗不是三个登录实例。工业相机放到1080p屏不会增加原始320×256画面信息：保留等比显示、1:1和放大选项；放大不标成画质提升。

机械臂的“命令已发送、控制板已接收、机构已到位、裁判确认装配成功”分开显示。UC指挥手的“发出任务、队友确认、执行中、完成/失败/取消”也分开显示，不能点击按钮就直接变成功。

## 5 建议的软件结构

继续使用现有C++/视频/显示基础，先拆清职责，逐步替换界面。暂不同时更换整个UI框架、视频解码器和官方通信栈。

```text
统一启动与配置
  ├─ 赛事规则包：2026兼容 / 2027 UL / 2027 UC
  ├─ 岗位配置：重装 / 步兵 / 指挥手
  └─ 设备配置：单屏 / 双屏 / 网卡 / 输入设备
             ↓
共享会话核心
  ├─ 官方协议适配 → 有来源、有时效的比赛/机器人状态
  ├─ 主视频 / 第二视角 / 队友视频 → 有界队列与最新图像
  ├─ 队内有线协同 → 身份、状态、任务和画面
  ├─ 控制出口 → 身份、权限、焦点、模式、频率检查
  └─ 记录与回放 → 数据可复核，回放没有控制出口
             ↓
岗位工作台＋独立辅助窗口
  ├─ 2D地图、视频、机构、资源、任务
  └─ 可选Unity 3D显示进程（从核心取状态）
```

### 5.1 三种配置分开管理

赛事决定“允许做什么、消息怎么解释、用哪张场地”；岗位决定“优先看什么、能发什么动作”；硬件决定“显示到哪、同时开多少路”。三者组合生成工作台，避免每种组合再复制一份代码。

建议在客户端源码内部逐步整理为 `app/session`、`protocol`、`rules`、`video`、`peer`、`control`、`ui`、`maps`、`tests` 等模块；这是职责划分目标，不要求一次性搬动全部现有文件。每次拆分保持已有回放可运行，再迁下一块。

### 5.2 一处负责发控制，其他窗口只提出请求

所有上行最终经过同一个检查入口，包括键鼠、升级、地图命令、装配、CustomControl，以及以后机械臂/飞镖请求。检查当前赛事、正式身份、业务权限、比赛阶段、控制模式、数据新鲜度、频率与重复动作。

- 辅助视频窗默认观察用途；鼠标拖动地图/拖动窗口不变成云台转动。
- 失去控制焦点、Alt-Tab、关闭窗口、断线、切角色时清空本地按住状态；在可用且被允许的链路上按协议表达释放，失联后的安全停机仍需车端超时逻辑。
- 鼠标按现协议累计位移语义处理：松键与丢弃未提交的新增输入，不等于把累计坐标突然归零；多窗口也只采样一次，避免制造云台位移突变或重复累计。
- 一个逻辑控制所有者。需要在重装装配面板操作时明确切换输入模式，退出时释放旧模式，不让两窗同时控制。
- 重连只恢复状态订阅和画面，不补发旧的飞镖发射、装配或机械臂动作；一次性动作有请求编号与结果。
- 请求编号用于本地/队内追踪；官方DartCommand、AssemblyCommand没有通用请求编号和逐次动作ACK，不能自行添加字段。没有官方逐次回执时显示“已提交、结果待确认”；自定义机构协议可以与电控另行约定确认。
- 已排队但尚未发出的命令带会话代次，真正发送前再核一次。退出或换车后取消旧代次，不能只在点击按钮时检查身份；已经发出的命令不宣称能靠清UI追回。
- 本车现有13 B自动CustomControl要变成明确的车型载荷配置。不能登录其他车后自动把敌方血量格式送进对方机械臂协议。

### 5.3 多窗口的实现顺序

先将单窗口中的状态、网络、控制和绘制解耦，再增加第二个原生窗口。一个来源只解码一次，多个窗口引用同一不可变帧，GPU资源用完后回收。各窗口处理尺寸、最小化、DPI和显示器变化，不能关副窗就停止本车会话。

输入只由当前持权主窗采样一次。每个窗口独立统计成功呈现和画面年龄；共享纹理等所有引用它的窗口GPU工作完成后才能回收。副窗等待、最小化或关闭不能无限阻塞主窗。

当前资源池、帧队列和等待恢复已经有基础；增加窗口意味着新的显示交换链、资源寿命和焦点组合，需要专项验证。即使是两个进程，也共享GPU，不能将进程隔离写成性能完全互不影响。

Unity首版建议做可选独立进程，通过版本化的本机通信只取场地、状态与标记。需要回传点击时只交“用户意图”，由主客户端审核后发送。Unity不拿车辆控制连接，也不自己登录官方端。先不做复杂窗口嵌入、跨进程GPU纹理共享；三维退出时二维工作台继续可用。

## 7 队友通信 从A/B变成跟身份走

### 7.1 网络结构

```text
各自官方端 ─ 专用网口 ─ 各自luojiamaster（本车控制不绕指挥席）
                              │另一有线网口
                    队内有线网络 / 交换机
                     │        │         │
                   重装     步兵      指挥手（UC）
```

UL两席可用独立有线直连；UC多席建议用单独队内交换网络。具体设备和走线在现场条件确认后定。每台机器的官方接口同为12.x专线时，不能把这些接口接成同一个广播网络。队内服务明确绑定自己的网卡，不启用系统网络桥接、互联网共享或包转发。

上图沿用当前已经跑通的官方接入方式。2027规则允许自定义终端经操作间接口接入赛事引擎，最终是否继续由官方选手端中转、官方接口测试怎样进行，要按实际发布环境确认，不把旧接线永久写死为唯一方式。

### 7.2 角色登记与发现

会话建立后在队内网登记“赛季/赛事、阵营、岗位、机器人ID、设备实例ID、会话编号、协议版本、可提供的画面”。可以在指定队内网卡上做UDP发现，再用可靠连接交换状态；发现失败有“填队友地址”的备用入口。不是把不认识的同网段电脑默认当可信队友。

界面显示“红方重装、红方3号步兵”，不再显示A/B。重复身份、对方阵营、版本不兼容、连接到本机、上局残留会话要明确拒绝或提示。对同一对终端只保留一条有效连接，解决双方同时发起的重复连接。队伍配置/本地确认绑定设备，心跳和会话编号用于断线清理。

指挥席退出，地面操作手仍看本车画面、正常控制；任务和队友状态显示失联。共同信息服务不能成为本车控制必经节点。

### 7.3 视频、状态与任务各走适合的方式

- 视频优先转发已经编码的完整帧，避免截图、重复压片。每路声明编码类型、参数、来源、帧号与接收时间。当前只转发主HEVC，工业相机H.264共享属于新增功能。
- 主视频首先保证本车；指挥席默认“一路重点视频＋其他按需预览”。缩小窗口并不会自动减少原码流解码负担；需暂停非重点解码或提供真正低负载预览，并实测代价。
- 有界队列、落后检测、关键帧恢复；随意丢掉H.264/HEVC参考帧会影响后续帧，必须遵守解码恢复路径。协议有最大长度、来源数量与消息速率限制。
- 状态带来源、更新时刻、序号和有效期，队友转发保留原来源与会话，禁止循环转发。数据过期显示年龄，不无限保持“正常”。
- 战术任务有任务ID、目标人、内容、地图点、创建时刻、有效期与状态。使用“已收到/接受/执行/完成/无法执行/取消”，重复消息不重复创建任务。
- “队员请掩护”是人对人任务；“地图标记”是官方赛事消息；“机械臂动作”是本体控制。三者不共用一个含糊的发送按钮。
- 各机未同步的时间不能直接相减称端到端延迟。队内校时记录误差；官方视频没有统一曝光时间时，只报告可测的接收/转发/显示时间和画面年龄。

**2026-11-18 静态初稿已完成：** [打开 UL 3V3 地图母图](../源码/resources/rmul-2027-3v3.svg)。用浏览器打开即可放大。尺寸按图 3-5 围挡内沿 12×8 m；简图的 2.5 m、4.5 m 两段，在同页独立读像素折算约 2.492 m、4.503 m。此结果只校验图纸比例。隧道用虚线标位置，不画未确定的地下边界。UL 离线体验和正式客户端的 3V3 岗位显示均已接入此图。原操作界面的旧地图独立保留。

**制作和队员验收按这个顺序：**

1. **取尺寸，画母图。** 在可缩放的矢量图中按尺寸绘制场地内框、主要地形和区域；以毫米读图，应用内部统一用米。把图号、版本、哪几条边有尺寸注明写在地图资源旁，不把整个规则 PDF、截图和中间草图塞进发布包。
2. **用没参与绘图的尺寸复查。** 对照图 3-5 的 2500、4500 mm 等尺寸线，事先留出至少两条作检验，用图上同一对端点量，不用参与定比例的外框证明自己画得准。保留一个核对表：图上标值／图中量值／差多少。没有标尺寸的边写“示意”。规则给出的场地制造容差不是画图时允许的误差。
3. **给队员过眼。** 第一次交付并排看“规则图＋我们的简图”，队员不读教程就能分清两边、中央区和隧道，不把隧道顶当作下面的地面。改图只动母图。屏幕长宽不合就留边；在两种窗口大小切红蓝方，同一地形和标签应一起转向、字保持正着。
4. **接入离线版。** 使用同一场地坐标系，明确原点、单位和轴向。用四角和内部已知点做固定样例；在两种窗口尺寸下检查显示、点击还原到同一点。在副屏或高缩放下重复一次。实地位置来源未经验证就只展示底图；回放标注与现场数据明确区分。
5. **遇到新版资料只有斜视图时才做校正。** 有同一地面上四个不共线、且已知平面位置的对应点，可以把这一层拉正，再用没参与校正的第五点检查。高台顶面和隧道底面不是同一个平面，不能用同一次变换推位置；被挡住的部分也无法由一张图恢复。缺独立校验点就只画示意，等官方尺寸图或现场测量再替换。
6. **应对后续规则更新。** UL 和 UC 各有独立的地图版本、图例和校验点。新规则如果只改区域名称，就只改标注；如改了外形、尺寸或方向，就重画涉及部分，并重跑对应点测试。旧版回放仍标原地图版本，找不到对应底图时提示，不悄悄套新图。

## 9 Unity三维地图怎么接 才真的有用

### 9.1 已查到的开源实际范围

[diaofenyuan/RMUC_2027map_unity](https://github.com/diaofenyuan/RMUC_2027map_unity)在本轮读取的提交 `f55769a94578362f84e7cd25fe0b3f5fc5e11a8a` 提供Unity场地工程和二维资源。文件树唯一C#文件是编辑器自动打开场景脚本；未见运行时机器人接入、队内通信或指挥控制脚本。因此它适合做场景起点，实时指挥功能需自己实现。

项目指定Unity 2022.3.62f1，模型约707万三角面；作者声明坐标属于内部参考、`map_ready=false`。本轮未找到仓库LICENSE文件。采用前确认素材分发条件、锁定版本，再做模型简化和坐标核验；不将整个大模型和Unity Library搬进luojiafox。

### 9.2 最小可用三维版

- 构建可离线运行的Unity Player，队员使用时无需打开Unity Editor。
- 首先显示地形和从主客户端送来的合法位置、队友名称、任务点；模型只是地图显示，不生成额外敌情。
- 与二维共用同一套坐标和状态，点选机器人可切对应队友视频；当前数据过期时同步淡出/标记。
- 提供俯视、斜视、重点区域三种固定视角，一键回正。二维继续作为快速总览。
- 用简化网格、简化材质、关闭不必要效果和限定刷新率控制GPU开销；背景地图先以30fps为试验档，最终由目标设备实测确定。
- 不确定高度时保持未知；仅有XY不能可靠判断上下层。地形碰撞检测不能替代传感器证明机器人在某层。

### 9.3 判断三维值不值得保留

让同一批队员用二维和三维完成同样的回放任务：定位队友、辨认高低层、找出目标点、发出可理解的任务、发现过期信息。记录完成时间、误点次数、错认层数、视线切换次数和主视频/输入受影响情况。

三维只在高低差、遮挡理解等任务确有帮助时作为推荐；一般战况总览仍可默认二维。以后路线建议还需要车型宽高、坡度、转弯和实测通行能力，地图颜色或看起来有路都不能证明车能通过。

## 10 后续岗位需求怎样进版本

重装优先核对相机来源、机构状态是否有可信反馈，界面为断更、未安装、未获确认分别留出文字。指挥席先实现二维赛事信息和队友视频按来源显示，独立验证授权与显示规则。车上原有功能继续按现行部署教程维护；新岗位专用硬件单列需求，不让一个没有接口或没有实物的按钮挡住联盟赛基础版。

## 11 实施顺序：一条主线，三个可以停下交付的版本

**开发按可用版本走。** 不先花几周重写整个底层。M1–M3先只打通“UL步兵一个岗位、一场回放、一张新地图”；同一套测法跑通后再加重装和队友。硬件条件和样例可并行收集，但上一版不稳不发布下一版。下表保留各阶段的目标和验收方法，当前完成进度以本页顶部的里程碑为准。

| 顺序 | 这一版做什么、改动主要落在哪 | 实际验收，失败怎么处理 |
| --- | --- | --- |
| M0 留住现版，定设备和样例 | 记交付 EXE 校验值、屏幕分辨率/缩放、物理视频口；沿用已有离线入口。选一段双路旧录流、一个可公开分发的小样例，配一组带标准答案的2027比赛消息。列出来源、样例名和基准版本 | 在当前 Windows 上实际打开现版、放大窗口、开菜单、回到画面；双路像素对照用原有基准。内置样例与维护者私有大录流分开，不能交给队友一条缺素材的命令 |

| M4 发布UL双机有线候选版 | 队友画面从登录身份自动命名和配对；官方连接状态与队内连接状态分开显示。正式场地的席位和网线由队员按部署教程接 | 两台真电脑走队内有线网络；分别测试同名冲突、掉一台、换边、重连、慢接收机。本车画面不被拖停；旧身份的最后一张图不能顶替新队友。双开同机只算开发测试。正式官方接入另列一项，拿到现场证据再标通过 |

| M7 做可删除的三维试验 | UC场馆只读浏览，独立进程。二维保留为默认；三维启动慢、关闭或崩溃都不影响现有客户端。未获许可的素材不进发行包 | 同一批新队员用二维和三维各找一次看台/坡道/地形层级，交换先后顺序；记录用时和答错次数，另测开三维前后视频长停顿。没有可重复的好处，就只留训练场馆浏览，赛用版不带 |
| M8 冻结赛用候选 | 只打包已通过的岗位和功能；一个正式入口、一个部署教程、一份精选数据。保留26实车包及上一可用发行版本；车端历史与接入条件仍在部署教程 | 在另一台干净电脑按教程从头走一次；官方联调、实际接屏、整局换边和旧版回退分别打勾。最终桌面连同支架、供电、扩展坞一并实摆，验接收端无遮挡、散热正常（制作规范S148–149） |

**三道交付线：** M3能让人体验；M4通过真实有线双机和对应官方验证才作为UL正式候选；UC另行验收，不拖住UL。M7是实验，可取消。谁来配合：M0–M3以客户端维护者为主，M3请一名新队员；M4需要两台有线电脑；M5需要笔记本和一块真HDMI屏；涉及官方席位、场地设备时再约现场人员。等硬件期间继续做可离线核对的部分。

### 11.1 每一步都要自己跑过 关键阶段交给CH复现

每个实施步骤执行同一条交付流程：**先说明要验证什么 → 完成修改 → 实际运行正常流程和相关异常流程 → 修复本步失败 → 给出可复现版本和结果。** 代码审查与编译只是其中一部分，实际运行验证是每步完成条件。

- 每步根据改动选择测试：界面要实际打开操作，协议要让样例消息经过真实解析和显示，视频要真实解码显示，通信要经过实际收发。M0可点击界面原型也要实际走一遍，并清楚标为原型。
- 新功能要检查，受它影响的旧功能也要回归。涉及性能时用相同设备、素材和配置做前后对照，保留失败结果和修复后的复测。
- 涉及身份、控制、数据正确性、闪退或本步核心功能的失败，修好并复测后才算本步完成。硬件尚未到位时写明“软件验证完成、双机/双屏/官方端/实车待测”，相关硬件验收保持未完成；可以继续不依赖该项的工作。
- 结果必须对应交给CH的那份程序：记录版本/校验值、设备、素材、参数、实际操作、预期与实际结果。测试版通过后又改代码，需要重测受影响部分，不能沿用旧结果充当新结果。
- 有界队列、真实发送预算、像素一致性、输入权限等已有约束继续执行；体验模式必须走独立离线入口，不创建官方连接、不发送车辆指令；样例失败就显示错误，不自动退回正常客户端。测试画面和模拟指令不进入车辆链路。
- 内部小步骤由开发者自行完成测试，不让CH逐条代测。关键里程碑提供试用版本，CH亲自复现并确认操作效果，再定下一阶段的交互与功能取舍。

## 12 验收要能量化 也要让人用得舒服

### 12.1 测量原则

新旧版用同一台设备、同一录流、同一配置；单独记录屏数、视频来源数、是否打开3D。客户端耗时不冒充车到屏延迟；新增性能门限是拟定目标，不写成已经达到。

| 验收内容 | 怎么测 | 判读 |
| --- | --- | --- |
| 身份与控制正确 | 每赛事/角色、红蓝、重复身份、切角色、断线、回放、焦点变化 | 不串车、不产生未授权上行，辅助窗不发本车键鼠 |
| 2027数据正确 | 给每机器人不同数值，缺字段/超长数组/乱序/断更/保留位 | 显示对象、单位、状态正确；未知不变成0或旧正常值 |
| 原视频一致 | 保留相同接收包，独立重放比对像素 | UI升级不能改变原B档内容；后处理若新增另标 |
| 本机输入响应 | 复用已建立的探针，测单屏/双屏/3D开关 | 同条件P95拟定不劣化超过10%且不超2ms额外增量；超出先定位，不能挑好看轮次 |
| 本机视频延迟 | 收齐所需码流到提交显示；分别看主、副、队友 | 拟定P95新增不超10ms；无法做到时降低辅助负载并重测 |
| 新图更新与年龄 | 用不同源帧编号计数，冻结时年龄继续长 | 不把重复绘制60fps当60张新图；弱机档写明实际来源/显示能力 |
| 多屏行为 | 扩展/复制、分辨率/DPI、拖窗、拔HDMI、睡眠恢复、关闭副窗 | 重要面板始终可找回，控制状态清楚，显卡恢复不崩 |
| 网络恢复 | 队友掉线、重复/乱序/慢消费者、重连、双方同时连接 | 不无限积压、不循环转发、不把上一局任务或动作重发 |
| 地图正确 | 四角＋内部点、红蓝切换、点击往返、桥/隧道高度未知 | 坐标转换误差与定位误差分开，不伪造楼层 |
| 首次使用 | 未参与开发的队员按README走开局流程 | 记录耗时、错误与求助；建议保存配置后3次以内主要操作进入工作台 |
| 任务与三维收益 | 同样场景分别用旧UI/新UI、2D/3D | 任务确认时间、误点、漏看、错认和主视角受影响均列出 |

### 12.2 测试分级

日常改动跑涉及的自动回归＋5–10分钟离线冒烟；网络变化用两台电脑；双屏变化用真实两屏。重要阶段做3轮完整比赛时长演练，UL 3V3每轮5分钟，UC每轮7分钟。大量加视频/3D或准备赛用冻结时才安排集中长测，时长先与CH排定，不每轮默认占一小时。

当前仍有短测内存增长观察项、旧长测未全通过及新版实车窗口/菜单复测项。先做针对性诊断、补齐相关失败证据，历史结果保留原口径；“几分钟没闪退”不能覆盖为“稳定性全面完成”。

飞镖命中后的界面遮挡机制、黄牌等处罚、普通视频断流分别建状态：UC第111页明确终端仍可正常收图，不能直接等同所有处罚也可显示，亦不能随意实现全黑。以对应规则、收到状态、各席权限决定内容，并应用到所有窗口、队友转发和3D数据消费；人工演示数据不得绕入赛用显示。

## 13 仓库和发行怎么保持干净

- 保持仓库四个子系统并列，不新增第五个顶层工程。客户端的新模块仍在`luojiamaster/源码`内。
- 当前用法放客户端README；部署放本文件夹README；未来路线只维护本文件；已发生、不能合并掉的证据放`档案`。
- 运行入口保持一个luojiamaster。可提供“联盟赛”“超级对抗赛”快捷入口，实际指向同一个应用与不同配置，不发一堆兵种EXE。
- 普通UL发行包包含必要资源即可；Unity模块以后单独做可选附件，由主应用启动。保持现行唯一入库EXE约定，新增大体积发行资源的存放方式在M7确定。
- 赛场运行不安装Unity编辑器、不临时联网下载依赖、不加载在线地图；官方模型源、全录流、构建缓存和试跑日志放维护机或专门发行附件。
- 分支/里程碑保存可回退版本；生产目录只放当前明确版本，软件内显示版本、规则版本、地图版本。用户自行执行Git提交/上传。
- 开源引用记录项目、提交、许可、使用范围；外部工程不整份塞进仓库。未确认许可的地图先研究，正式分发前补齐。
- 修改正式客户端时继续核`C:\rm26build`、中文宽字符路径、脚本编码、同步EXE与MD5；不因新UI绕开既有稳定性保护。

## 14 谁配合 哪些事现在就能做

CH负责产品取舍、队员体验、优先级与里程碑验收；客户端开发负责协议/状态/界面/网络/测量；电控负责本体字段、模式、限位和动作确认；算法负责相机/定位的数据来源、坐标和误差；操作手负责真实任务反馈。若暂时只有CH与开发助手推进，就先按M0–M4收敛，不把待协作者到位写成已具备。

**下一轮建议直接交付M0的四样东西：**

1. 欢迎/赛事/岗位/身份的连贯界面稿，以及UL重装、UL步兵、UC重装双屏、UC指挥双屏示意；先让CH看懂并挑布局。
2. 真实电脑的硬件盘点与双屏/有线连接图，标出可直接用、需要补配、需要现场确认。
3. 2027协议字段与角色权限的首批测试样本，尤其血量顺序、地图单位、装配权限和私有载荷，形成后续开发的对照。
4. UL 3V3 二维地图初稿：按第 8 节用图 3-5 描绘，先看规则图与简图的对照，再进入客户端集成。

先做能点通一趟的UL步兵样板，再把用得上的共用部分提出来。Unity同时可以做离线资源评估，但不挤占UL可用版的主线。

### 14.1 第一场拿来验收的“故意刁难”回放

示例（不是比赛记录）：先送 `[101,103,104,107,201,203,204,207]`，再告诉客户端自己是红方3号。身份到达前只显示“待确认”；到达后红3显示103、蓝3显示203、7号对应107/207，UL 3V3不把4号画成阵亡。把身份换成蓝3重新跑一次，己方103应落在蓝3。随后暂停、恢复、平局结算、开下一局；新局不出现上局比分，画面暂时不来时不拿上一局图充数。这条回放同时能验登录、消息先后、换边、地图和屏幕上真正显示的数字。现码 `main_window.cpp` 约429行先看身份是否为红，身份未到时会走非红分支；这是代码路径判断，尚未用新版做实测。

**给队员的第一轮试用只要约3分钟：** 打开体验版 → 选UL 3V3步兵 → 观察两路画面并打开工业相机 → 看一次冻结、恢复和换边。交付时附真实程序、可分发样例和预期截图。队员能答“我现在是谁、我看的哪路、这个数据是不是旧的”，才把入口交互算完成。现在可双击 EXE 选 UL 3V3 离线体验，试选岗、双路录流、地图视角翻转和重播。模拟冻结、正式换边和比赛数据回放仍在后续阶段。
